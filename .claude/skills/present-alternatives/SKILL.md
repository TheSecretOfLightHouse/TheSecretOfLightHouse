# 대안 제시

기술적 트레이드오프가 있는 결정이나 사용자가 요청한 비교에 적용한다. 규칙으로 답이 정해지거나 사소한 구현 선택이면 바로 작업한다. 순수 선호가 필수 입력이면 [요청 명확화](../clarify-ambiguous-request/SKILL.md)를 사용한다.

## 근거 수집

- [AGENTS.md](../../../AGENTS.md)와 [실행 정책](../../../docs/ai/01_AGENT_EXECUTION_POLICY.md)에서 작업 범위와 기존 결정을 확인한다.
- `Packages/manifest.json`과 `ProjectSettings/ProjectVersion.txt`에서 실제 패키지·에디터 버전을 확인한다. 계획된 도입을 설치 완료로 표현하지 않는다.
- 네트워크 선택은 [권위 경계](../../../docs/unity/NETWORK_AUTHORITY.md)와 [협업 경계](../../../docs/unity/SERVER_CLIENT_WORKFLOW.md)를 읽는다. 스타일·폴더 규칙은 [코딩 컨벤션](../../../docs/coding-convention.md)을 따른다.
- 현재 구현 상태(Mirror 권위·동기화 구현 여부)는 [아키텍처 §4](../../../docs/04-architecture.md#4-현재-코드의-배치)와 코드로 확인하고, 대안 비교에서 "코드에 이미 있는 것"과 "계획"을 구분한다.
- API·패키지 호환성처럼 달라질 수 있는 사실은 실제 패키지와 공식 문서로 검증한다. 미정인 기획·서버 빌드 설정·인원·담당자는 전제로 확정하지 않는다. 서버 실행 방식과 호스팅은 현재 설정과 문서에서 확인된 범위만 전제한다.

## 비교와 결정

1. 실제로 채택할 가치가 있는 대안만 추린다. 보통 2~3개면 충분하며 개수를 채우려고 후보를 만들지 않는다.
2. 대안마다 방식, 장점, 단점, 구현·검증 비용과 TheSecretOfLightHouse에서의 영향을 같은 기준으로 비교한다. 짧으면 문장으로, 비교 항목이 많으면 표로 정리한다.
3. 네트워크라면 서버 판정·클라이언트 표현, 파생 계산, 실제 사용하는 호스트·서버 실행 방식에서의 동작, M2 이상 검증 비용을 평가한다. 패키지라면 실제 버전 호환성과 도입 허용 범위를 확인한다.
4. 추천안을 명확하게 제시하고 근거를 연결한다. 미정 값에 따라 결론이 바뀌면 조건부 권장과 필요한 결정을 설명한다.
5. 기존 요청으로 결정할 수 있는 구현 선택은 추천안을 적용해 계속 진행한다. 게임 디자인·팀 계약·범위 확장 등 사용자 결정을 요구하는 경우에만 [요청 명확화](../clarify-ambiguous-request/SKILL.md)로 필요한 질문을 남긴다.

분석 요청 자체는 패키지 설치·코드 수정·새 시스템 도입 승인이 아니다. 사용자가 선택하면 같은 결정을 재확인하지 않고 허용된 작업을 수행한다.

# 문서–코드 일치도와 SQALE 코드 품질 평가

두 부분으로 나뉜다. 사용자가 한쪽만 요청하면 그 부분만 수행한다. 문서 자체의 품질은 [문서 품질 평가](../audit-doc-quality/SKILL.md), 특정 기능의 기획 공백과 구현 상태 서술은 [기획–코드 공백 검토](../review-design-code-gaps/SKILL.md)가 맡는다. 이 스킬은 둘과 달리 **수치로 측정하고 근거 표본을 밝힌다**.

## 지킬 것

- 읽기 전용이다. 코드·문서·씬·프리팹·`.meta`를 수정하지 않는다. 수정은 사용자가 보고서를 보고 별도로 요청한다. 보고서 저장을 요청받으면 Git 제외 `.claude/docs/{처음 쓴 날짜}/`에 두고 이어지는 평가는 원본을 갱신한다.
- 이 보고서는 **참고 지표**다. [검증 플레이북](../../../docs/ai/03_VERIFICATION_PLAYBOOK.md)의 `PASS/CONDITIONAL/REJECT` 판정이나 완료 상태를 대신하지 않고, 새 코딩 규칙이나 일괄 오류 등급을 만들지 않는다. 기능 결함의 심각도는 재현과 영향으로 따로 판단한다.
- 점수·비율은 표본과 가정을 함께 적는다. 정적 분석(Grep·읽기)으로 얻은 값이며 Unity 컴파일·Play Mode·4인 접속은 실행하지 않았다면 `런타임 미검증`으로 명시한다. 파일·타입이 존재한다는 이유로 기능 구현이나 동작을 인정하지 않는다([지식 맵](../../../docs/ai/07_PROJECT_KNOWLEDGE_MAP.md)의 확인 기준).
- 코드는 `Assets/01.Scripts/`만 대상으로 한다. `Assets/Mirror/`, `Assets/Plugins/`, `Assets/ThirdParty/`, `Library/`, `Temp/`, 생성 파일은 제외한다. 제외한 범위를 보고서에 적는다.
- 기준 우선순위는 최신 사용자 결정 → [제공된 v4](../../../docs/design/references/game-design-v4.md)다. 문서와 코드가 다를 때 어느 쪽이 맞는지 임의로 정하지 않고 [문제 대장](../../../docs/07-design-issue-register.md)의 버전 차이와 담당을 근거로 양쪽을 보고한다. 다른 담당의 코드를 평가한 결과를 전달하는 것은 괜찮지만 수정은 [소유권 확인](../check-code-ownership/SKILL.md)을 따른다.

## 부분 1. 문서–코드 일치도

### 1-1. 대상 문서

범위를 정하지 않았으면 코드 사실을 직접 서술하는 문서를 기본으로 한다.

| 문서 | 대조할 주장 |
|---|---|
| [아키텍처](../../../docs/04-architecture.md) | 폴더·층(Rules/Net/Server/View), 파일 위치, asmdef 참조, 현재 C# 파일 수, 네임스페이스 |
| [지식 맵](../../../docs/ai/07_PROJECT_KNOWLEDGE_MAP.md), [코드 소유권](../../../docs/CODE_OWNERSHIP.md) | 진입점 경로, 담당 폴더, `.github/CODEOWNERS` |
| [코딩 컨벤션](../../../docs/coding-convention.md) | 문서가 말하는 구조·규칙을 기존 코드가 따르는지 |
| [구현 로드맵](../../../docs/05-implementation-roadmap.md), [담당자별 작업](../../../docs/06-owner-work-plan.md) | 완료·진행 표기와 실제 구현 |
| [기술설계서](../../../docs/03-technical-design.md), [시스템 디자인](../../../docs/01-system-design.md), [게임 기획 v4](../../../docs/design/references/game-design-v4.md) | 코드에 구현된 범위의 규칙·수치·상태 전이·권위. 아직 구현하지 않은 규칙은 불일치로 세지 않는다 |

### 1-2. 주장 추출과 판정

1. 대상 문서에서 **코드나 설정으로 검증할 수 있는 주장**을 뽑는다. 유형: 경로·파일, 타입·멤버 이름, 폴더 구조·asmdef·패키지 버전, 수치·기본값(`[SerializeField]`·ScriptableObject), 상태·전이·계약(Command/Rpc, 권위, 허용 수신자), 담당·CODEOWNERS, 개수(파일 수 등).
2. 주장이 너무 많아 전수 확인이 어려우면 문서별로 균등하게 표본을 뽑고, 표본 수와 선정 방법을 적는다. 전수 확인한 문서와 표본 문서를 구별한다. 서술형 의도·밸런스·재미처럼 코드로 검증할 수 없는 주장은 분모에서 뺀다.
3. 각 주장을 코드 근거(`파일:줄`, 검색한 경로·패턴)와 함께 아래 중 하나로 판정한다.

| 판정 | 의미 | 일치율에서의 처리 |
|---|---|---|
| 일치 | 문서와 코드가 같다 | 1점 |
| 부분 일치 | 방향은 같으나 이름·수치·범위·층이 다르다 | 0.5점 |
| 불일치 | 문서와 코드가 다르다. 문서가 `완료`·`구현`이라고 쓴 것이 코드에 없는 경우 포함 | 0점 |
| 계획 미구현 | 문서가 계획·가안·미정이라 밝혔고 코드가 아직 없다 | 분모에서 제외, `구현 진행률`로 따로 보고 |
| 문서 누락 | 코드에 있는 기능·타입·폴더가 어느 문서에도 없다 | 일치율 분모에는 넣지 않고 `문서 커버리지`로 보고 |
| 확인 불가 | 런타임 실행·씬 YAML 직접 해석·외부 도구가 필요하다 | 분모에서 제외, 사유와 필요한 검증 수준 기록 |

4. 코드에서 못 찾았으면 검색한 경로·패턴과 한계를 적고 저장소 전체에 없다고 단정하지 않는다. 폴더·빈 타입·주석·패키지 존재는 구현으로 세지 않는다. 선언만 있는지, 로컬 동작인지, 서버 판정·클라이언트 연결까지 있는지 구별한다.
5. 불일치마다 `문서가 낡음`, `코드가 기획과 다름`, `문서 간 모순`, `판단 보류(결정 필요)`로 원인 후보를 붙이되 확정하지 않는다.

### 1-3. 지표

- **문서–코드 일치율** = (일치 + 0.5 × 부분 일치) ÷ (일치 + 부분 일치 + 불일치) × 100. 문서별·도메인별(`00.Common` ~ `99.Dev`)로 계산하고 전체 값은 문서별 값의 단순 평균이 아니라 주장 단위로 다시 계산한다.
- **문서 커버리지** = 문서에 언급된 코드 기능 단위 ÷ 코드의 전체 기능 단위. 기능 단위는 `Assets/01.Scripts/` 하위 기능 폴더(예: `05.Player/State`)로 하며, 기준을 보고서에 적는다.
- **구현 진행률** = 계획 문서가 요구하는 항목 중 코드가 있는 항목 ÷ 전체 항목. 동작 검증 완료와 구분해 `코드 있음`까지만 말한다.
- 표본이면 표본 크기를 함께 적고 "추정치"라고 쓴다. 표본이 20개 미만이면 비율을 신뢰하기 어렵다는 주의를 붙인다.

## 부분 2. SQALE 코드 품질

SQALE(Software Quality Assessment based on Lifecycle Expectations)은 품질 요구사항 위반마다 **수정 비용**을 추정해 합산하고, 이를 품질 특성 계층에 모아 기술 부채와 등급을 얻는 방법이다. 아래 모델은 SQALE의 구조를 따르되 규칙과 비용은 이 저장소 기준으로 정했다.

### 2-1. 품질 모델

특성은 SQALE의 8가지이며 아래 순서(수명주기 순서)로 부채가 아래에서 위로 누적된다. 낮은 특성의 문제는 높은 특성 달성도 막는다는 SQALE의 전제다.

`테스트성(T)` → `신뢰성(R)` → `변경성(C)` → `효율성(E)` → `보안성(S)` → `유지보수성(M)` → `이식성(P)` → `재사용성(U)`

### 2-2. 요구사항(규칙)과 단위 수정 비용

규칙의 출처는 [코딩 컨벤션](../../../docs/coding-convention.md), [아키텍처](../../../docs/04-architecture.md), [네트워크 권위](../../../docs/unity/NETWORK_AUTHORITY.md)다. 이 표는 문서가 요구하는 규칙을 SQALE 특성에 배치하고 탐지법·비용을 정한 것이며 **새 팀 규칙이 아니다**. 요구사항 열에 `측정 임계치`라고 적은 행은 문서에 값이 없거나 문서가 직접 요구하지 않는 설계 지침으로, 위반이 아니라 SQALE 측정을 위해 이 스킬이 가정한 참고 기준이다. 보고서에서 이 행의 부채는 `문서 요구` 부채와 따로 소계해 보여 주고 합계에는 둘을 구분해 적는다.

단위 비용은 한 건을 고치는 데 드는 사람-분의 **초기 추정치**다. 팀이 실제 수정 시간으로 보정하고, 보정하면 값을 보고서에 적는다. `영향`은 방치했을 때의 사업 영향 1(낮음)~4(치명)로 우선순위 정렬에만 쓴다.

| U1 | 재사용성 | 측정 임계치: 기능이 다른 기능의 내부 타입을 직접 참조하지 않고 `00.Common`·`Net/` 계약을 쓴다. 아키텍처 §3은 도메인 간 의존을 담당자 합의로 검토한다고만 한다 | 도메인 폴더 간 `using`·타입 참조 | 45/건 | 3 |
| U2 | 재사용성 | 측정 임계치: 정적 전역 상태·싱글턴에 의존하지 않는다 | `static` 가변 필드, `Instance` | 45/건 | 2 |

**허용된 예외**는 부채에서 빼고 보고서에 따로 적는다. 현재 문서가 명시한 것: 기존 타입·네임스페이스·직렬화 필드는 경계 이관에서 유지한다(컨벤션 §파일, 아키텍처 §5). 기능 루트에 책임이 섞인 기존 코드를 둘 수 있다(아키텍처 §2). 문서가 예외를 말하지 않는 위반은 부채로 센다. 새로 발견한 예외는 사용자에게 확인한다.

규칙이 현재 코드에 적용되지 않는 경우(예: Mirror 권위·동기화 코드가 아직 없으면 S1~S3, R2, E2)는 **해당 없음**으로 표시하고 "위반 0"으로 쓰지 않는다. 대상 코드가 없는 것은 품질이 좋은 것이 아니라 아직 측정할 것이 없는 것이다.

### 2-3. 계산

1. 규칙별로 위반 건수를 센다. 후보를 Grep으로 찾은 뒤 반드시 해당 줄을 읽어 확인하고 오탐을 뺀다. 자동 탐지로 확인하지 못한 규칙(M1·M3 등)은 표본 파일을 읽고 `표본 추정`으로 표시한다.
2. **수정 비용** = 위반 건수 × 단위 비용. 규칙 합이 특성별 `부채`(분)다.
3. **SQI(SQALE Quality Index)** = 전체 특성 부채의 합. 시간으로 환산해 보고하고 8시간을 1일로 쓴다. `문서 요구` 규칙의 소계와 `측정 임계치` 규칙의 소계를 따로 적는다.
4. **개발 비용** = 평가 대상 코드 줄 수 × 30분. 줄 수는 빈 줄·주석 줄을 뺀 C# 줄이며(SonarQube 기본 가정, 팀이 보정 가능) 측정 방법을 적는다. 이 가정은 부채 비율의 크기를 직접 바꾸므로 보고서 첫머리에 밝힌다.
5. **부채 비율** = SQI ÷ 개발 비용 × 100. 특성별 비율도 계산한다.
6. **등급**(부채 비율): A ≤ 5%, B ≤ 10%, C ≤ 20%, D ≤ 50%, E > 50%.
7. **누적 피라미드**: 각 특성의 누적 부채 = 그 특성과 그 아래 특성(T부터)의 부채 합. 어떤 특성에서 등급이 처음 떨어지는지 보여 준다.
8. **우선순위**: `영향 ÷ 단위 비용`이 큰 규칙, 같은 값이면 건수가 많은 규칙부터 상위 10개를 낸다. 영향이 4인 항목은 부채 합계와 별도로 먼저 보여 준다.

줄 수가 적은 코드는 개발 비용이 작아 비율이 크게 흔들린다. 전체 줄 수가 3,000줄 미만이면 등급보다 건수와 규칙별 부채를 우선 읽도록 보고서에 적는다. 단위 비용을 임의로 바꿔 등급을 맞추지 않는다.

### 2-4. 점검 보조 명령

저장소 루트의 PowerShell에서 실행한다. 모든 결과는 후보이며 줄을 읽어 확인한다.

```powershell
# 대상 파일과 코드 줄 수 (빈 줄·// 주석 제외)
$cs = Get-ChildItem Assets\01.Scripts -Recurse -Filter *.cs
$loc = ($cs | ForEach-Object { (Get-Content $_.FullName -Encoding UTF8 | Where-Object { $_.Trim() -ne '' -and $_.Trim() -notmatch '^(//|/\*|\*)' }).Count } | Measure-Object -Sum).Sum
"files=$($cs.Count) loc=$loc devCostMin=$($loc*30)"
# 규칙 후보 (E1·P1 등): 호출 위치 확인용
Select-String -Path $cs.FullName -Pattern 'Find(Object|WithTag|GameObjectWithTag)|SendMessage|\bInput\.(Get|mouse)|UnityEditor|#if UNITY_EDITOR|Debug\.Log' | ForEach-Object { '{0}:{1}: {2}' -f $_.Path.Substring((Get-Location).Path.Length+1), $_.LineNumber, $_.Line.Trim() }
```

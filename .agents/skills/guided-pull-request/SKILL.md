# 가이드 풀 리퀘스트

PR 생성·수정 요청에 적용한다. [AGENTS.md](../../../AGENTS.md)와 [실행 정책](../../../docs/ai/01_AGENT_EXECUTION_POLICY.md)을 읽고 요청이 초안인지 실제 게시인지 구분한다. 준비·검증을 먼저 끝내고 필요한 승인만 마지막에 받는다. 세션에서 확정한 본문과 게시 범위는 다시 승인받지 않는다.

## 브랜치와 변경 분석

1. 현재 브랜치, `git status`, remote와 실제 브랜치 목록을 확인한다. 작업 브랜치는 `feature/<이름>`이다. `main`이나 대상 통합 브랜치 자체에서 PR을 만들지 않는다.
2. base는 통합 브랜치 `develop`이다. 사용자가 다른 base를 지시하면 따르고, 원격에 `develop`이 없으면 만들지 말고 알린다. base가 확정되면 `git log <base>..HEAD --oneline`, `git diff <base>...HEAD --stat`과 diff를 읽는다.
3. 커밋되지 않은 작업과 push되지 않은 커밋을 구분한다. 무관한 파일을 임의로 커밋하지 않는다. 추가 커밋이 요청 범위에 포함되면 [가이드 커밋](../guided-commit/SKILL.md)을 따른다. push도 허용된 브랜치·범위에서만 수행한다.
4. 씬·`.meta`·네트워크 권위·밸런스 상수·대용량 바이너리를 확인한다. PR 크기·분할 기준은 [커밋·PR 컨벤션](../../../docs/commit-convention.md)의 커밋 단위(4장)와 `.github/PULL_REQUEST_TEMPLATE.md`에 있는 것만 적용하고, 서로 무관한 변경이 섞였으면 나눌 경계를 알린다. 없는 기준을 강제하지 않는다.
5. [review-design-code-gaps](../review-design-code-gaps/SKILL.md) 스킬로 변경 내용이 기획·문서와 일치하는지 확인한다. 문서와 코드가 다르면 최신 사용자 결정과 [v4 원문](../../../docs/design/references/game-design-v4.md)을 기준으로 어느 쪽이 낡았는지 확인해 PR 본문에 알린다. 문서에 없는 변경은 근거를 확인하고, 근거가 없으면 PR 본문에 알린다.

## 제목·본문·검증

- `.github/PULL_REQUEST_TEMPLATE.md` 또는 실제 선택된 PR 템플릿이 있으면 매번 읽고 구조를 따른다. 안내용 HTML 주석만 제거한다. 템플릿이 없으면 없음을 밝히고 [커밋·PR 컨벤션](../../../docs/commit-convention.md) 6장(PR 제목)과 이 스킬의 이슈·검증·시각 자료·남은 작업 항목으로 본문을 준비한다.
- 제목은 [커밋·PR 컨벤션](../../../docs/commit-convention.md) 6장의 `<타입>: <무엇>` 형식으로 변경 결과를 설명한다. 여러 커밋이면 대표 타입 하나를 고른다.
- 관련 이슈 번호는 확인된 것만 연결한다. 모르면 미확인으로 남기고 필수 입력인 경우에만 질문한다.
- 확인한 항목만 체크한다. 실행하지 않은 테스트는 체크하지 않고 절차와 미검증 이유를 적는다. 사용자 보고와 직접 실행 결과도 구분한다.
- 네트워크 변경은 [검증 플레이북](../../../docs/ai/03_VERIFICATION_PLAYBOOK.md)과 [멀티플레이 테스트](../../../docs/ai/04_MULTIPLAYER_TEST_PROTOCOL.md)의 M2 이상 기준을 따른다. 인원 조건은 현재 프로젝트 문서에서 확인한 값만 사용한다.
- 시각적 변경이면 실제 캡처를 첨부하거나 필요한 자료를 요청한다. 해당 없는 템플릿 섹션은 저장소 양식에 따라 표시하고, 검증한 것처럼 채우지 않는다.
- 남은 작업·알려진 문제·테스트 등급을 근거대로 적는다. 임의의 AI 표기를 PR 본문에 추가하지 않는다.

## 리뷰 담당과 생성

1. `.github/CODEOWNERS`가 있으면 실제 규칙을 읽고, 없으면 [담당 경계](../../../docs/CODE_OWNERSHIP.md)와 사용자 지정으로 리뷰 담당을 확인한다. 계정명·권한·자동 리뷰 동작을 추측하지 않는다.
2. 먼저 `gh --version`과 `gh auth status`로 gh 설치·로그인을 확인한다. 없으면 [gh 설치와 로그인](../../../docs/unity/UNITY_START_HERE.md#github-cli-설치와-로그인)을 사용자에게 안내하고 완료 뒤 이어 간다. `gh api user --jq .login`으로 작성자를 확인한다. 담당자는 요청에 다른 지정이 없으면 `@me`로 둔다. 작성자 자신을 리뷰어로 지정하지 않는다. 담당자 계정이 미정이면 추측해 리뷰 요청을 보내지 않는다.
3. 제목·본문·base/head·담당자·리뷰어를 제시한 뒤 승인된 요청을 실행한다. CLI를 쓰면 저장소 밖 UTF-8 임시 파일과 `--body-file`로 실제 줄바꿈을 보존한다.

```text
gh pr create --base <확인한-base> --head <작업-브랜치> --assignee @me --title <제목> --body-file <임시파일>
```

리뷰어 옵션은 확인한 계정만 추가한다. 안내 뒤에도 gh를 쓸 수 없으면 게시 가능한 제목과 본문을 제공하고 미생성임을 알린다. 생성 결과와 URL을 확인하고, Codex의 `attach_artifact` 도구가 있으면 생성한 PR을 현재 채팅에 연결한다. 기존 PR을 수정·리뷰하는 요청도 그 PR을 연결한다.

생성 결과가 불명확하면 기존 PR을 조회해 중복 생성을 막는다. 리뷰어 설정만 실패했다면 같은 PR의 해당 설정만 보완하고 결과를 보고한다. 요청하지 않은 병합·추가 이슈·다른 PR 수정은 수행하지 않는다.

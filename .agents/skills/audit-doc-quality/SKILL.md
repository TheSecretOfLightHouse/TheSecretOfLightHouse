# 문서 품질 평가

[claude-md-improver](https://github.com/anthropics/claude-plugins-official/blob/main/plugins/claude-md-management/skills/claude-md-improver/SKILL.md)의 `발견 → 평가 → 보고서 → 제안 → 승인 후 적용` 흐름과 A~F 등급을 따르되, 이 저장소의 문서 규칙에 맞게 기준과 배점을 다시 정했다. 문서와 코드의 일치도·코드 품질은 [문서–코드 일치도·SQALE 평가](../audit-doc-code-sqale/SKILL.md)가 맡는다.

평가는 읽기 전용이다. 보고서까지는 파일을 수정하지 않는다. 수정은 사용자가 항목을 승인한 뒤 그 항목만 적용하고, 커밋·푸시·게시는 요청 범위에 없으면 하지 않는다. 사용자가 보고서 저장을 요청하면 Git 제외 `.claude/docs/{처음 쓴 날짜}/`에 두고 이어지는 평가는 원본을 갱신한다.

## 기준 문서

- [문서 분류와 현재성 기준](../../../docs/DOCUMENTATION_POLICY.md): 위치·자립성·현재 규칙과 계획의 분리·금지 잔재. 이 스킬의 `현재성`, `자립성`, `금지 잔재` 점수는 이 문서를 근거로 한다.
- [AI 작업 문서](../../../docs/ai/README.md): 문서 지도와 스킬 목록. 새 문서는 [읽기 안내](../../../docs/00-reading-guide.md)·이 문서의 문서 지도에서 도달할 수 있는지, 새 스킬은 이 문서의 스킬 표에 있는지 본다. [지식 맵](../../../docs/ai/07_PROJECT_KNOWLEDGE_MAP.md)은 기능별 코드 진입점 지도이므로 문서·스킬마다 항목이 있어야 하지는 않는다.
- 규칙 우선순위는 최신 사용자 결정 → [제공된 v4](../../../docs/design/references/game-design-v4.md)다. 보존 자료(`docs/design/archive/`)가 v4와 다른 것은 결함이 아니라 [문제 대장](../../../docs/07-design-issue-register.md)의 버전 차이일 수 있으니 대장을 확인한 뒤 판정한다.
- 한 규칙의 단일 기준은 기획서·코딩 컨벤션·커밋 컨벤션 등 해당 문서다. 다른 문서가 같은 규칙을 다시 정의하면 중복으로 본다.

## 1. 발견

범위를 사용자가 정하지 않았으면 아래를 모두 대상으로 한다. 파일 목록은 Glob으로 만들고 존재하지 않는 항목은 건너뛴다.

| 구분 | 위치 | 비고 |
|---|---|---|
| 지침 | 루트 `AGENTS.md`, `CLAUDE.md`(`@AGENTS.md` 가져오기), 하위 폴더의 `CLAUDE.md`·`AGENTS.md` | `CLAUDE.md`는 가져온 내용까지 한 문서로 평가한다 |
| 공유 문서 | `docs/**/*.md` | `docs/design/archive/`와 `references/`는 보존 자료라 현재성 감점 대상이 아니고 출처·표기만 본다 |
| 스킬·에이전트 정의 | `.claude/skills/*/SKILL.md`, `.agents/skills/*/SKILL.md`, `.claude/agents/*.md` | 스킬은 두 위치의 사본이 같은지도 비교한다. 에이전트 정의는 `docs/ai/TOOL_SETUP.md`·`08_SUBAGENT_ORCHESTRATION.md`의 안내와 맞는지 본다 |
| 템플릿 | `.github/` 아래 PR·이슈 템플릿, `CODEOWNERS` | 문서가 가리키는 이름·담당과 일치하는지 본다 |

개인 파일(`CLAUDE.local.md`, `.claude/settings.local.json`, 전역 `~/.claude/CLAUDE.md`)은 사용자가 지정하지 않으면 읽지 않는다. 지정해도 비밀값은 보고서에 옮기지 않는다. `.claude/docs/`·`.claude/handover/`의 개인 기록은 평가 대상이 아니다.

## 2. 평가

문서 유형별로 100점 만점 기준표를 쓴다. 각 기준은 근거(경로·줄·확인한 명령)와 함께 점수를 매기고, 확인하지 못한 기준은 0점 처리하지 말고 `미평가`로 표시해 분모에서 뺀다.

### 2-1. 지침 문서 (AGENTS.md · CLAUDE.md · 스킬)

| 기준 | 배점 | 만점 조건 |
|---|---:|---|
| 명령·절차 | 20 | 작업별로 읽을 문서·실행 방법이 있고 바로 따라 할 수 있다. 명령은 실제 도구와 경로를 쓴다 |
| 구조·맥락 | 20 | 프로젝트 전제(엔진·패키지 버전·담당·실행 구조)와 문서 간 관계가 코드·설정과 맞는다 |
| 비자명한 규칙 | 15 | 코드만 봐서는 알 수 없는 제약(권위 경계, 수정 금지 영역, 승인 조건)을 담았다 |
| 간결성 | 15 | 코드로 알 수 있는 사실, 일반론, 한 번뿐인 수정 기록 없이 짧다. 같은 규칙이 두 곳에 없다 |
| 현재성 | 15 | 링크·경로·버전·담당·스킬 이름이 현재 저장소와 일치하고 폐기된 구조를 안내하지 않는다 |
| 실행 가능성 | 15 | 조건과 행동이 구체적이다. 금지는 대안을, 승인은 대상과 시점을 함께 적었다 |

### 2-2. 공유 문서 (docs/)

| 기준 | 배점 | 만점 조건 |
|---|---:|---|
| 현재성 | 25 | 경로·링크·버전·담당·수치가 현재 코드·설정·최신 결정과 일치한다. 낡은 내용은 낡았다고 표기돼 있다 |
| 구분 명확성 | 20 | 확정·가안·미정, 계획·구현·검증이 서로 다른 표기로 나뉘고 완료를 단정하지 않는다 |
| 단일 기준·비중복 | 15 | 한 규칙이 한 문서에만 정의되고 나머지는 링크한다. 문서 간 모순이 없다 |
| 자립성 | 15 | 필요한 결론·조건·한계가 본문에 있고 개인 기록·외부 저장소를 필독으로 요구하지 않는다 |
| 실행 가능성 | 15 | 읽은 사람이 다음 행동·담당·완료 기준을 알 수 있다 |
| 구조·가독성 | 10 | 제목 계층, 표, 길이가 적절하고 지도 문서([읽기 안내](../../../docs/00-reading-guide.md), [AI 문서](../../../docs/ai/README.md))에서 도달 가능하다 |

### 2-3. 결정적 점검 (모든 문서에 먼저 실행)

판단 이전에 기계적으로 확인할 수 있는 항목이다. 결과는 `현재성`·`간결성`·`자립성` 점수의 근거로 쓴다.

1. **상대 링크 존재**: 아래 PowerShell을 저장소 루트에서 실행한다. 앵커(`#...`)는 파일 존재만 확인하고 제목 일치는 Grep으로 따로 본다.

```powershell
$root=(Get-Location).Path
$files=@(Get-Item AGENTS.md,CLAUDE.md,.github\PULL_REQUEST_TEMPLATE.md -ErrorAction SilentlyContinue)+@(Get-ChildItem docs,.claude\skills,.agents\skills -Recurse -Filter *.md)
$n=0;$bad=@()
foreach($f in $files){$t=Get-Content $f.FullName -Raw -Encoding UTF8
 foreach($m in [regex]::Matches($t,'\]\((?!https?:|mailto:|#)([^)#\s]+)(#[^)]*)?\)')){$n++
  $p=[uri]::UnescapeDataString($m.Groups[1].Value)
  if(-not (Test-Path -LiteralPath (Join-Path $f.DirectoryName $p))){$bad+=('{0} -> {1}' -f $f.FullName.Substring($root.Length+1),$p)}}}
"files=$($files.Count) links=$n broken=$($bad.Count)";$bad
```

2. **본문 속 경로·타입 이름**: 문서가 `Assets/...`, `docs/...`, 타입명으로 가리키는 것이 실제로 있는지 Glob·Grep으로 확인한다. 깨진 항목은 줄 번호와 함께 모은다.
3. **버전·패키지**: 엔진·URP·Input System·Mirror 버전을 말하는 문서는 `ProjectSettings/ProjectVersion.txt`, `Packages/manifest.json`과 대조한다.
4. **담당·계정**: 담당자 이름·GitHub 계정은 [코드 소유권](../../../docs/CODE_OWNERSHIP.md)과 `.github/CODEOWNERS`와 대조한다. 김민성은 게임 코드 담당이 아니다.
5. **스킬 사본 일치**: `.claude/skills/{이름}/SKILL.md`와 `.agents/skills/{이름}/SKILL.md`를 SHA256으로 비교하고, 한쪽에만 있는 스킬이 없는지, [AI 문서](../../../docs/ai/README.md)의 스킬 표·개수와 맞는지 본다. 다른 파일은 줄 단위로 비교해 **Claude/Codex 도구 이름이나 호출 방식을 말하는 줄**(예: 질문 도구, PR 연결 도구)만 다르면 의도된 차이로 보고 감점하지 않는다. 그 밖의 줄이 다르면 불일치로 센다.
6. **금지 잔재**: 다른 프로젝트 이름, 개인 절대 경로, 비밀값·계정·토큰 패턴을 Grep으로 찾는다. 비밀값이 발견되면 값을 보고서에 쓰지 말고 파일·줄만 알린다.
7. **중복 정의**: 같은 규칙 문장이나 표가 두 문서 이상에 있는지 핵심 문구로 Grep한다. 링크로 대체 가능한지 판단한다.

## 3. 등급

| 등급 | 점수 | 의미 |
|---|---|---|
| A | 90~100 | 현재 코드와 맞고 바로 쓸 수 있다 |
| B | 70~89 | 대체로 좋고 사소한 빈틈이 있다 |
| C | 50~69 | 기본은 있으나 핵심 정보가 빠졌거나 일부 낡았다 |
| D | 30~49 | 성기거나 낡아서 오해를 만들 수 있다 |
| F | 0~29 | 없거나 심하게 낡았다 |

점수는 `획득 점수 ÷ 평가한 기준의 배점 합 × 100`으로 환산한다. 점수는 문서 개선 우선순위를 정하는 도구이며 기획의 옳고 그름이나 구현 완료를 뜻하지 않는다. 숫자를 맞추려고 기획 내용을 바꾸자고 제안하지 않는다.

## 4. 보고서

수정하기 전에 아래 순서로 먼저 낸다. 결론을 첫 줄에 두고 한국어로 쓴다.

```markdown
## 문서 품질 보고서
- 평가 범위: N개 파일 (제외한 범위와 이유)
- 평균 점수: NN (등급), 수정 권장: N개
- 결정적 점검: 링크 N개 중 깨짐 N, 경로 불일치 N, 사본 불일치 N, 금지 잔재 N

### 파일별 요약
| 파일 | 유형 | 점수 | 등급 | 가장 큰 감점 |
|---|---|---:|---|---|

### 파일별 상세 (C 이하 또는 요청한 파일)
기준별 점수 표 → 문제(경로:줄, 근거) → 권장 수정

### 미평가·한계
확인하지 못한 기준과 이유
```

가장 점수가 낮은 문서와 영향이 큰 문제(오해로 잘못된 작업을 유발하는 낡은 지침, 서로 모순되는 규칙)부터 정렬한다. 문서만 보고 판단한 항목과 코드·설정으로 확인한 항목을 구별한다.

## 5. 수정 제안과 적용

1. 제안은 실제로 도움이 되는 것만 한다. 코드로 알 수 있는 내용 반복, 일반 모범사례, 한 번뿐인 수정 기록은 추가하지 않는다.
2. 각 제안은 `파일 · 줄`, 변경 전후 diff, 이유 한 문장으로 보여 준다. 규칙은 단일 기준 문서에만 쓰고 다른 문서는 링크로 바꾼다.
3. 사용자가 승인한 항목만 Edit로 적용하고 기존 구조·표기(확정·가안·미정)를 보존한다. 파일 이동·삭제는 들어오는 링크와 나가는 링크를 함께 정리한다([문서 분류](../../../docs/DOCUMENTATION_POLICY.md)의 갱신 순서).
4. 적용 뒤 결정적 점검을 다시 실행해 새로 깨진 링크가 없는지 보고한다. 실행하지 않은 점검은 `미실행`으로 적는다.
5. 다른 담당의 문서나 공용 계약 문서를 수정해야 하면 [소유권 확인](../check-code-ownership/SKILL.md)을 먼저 한다.

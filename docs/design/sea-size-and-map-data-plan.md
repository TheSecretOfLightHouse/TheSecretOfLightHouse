## 1. 요청과 설계 경계

변경된 등대섬과 자원섬을 다시 측정하고, 겹침 없이 짧은 항해가 가능한 간격으로 섬·각 해역·전체 맵을 줄인다. 파도 때문에 평지보다 느린 실제 이동과 4인 플레이를 기준으로 삼는다. 이동 위험은 거리를 늘리는 대신 몬스터 스폰 수 증가로 조정한다. 지도·미니맵 제작에 필요한 월드 생성 데이터를 최명기 담당자에게 제공한다.

이번 산출물은 설계 문서다. 코드·씬·프리팹·데이터 에셋 변경, 몬스터 수치 적용, 지도 UI 제작, 외부 연락·게시·커밋·푸시는 포함하지 않는다. 구체적인 거리·시간·몬스터 수는 측정 후 정할 가안이며 이 문서로 확정하지 않는다. 내해·중해·외해 해금, 자원 종류·총량·섬 수의 변경도 이번 요청에서 자동 승인된 것으로 보지 않는다.

## 2. 역순 검토 결과

완료 결과에서 입력으로 거슬러 올라가 의존성과 실패 조건을 확인했다. 발견 사항을 아래 구조와 단계에 반영했으므로 설계 문서 작성의 차단 조건은 없다. 구현·재미·성능이 검증됐다는 뜻은 아니다.

| 역순 | 확인한 문제와 근거 | 보완·통과 조건 |
|---|---|---|
| 지도 인계 | MapStateNet에 Layout, Config, Info, ContentHash, IsLayoutReady, LayoutReady, LayoutReleased가 이미 있다. 새 준비 이벤트를 중복 설계할 필요가 없다. | 기존 경로를 재사용하고 UI 늦은 구독·해제·다음 판 교체를 처리한다. 공개 기본 지형과 개인별 환영 섬 표시를 분리한다. |
| 통합 검증 | 시드가 같아도 설정·프리팹 차이로 결과가 달라질 수 있다. 기존 기록에 Different seeds 검사 실패가 남아 있다. | 동일 시드 일치와 서로 다른 시드 다양성을 따로 확인한다. 기존 실패와 신규 회귀를 분리한다. |
| 몬스터 증량 | SpawnerPlacementStep은 후보가 MinCount보다 적으면 예외를 낸다. 맵을 줄이면 섬·암초·안전 반경 제외 후 공간이 부족할 수 있다. | 섬 배치 성공뿐 아니라 스포너 생성까지 검사한다. 스포너 수와 활성 몬스터 수·재생성 주기를 구분한다. |
| 해역 축소 | ZoneConfig 반경만 줄이면 섬 마진·해역 폭·암초·폭풍벽·안전지대가 상대적으로 커진다. | 실제 항행 가능 영역, 해금별 경로, 안전지대 밖 생성 공간을 함께 검사한다. |
| 섬 간격 | MapGenerationConfig는 자원섬 최대 반경으로 공통 간격을 계산한다. IslandSlotStep 이후 IslandAssignmentStep이 실행된다. | 먼저 실측 반경·공통 여유를 바로잡는다. 부족할 때만 섬 종류를 먼저 정하는 배치 방식으로 확장한다. |
| 이동 시간 | 중심 거리만 줄여도 반대쪽 부두·출항·선회·파도로 실제 이동은 길 수 있다. | 부두 간 실제 항로와 출항·접안 시간을 측정한다. 인접 섬 연결뿐 아니라 등대 왕복과 먼 섬 고립도 검사한다. |
| 실측 | 기존 P0 표는 Terrain 크기이며 최신 Final 외곽·부두·회전의 점유 경계를 대체하지 못한다. | 최종 사용 프리팹, 배율, 변형과 자식 오브젝트를 확인해 경계를 다시 측정한다. |

관련 설계 대장: W14 접근성·필수 공급 보장은 계약 확인 필요, W17 일반 몬스터 안전지대는 부분 결정 및 실제 플레이 검증 잔여, W18 위협 중첩은 검증 가설이다. R18 개인 지도 비교를 통한 환영 섬 판별은 가설 검증 대상이다. 이 문서로 해당 항목을 해결 처리하지 않는다. 기존 v4의 외해 장거리 귀항 방향은 이번 사용자의 거리 축소 지시를 우선하며, 위험도 차이는 유지할 몬스터·기존 환경 조건으로 검증한다.

## 3. 목표 구조와 배치 정책

Final 프리팹 실측 → 경계 데이터 → 항해 시간 기준 → 섬·암초 배치 및 항로 검사 → 해역 경계 확정 → 확정 MapLayout → 몬스터 배치와 지도 제공으로 연결한다.

### 경계의 구분

- 배치 경계: 육지·충돌 장애물·부두 등 항행을 막거나 접안 공간을 점유하는 XZ 범위. 장식 나뭇잎·이펙트 Renderer 전체를 무조건 포함하지 않는다. 포함·제외 근거를 기록한다.
- 보행·해안 경계: 기존 걷기 마스크·난파물 해안 탐색이 사용하는 경계. 배치 반경 변경으로 무조건 대체하지 않는다.
- 지도 윤곽: 실제 섬 모양을 표현할 로컬 XZ 윤곽 또는 지도용 이미지 메타데이터. 충돌 방지 원을 섬 그림으로 대체하지 않는다.

루트 기준 중심 오프셋, 실제 배율, 모든 사용 Variant를 측정한다. 원형 보수 경계는 회전에 안전하도록 정하고, 부두 진입점·방향은 섬 yaw로 함께 변환한다. 기존 Radius가 해안 검색·안전 판정 등에 소비되는 경로를 조사한 뒤 보정하며, 의미가 다르면 별도 필드가 필요한지 판단한다.

### 배치 방식의 단계적 선택

1. 기존 슬롯 우선 구조를 유지하고 실측 반경, SailingChannelWidth, ExtraIslandSpacing, ShipClearance, RouteCellSize를 함께 검토한다. 코드 선언 기본값과 실제 에셋값을 구분한다.
2. 이 방식으로 목표 시간·해역 크기·섬 수를 함께 만족하면 구조 변경을 하지 않는다.
3. 큰 섬 때문에 공통 간격이 계속 과대해지는 경우에만 종류·Variant 선택 후 크기별 배치로 전환한다. 쌍별 최소 중심 거리는 rA + rB + 필요한 바다 간격을 기본으로 한다. 등대섬 반경도 명시적으로 포함한다.
4. 전환 시 QuotaAssigner·FillAssigner의 종류별 최소/최대·해역 제한·필수 공급 조건을 보존하고, 결정적 난수 순서·해시·재시도 경로를 함께 검증한다. 샘플러 교체나 정밀 다각형 배치는 기본 범위가 아닌 조건부 확장이다.

최소 간격만으로 긴 항해나 고립을 막을 수 없으므로, 부두 간 도달 가능한 항로 그래프를 검사한다. 각 해금 단계에서 등대부터 필요한 섬에 도달하고 귀환할 수 있어야 한다. 모든 섬 쌍을 동일 거리로 강제하지 않으며, 인접 항로와 등대 왕복의 긴 꼬리를 확인한다.

## 5. 항해·몬스터 조정 방법

출항→부두 이탈, 순수 항해, 접안 시간을 나눠 측정한다. 직선 거리뿐 아니라 암초 우회·부두 방향·파도에 따른 실제 경로 길이와 시간을 기록한다. 몬스터를 배제한 거리 조정 시험 후 정상 몬스터를 적용해 위험 증가분을 비교한다. 최종 목표 초·미터는 측정 전 확정하지 않는다.

몬스터는 배치점 수, 점별 활성 수, 전역/해역 상한, 재생성 시간, 패트롤·탐지 범위를 확인한다. World는 배치 위치·해역·프로필, Monsters는 실제 생성·수명·AI를 담당한다. 맵 축소로 밀도가 높아지는 것만으로 요청의 실제 수 증가를 충족했다고 보고하지 않는다.

분당 조우, 동시 추적 수, 실제 활성 수, 난파 빈도, 귀항 성공, 4인 집중 시 성능을 비교한다. 보스·소환 몬스터까지 일괄 증량하지 않는다. 안전 반경을 줄이거나 섬 수·자원량을 줄여 스포너를 억지로 넣지 않는다. 배치 공간 부족은 설정 부적합으로 보고하고 후보를 되돌린다.

## 6. 지도·미니맵 데이터 계약안

기존 MapStateNet과 MapLayout을 읽는 얇은 제공 계층을 우선 검토한다. 아래는 요구 필드이며 새 타입·메서드 이름의 확정안이 아니다.

| 항목 | 제공 내용·주의 |
|---|---|
| 판 식별 | MapSeedInfo, 레이아웃/콘텐츠 해시와 판 수명. 생성 버전은 기존 정보로 충분한지 확인 후 필요할 때만 추가 |
| 준비·해제 | IsLayoutReady와 LayoutReady/LayoutReleased 재사용. 늦게 구독하면 현재 상태를 읽고, 해제 때 이전 판 UI·참조 제거. 레이아웃 준비와 시각 에셋 생성 완료의 차이를 명시 |
| 좌표 | 월드 XZ 평면, 원점, 지도 bounds, 북쪽·UI Y 반전 규칙. 정규화는 (위치 - bounds.min) / bounds.size이며 0 크기·범위 밖 처리 명시 |
| 섬 | Index는 같은 판 안의 ID, ArchetypeId·VariantIndex·Zone·Position·Radius·YawDegrees. Index를 다음 판까지 영구 ID로 쓰지 않음 |
| 지도 외형 | Archetype/Variant별 로컬 윤곽 또는 이미지·기준 크기·중심 오프셋. 월드 좌표로 회전·이동하는 규칙 |
| 부두·암초 | 필요 표시 범위를 UI 담당자와 확인. 부두 로컬 위치·방향, 암초 실제 범위와 회전 규칙 |
| 해역·상태 | 생성 설정에서 확정된 해역 경계와 실제 해금 상태 소비 경로. UI에서 날짜 규칙을 별도 복제하지 않음 |
| 정보 범위 | 공개 지형과 개인별 환영 섬·탐색 상태를 분리. 항해사 예외를 전체 공용 데이터에 섞지 않음. 비공개 역할·스폰 출처 정보는 제공하지 않음 |

시드만 전달하고 UI에서 독립 생성기를 새로 만드는 방식은 피한다. 기존 동일 시드 생성 결과와 설정·콘텐츠 일치를 재사용한다. 정확한 해안 윤곽 전달 비용이 크면 우선 섬 아이콘과 크기·회전·오프셋으로 연결하고, 정밀 윤곽은 지도 요구에 따라 결정한다. 지도 UI 프레임마다 프리팹·씬 전체를 탐색하지 않도록 판 시작 시 정적 데이터를 구성한다.

인계 묶음: 필드·소유권 표, 좌표 변환 예제, 생성/해제 구독 예제, 기준 시드와 기대 배치, 지도 경계, 개인별 표시 규칙, 알려진 한계, 실제 검증 결과. 파일 작성과 담당자에게 실제 전달한 상태는 구분한다.

## 8. 검증과 완료 기준

자동·에디터 검사 계획: 변경 전후 동일 시드 묶음 최소 200개 비교를 초기 가안으로 삼는다. 생성 실패율·재시도·섬 수·필수 자원량·경계 이탈·섬/암초 겹침·부두 접근·해금별 연결성·스포너 최소 수 충족·시간 분포를 기록한다. 표본 통과를 모든 시드 보장으로 표현하지 않는다. 추가 검사는 새 실패·변경에 맞춰 수행한다.

플레이 검사 계획: 대표 파도와 해금 단계별 등대↔자원섬·자원섬↔자원섬 항해, 4인 동시 출항·귀항, 몬스터 중첩, 난파·구조·해안 드롭, 해안 걷기 경계·접안 회귀를 확인한다. 호스트·원격의 레이아웃/콘텐츠와 지도 위치·yaw·해역 경계가 일치해야 한다. 성능은 변경 전후 같은 조건으로 비교한다.

범위 완료 조건: 최신 섬 실측표, 실제 항해에 근거한 축소 설정, 겹침 없는 항로와 공급 유지, 실제 몬스터 증량 결과, 최명기에게 제공할 데이터·예제·한계, 실행한 검증과 미검증 목록이 모두 남아야 한다. 별도 PC 검증 불가·수신자 미확인·UI 미연결은 숨기지 않고 별도 잔여로 보고한다.

## 11. 단계별 세션 실행·재개 규칙

각 단계는 별도 세션에서 진행할 수 있다. 새 채팅 생성은 사용자가 직접 요청하거나 시작하며, 이 문서는 채팅을 자동 생성하지 않는다. 기본 실행 단위는 한 세션에 한 단계다. 단계가 끝나면 결과와 다음 시작 문구를 남기고, 다음 단계의 구현을 자동으로 이어가지 않는다. 단계 중단 시 미완료 상태 그대로 인계한다.

### 공통 시작 절차

1. AGENTS.md → docs/WORK_POINTER.md → 해당 담당자 POINTER.md → 이 설계의 해당 단계 → 직전 단계 결과·인수인계 순으로 읽는다.
2. 실제 브랜치·HEAD·git status·staged/unstaged diff와 관련 에셋 참조를 다시 확인한다. 최초 기준 47e36bf9를 계속 현재 상태로 가정하지 않는다.
3. 직전 단계의 완료 조건과 검증 증거를 확인한다. 미완료 의존성이 있으면 해당 부분부터 재개하고, 무관한 과거 작업은 실행하지 않는다.

## 12. 커밋·PR 안내 시점

단계를 끝내거나 공유 가능한 변경 단위가 완성되면 해당 세션은 아래 기준으로 사용자에게 안내한다. 이 요청은 안내 절차를 설정하는 것이며 커밋·push·PR 게시·병합의 실행 승인이 아니다. 이미 명시적으로 승인된 실행은 반복 확인하지 않는다. 실제 실행 시 guided-commit 또는 guided-pull-request 스킬과 최신 컨벤션·실제 PR 템플릿을 읽는다.

### 커밋 안내

| 시점 | 권장 단위·조건 |
|---|---|
| 현재 설계 정리 완료 | 설계 문서와 pointer 변경 중 이번 요청 부분을 검토한 뒤 docs 커밋 안내. 기존 pointer의 타 작업 변경을 함께 stage하지 않음 |
| S0~S2 결과 확보 | 재현 가능한 기준표·실측·측정/계약 초안의 의미 있는 단위로 docs 커밋 안내. 세션 수에 맞춰 억지 분할하지 않음 |
| S3 완료 | 간격 변경과 필요한 검사·기준 문서·단계 기록을 한 목적의 단위로 안내. 구조 변경과 수치만 변경한 경우 타입을 구분 |
| S4 완료 | 축소 설정·관련 회귀 검증·문서가 함께 검토 가능할 때 안내. S3과 분리하면 유효하지 않은 조합이면 함께 묶되 이유 기록 |
| S5 완료 | 몬스터 증량 설정/실행 변경과 실제 검증·문서를 묶음. World와 Monsters 담당 브랜치가 다르면 담당별 커밋과 연동 기준을 기록 |
| S6 완료 | World 제공 기능·예제·계약·인계 문서의 동일 목적 변경을 안내. 코드 없이 문서만 바뀌면 docs |
| S7 완료 | 새 수정이 있으면 그 목적에 맞춘 커밋, 결과 문서만 있으면 docs. 변경이 없으면 커밋 불필요 |

수치 조정은 chore, 새 기능은 feat, 결함 수정은 fix, 동작 불변 구조 개선은 refactor, 문서만은 docs를 기준으로 실제 diff에 맞게 선택한다. 메시지 원문 기준은 [커밋·PR 컨벤션](../commit-convention.md)이다. 씬별 분리·에셋과 .meta 동반·기능과 문서 동기화를 지킨다. SVN 대상 변경은 Git 커밋에 담겼다고 보고하지 않고 필요한 SVN 반영 시점을 함께 알린다.

각 안내는 '권장/아직 이른 이유/불필요' 중 하나, 대상 파일·제안 메시지, 검증과 잔여, 기존 변경 혼입 위험을 짧게 제시한다. 커밋 전에는 범위와 staged diff를 확인하고 git add .를 사용하지 않는다. 승인·생성 후 실제 해시를 기록하며 제안 메시지를 완료 커밋으로 기록하지 않는다.

### PR 안내

- S2: 지도 소비자가 일찍 계약을 확인해야 하면 문서 검토용 Draft PR을 선택적으로 안내한다. 합의된 계약으로 표현하지 않는다.
- S4: 월드 간격·해역 축소가 독립적으로 검토 가능해지는 첫 기본 PR 안내 시점이다. S3~S4 변경과 근거를 함께 제시한다. 아직 증량 전이면 해당 상태와 후속 S5를 명시한다.
- S5: 몬스터 변경이 별도 담당 브랜치이면 별도 PR을 안내하고 선행 월드 커밋/PR 의존성을 기록한다. 동일 head/base PR이 있으면 새 PR보다 기존 PR 갱신을 우선한다.
- S6: 지도 제공 계약·World 연결을 소비자에게 공유할 PR을 안내한다. 기존 PR 범위와 자연스럽게 같으면 갱신하고, 독립 변경이면 분리한다.
- S7: 필수 검증과 남은 차단 조건을 확인한 뒤 Draft 해제·최종 리뷰 요청 적기를 안내한다. 미검증을 통과로 체크하거나 자동 병합하지 않는다.

기본 base는 develop, head는 실제 feature/<이름> 브랜치다. 게시 전 전체 base...head diff를 확인한다. feature/minseo에 이미 있던 무관한 커밋이 포함되면 이번 단계만의 PR이라고 소개하지 않고 분리 방법을 먼저 제안한다. 이 문서 작성만으로 브랜치 생성·변경·cherry-pick을 실행하지 않는다.

PR 안내에는 포함 범위·제목/본문 초안·담당 경계·실제 검증·미검증과 의존성, Git/SVN 공유 상태를 준비한다. push·게시 요청 이후에만 실제 원격 상태·중복 PR·권한을 확인해 실행한다. 각 단계 기록에 마지막 안내와 커밋 해시/PR URL 또는 '미실행'을 남겨 다음 세션이 중복 안내·중복 생성을 피하도록 한다.

## 1. 목표
아래를 **이 순서대로** 구현한다. 각 단계가 끝나면 컴파일·M0를 확인하고 원문 기록을 남긴다. 모든 항목은 사용자가 2026-10-27에 승인했다. 근거는 [UI연출-기획.md 끝 절](../../../김지훈/2026-10-26/UI연출-기획.md)과 이번 대화다.

### A. 모듈 제작 (작업대 화면 + 작업대 모델)
1. **본인 제작 성공**: 제작 결과(성공)를 받은 뒤 재료 줄 아이콘들이 진행 영역 가운데로 빨려 들어가고, 빛과 함께 모듈 아이콘이 나타난다. 버튼을 누른 순간에 시작하지 않는다. 동시에 눌러 진 쪽에는 연출이 나오면 안 된다.
2. **모듈 → 보관함 칸**: 이어서 완성된 모듈 아이콘이 보관함 칸(`_storedSlots`)으로 날아가 들어가고, 그 칸의 개수 +1이 튀고, 가져가기 버튼(`_takeButton`)이 한 번 빛난다.
3. **다른 선원이 제작**: 화면을 열고 있으면 재료 줄이 비워지면서 보관함 칸만 +1 펄스를 받는다. 이름은 표시하지 않는다.
4. **작업대 모델(월드)**: 불꽃·먼지 파티클과 망치 소리를 낸다. 소리는 3D로 거리에 따라 작아지고, 작업대 근처 사람만 보고 듣는다. 신호는 모든 PC가 받는 `WorkbenchNet.RecipeCompleted`(`RpcRecipeCompleted`)다.
5. **알림 띠 C 생략**: 작업대 화면이 열려 있는 PC에서는 [TowerMatchEffects.cs:221](../../../../Assets/01.Scripts/04.Lighthouse/Tower/View/TowerMatchEffects.cs#L221)의 "○○ 모듈 완성" 띠를 띄우지 않는다. 나머지 PC에는 지금처럼 띄운다. 제작자 본인뿐 아니라 화면을 연 사람 모두가 생략 대상이다(사용자가 승인한 정의).

### B. 가져가기 / 되돌려놓기 (본인 화면만)
6. **가져가기 성공**: 보관함 칸의 모듈이 운반 줄(`_carryBar`·`_carryIcon`)로 날아가 손에 들린 표시가 된다. 화면을 닫으면 들고 있는 부품 표시 D(`CarriedModuleIndicator`)가 화면 구석에서 미끄러져 들어온다.
7. **되돌려놓기 성공**: 반대로 운반 줄의 모듈이 보관함 칸으로 날아간다. D는 미끄러져 나간다.
8. 들고 있다는 정보는 본인 PC에만 온다(`TargetCarriedChanged` → `OwnCarriedRecipe`). 이 연출은 **본인 화면에서만** 재생하고, 다른 PC에 새 정보를 보내지 않는다. 다른 PC는 보관함 개수 감소만 보며, 여기에는 연출을 넣지 않는다.

### C. 모듈 장착 (등대 장착 화면 + 등대 칸 모델)
9. **장착 화면**(`TowerScreen`): 장착 성공 결과를 받으면 들고 있던 모듈 아이콘이 대상 칸으로 날아가 '철컥' 끼워지고 칸 테두리가 빛난다. D는 사라지는 연출과 함께 없어진다.
10. **층 줄 스윕**: 이번 장착으로 그 층이 다 차면(`TowerNet.IsFloorComplete`) 층 줄 전체에 빛이 훑고 지나가고 "N층 수리 완료"가 찍힌다.
11. **수리 카운트**: "3/8 → 4/8"로 올라가며 숫자가 튄다(`SlotInstalled`).
12. **등대 모델**(`TowerView`): 칸 모델이 즉시 켜지는 대신 위에서 내려앉는다.
13. ~~층 창문 불·등대 불빛 단계~~ — **하지 않는다.** 10-26 결정([UI연출-기획.md 10행](../../../김지훈/2026-10-26/UI연출-기획.md)): 등대는 마지막에 한 번 켜지고 탈출하는 이야기라 층마다 불이 켜지면 어긋나고, 창문 모델도 없다(v4 "불빛은 마지막에 켜지고 게임이 끝난다"). 2026-10-27 제안에 잘못 들어갔다가 사용자 지적으로 삭제.
14. 기존 전체 연출 ①(게이지·"+12.5%"·띠)은 유지한다.

### D. 마지막에 한 번에: 마피아 인출 (사용자 결정 2026-10-27)
15. **인출 표시**: 작업대 화면을 보고 있을 때 재료 투입량이 **제작이 아닌 이유로** 줄면(=마피아 인출), 그 재료 줄을 **빨갛게 깜빡인다**. 누가 뺐는지는 표시하지 않는다. 지금까지 보류했던 E(인출 공개, R19)의 화면 범위 결정이다.
16. **인출 버튼을 작업대 화면에 둔다.** 지금은 개발용 `TowerTrialPanel`에서만 인출할 수 있다. 서버 판정은 이미 있다(`ModuleInteractionHandler.HandleWithdraw`의 마피아 확인, `WorkbenchNet.Withdraw`).

### 구현 메모 (2026-10-27 기준, 줄 번호는 바뀌었을 수 있음)
**재사용할 것.** 투입 연출 세션에서 만든 `WorkbenchScreenEffects`(internal, 트윈 실행기)가 있다. `PlayFlight(icon, from, to, landCount)`, `PlayPunch`, `PlayFlash`, `PlayShake`, `PlayGain`, `SetReadyGlow`, `Tick`, `StopAll`를 제공하고, 풀은 고정 배열이라 매 프레임 할당이 없다. 효과음 훅은 `WorkbenchScreen.EffectCued`(`WorkbenchEffectCue`)이며 구독자는 없다. "빨려 들어감"(여러 아이콘이 한 점으로 모임)과 "빛 터짐", "미끄러져 들어옴/나감"은 아직 없으므로 이 클래스에 추가한다. 등대 장착 화면도 같은 클래스를 쓰려면 이름을 일반화하거나 `TowerScreen`용 실행기를 따로 둔다. 다음 세션이 판단한다.

**본인 결과와 동기화 순서.** 투입 세션에서 확인한 사실: 결과(`TargetRpc`)는 즉시 가고 `SyncList`·`SyncDictionary` 변경은 다음 동기화 때 간다. 그래서 원격 클라이언트는 결과를 먼저 받고, 호스트는 순서가 반대일 수 있다. 제작도 "결과 성공"과 "투입량 0·보관 개수 +1"·`RpcRecipeCompleted`의 도착 순서를 가정하지 말고, 투입 때처럼 **본인 제작 레시피 ID를 기억해 두고** `RecipeCompleted`(같은 ID)를 받으면 그것을 본인 몫으로 소비하는 방식을 권한다. 남는 완성 신호는 다른 선원의 제작(3번)이다. 확인은 M2에서 한다.

**작업대 화면 코드 위치.**
- 요청 흐름: `HandleCraftClicked`, `HandleTakeClicked`, `HandleReturnClicked` → `Send`(`_pendingAction`) → `HandleResultReceived`.
- 보관함 칸: `RefreshSketchStock`(페이지가 있어 해당 레시피 칸이 화면에 없을 수 있음 → 그때는 착지점을 페이지 버튼이나 가져가기 버튼으로 대체).
- 운반 줄: `RefreshCarry`. `IsOpen` 공개 속성이 이미 있다(`WorkbenchScreen.IsOpen`).
- 줄어듦은 지금 "즉시 반영, 연출 없음"이다. D-15에서 제작과 인출을 구분해 바꾼다. 구분 방법: 같은 갱신에서 그 레시피의 보관 개수가 늘었거나 `RecipeCompleted`를 받았으면 제작, 아니면 인출이다. 순서 문제가 있으므로 짧은 유예(예: 투입 세션의 `OwnDepositSeconds`와 같은 방식)를 두고 M2에서 확인한다.

**알림 띠 C 생략(5번).** `TowerMatchEffects`(Tower/View)가 `WorkbenchScreen`(Workbench/View)의 `IsOpen`을 알아야 한다. 둘은 같은 `Lighthouse.Runtime` 어셈블리다. 직렬화 참조를 추가하면 `TowerMatchEffectsSetup` 빌더에서 연결하고 다시 빌드·씬 적용한다(YAML 직접 편집 금지).

**작업대 모델(4번).** 파티클·`AudioSource`(spatialBlend 1, 거리 감쇠)를 작업대 오브젝트 아래에 두는 새 View 컴포넌트로 만든다. 작업대 나무 모델은 `WorkbenchModelSetup`이 JH04 인스턴스에 넣었다. **공용 `Workbench.prefab`까지 바꿀지는 미결정**(POINTER 10-23 행)이다. 이번에도 설정 메뉴로 JH04에 붙이고, `MainGame` 반영은 사용자에게 확인한다. 망치 소리 에셋은 정해지지 않았다. `Assets/`와 SVN 체크아웃에서 쓸 만한 효과음을 먼저 찾아보고, 없으면 클립 필드만 비워 두고 보고한다.

**운반 D(6·7번).** [CarriedModuleIndicator.cs](../../../../Assets/01.Scripts/04.Lighthouse/Workbench/View/CarriedModuleIndicator.cs)는 `OwnCarriedRecipe`가 바뀔 때 `_root.SetActive`만 한다. 미끄러짐을 넣되 작업대 화면이 열려 있는 동안에는 숨겨져 있는지(겹침 여부)를 먼저 플레이로 확인한다.

**등대 장착 화면(9~11번).** `TowerScreen`: `Refresh`, `HandleInstallClicked`, `HandleResultReceived`, `HandleChanged`. 칸은 `TowerSlotView`(`Show(icon, state)`). 10-27 새 아트(층별 배경 단계)는 커밋 `9d33b77`로 되돌려 기존 스케치 화면이다. 배경 단계 교체는 없다. 기존 문제로, 왼쪽 슬롯이 대상일 때 '여기' 표시가 가려진다.

**등대 모델(12번).** [TowerView.cs](../../../../Assets/01.Scripts/04.Lighthouse/Tower/View/TowerView.cs)는 `_slotVisuals[i].SetActive`와 `_completeVisual`만 한다. JH04·`MainGame`·`TWJH04TestScene`에 배치돼 있고 `_slotVisuals`가 연결돼 있다. `_completeVisual`(모든 칸이 찼을 때)은 기존 그대로 두고 이번에 손대지 않는다. 첫 상태 수신(중간 접속)에는 콜백이 없으므로 내려앉기 연출은 `SlotInstalled`에서만 재생하고, `Refresh`는 즉시 상태를 맞춘다.

**인출(D-16).** 2026-10-20 기록에 "작업대 프리팹에 `Withdraw` 지원 행동이 없어 서버가 인출을 거절, 설정 메뉴가 JH04 인스턴스에만 추가"라고 되어 있다. 2026-10-27 파일 확인 결과: `JH04TestScene`·`MainGame` 모두 작업대 인스턴스(`Workbench.prefab`) 덮어쓰기로 `_supportedActions` 6개(…, `Withdraw`=3, `TakeModule`=16, `ReturnModule`=17)를 갖고 있어 서버가 인출을 받는다. 원본 `Workbench.prefab`에는 없으므로 새 씬에 작업대를 놓으면 다시 추가해야 한다. 클라이언트가 자기 역할(마피아 여부)을 알 수 있는 공개 API가 있는지 확인하고, 있으면 마피아에게만 버튼을 보인다. 없으면 버튼 노출 범위를 사용자에게 묻는다(시민에게 보이면 역할 추리 단서가 되지는 않지만 혼란을 줄 수 있음). 서버가 단계(수리 중)를 검사하지 않음, 인출 기록 없음, 한도 미정(W08)은 그대로 남는다. 결정 문서·[설계 문제 대장](../../../07-design-issue-register.md) R19·W08 항목에 이번 결정(화면에서 빨간 깜빡임, 화면 버튼)을 반영한다.

- 되돌리면 안 되는 변경: 투입 연출(`598235c`), A·B 제작·운반 연출 코드(미커밋, [원문](../../../김지훈/2026-10-27/작업대-제작운반연출.md))
- 다른 사람이 병행 작업 중인 파일: 없음. 인벤토리 화면(최명기)과 역할·투표 코드(박태욱)는 건드리지 않는다. 역할 정보를 읽기만 해야 하면 기존 공개 API를 쓰고, 없으면 박태욱에게 요청한다.

- 비공개 정보: 제작자·투입자·인출자·보유자 이름은 어떤 화면에도 표시하지 않는다.

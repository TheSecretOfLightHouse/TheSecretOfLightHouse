## 결정 내용

2026-10-13 김지훈이 JH02(상호작용 요청)의 대상 탐지·식별 방식을 정했다. 상세는 [네트워크 권위 §2.2](../../../unity/NETWORK_AUTHORITY.md#22-jh02-상호작용-요청-경로)와 [지훈 시스템 설계 §5.1](../../../design/jihun-system-design.md#51-식별과-전송)에 있다.

- 플레이어가 상호작용 키를 누르면 **각 플레이어 PC**의 Interaction 컴포넌트(김지훈)가 근처 대상을 고른다.
- 2026-10-14 갱신: 대상이 네트워크 객체이면 **Mirror netId**로 식별한다. 서버 대상 장부의 번호 발급·등록·SyncVar는 없앴다. 대상 프리팹에는 김지훈의 표식 컴포넌트(상호작용 가능·기본 동작 표시, 등록 없음)만 붙인다.
- 대상이 네트워크 객체가 아니면(각 PC에서 만드는 채집 지점 등), 플레이어 PC가 **(대상 종류, 기존 ID)**를 보내고 서버 변환기가 강민서 조회 계약(`IHarvestSpotQuery.TryGetSpot` 등)으로 확인한다. 강민서의 `SpotInfo`·`IslandHandle` 타입은 바꾸지 않고 김지훈이 adapter를 만든다.

## 자원 ID와 SpotId 구분 (2026-10-14 보충)

"자원 ID만 알면 되지 않나"라는 질문에 대한 답이다.

| 작업 | 필요한 것 | SpotId 생성 방식(`HarvestSpotIds.Compose`) |
|---|---|---|
| JH03 작업대·레시피·투입 | `ResourceId`와 수량만 | 몰라도 됨 |
| JH02 채집 요청 | **어느 지점인지 가리키는 SpotId** | 몰라도 됨 |

- 채집은 지점 단위로 처리된다. 강민서 계약 `IHarvestSpotRegistry.TryConsume(spotId, …)`가 지점별 잔량을 줄이고, `TryGetSpot(spotId, …)`의 위치로 거리를 검증한다. 같은 자원의 지점이 여러 개면 `ResourceId`만으로는 구별할 수 없다.
- 김지훈에게 필요한 것은 생성 로직이 아니라 아래 두 가지다. 확인 항목 2·3과 같다.
  1. 플레이어 PC가 근처 지점의 SpotId를 읽을 방법. 제안: 채집 지점 오브젝트에 SpotId를 담은 컴포넌트와 콜라이더를 붙이면 Interaction 컴포넌트가 이를 탐지해 읽는다. 이 경우 위치로 찾는 조회 인터페이스는 필요 없다.
  2. 같은 판의 4개 PC에서 같은 지점이 같은 SpotId를 갖는 것(MS01 완료 기준과 같음).

## 강민서 범위에서 확인할 것

| # | 확인할 것 | 이유 |
|---|---|---|
| 1 | 채집 지점은 네트워크 객체(서버 Spawn)인가, 같은 시드로 각 PC에서 생성하는 일반 오브젝트인가 | 일반 오브젝트이면 위의 (종류, SpotId) 방식을 쓴다. 네트워크 객체이면 netId 방식을 쓰고 2·3은 필요 없다 |
| 2 | 플레이어 PC에서 "근처 채집 지점의 위치와 SpotId"를 얻을 방법 | 탐지는 플레이어 PC에서 한다. 지금 `IHarvestSpotQuery`는 `SpotId`로 한 지점을 조회하는 기능만 있고, 위치로 근처 지점을 찾는 기능은 없다 |
| 3 | 같은 판의 4개 PC에서 같은 지점이 같은 `SpotId`를 갖는지 | 1이 일반 오브젝트이면 필수다. MS01 완료 기준(같은 판의 위치·ID가 4인 동일)과 같은 조건이다 |
| 4 | 특수 섬(`IslandHandle`), 유령선(MS06), 표류 잔해(MS02)가 각각 네트워크 객체인지 | 대상마다 위의 두 방식 중 어느 쪽을 쓸지 정한다 |

## 강민서가 할 일 (확인 후)

- 2의 조회 방법을 제공한다. 형태(인터페이스·컴포넌트)는 강민서가 정하고 김지훈에게 알려 준다.
- 네트워크 객체 대상(유령선·표류 잔해 등)의 프리팹에는 김지훈의 표식 컴포넌트 `InteractionTarget`(`03.Interaction/Targets/Net/`, 2026-10-14 구현)을 붙이고 허용 동작·범위를 정한다. 등록 동작은 없다.
- 채집 지점이 각 PC에서 만드는 일반 오브젝트이면, 서버 확인용으로 `INonNetworkTargetAdapter`(`03.Interaction/Targets/Server/`)를 구현해 `TargetResolver.RegisterAdapter(InteractionTargetKind.HarvestSpot, …)`로 등록하는 방식을 제안한다. 형태는 확인 항목 1·2의 답을 받은 뒤 함께 정한다.
- 게임 씬에서 각 PC의 월드 생성이 끝났다는 신호를 제공한다. 김지훈이 4명 모두의 완료를 확인한 뒤 판을 시작한다(2026-10-13 로비 시작 결정, [승패·투표 결정 §8](../../../design/win-vote-decisions.md#disconnection)).
- 채집 판정(잔량 차감·지급)은 지금처럼 강민서·최명기 기능이 맡는다. 김지훈 Validator는 경제·횟수 규칙을 대신 판정하지 않는다.

## 강민서 답변 (2026-10-16)

### 1. 채집 지점의 생성 방식: 각 PC 생성

- 채집 지점(`HarvestSpot`)은 섬 프리팹의 자식에 붙는 일반 컴포넌트이고 네트워크 객체가 아니다. 같은 맵 시드로 각 PC가 섬을 만들고, `HarvestSpotBinder`가 프리팹의 `HarvestSpot` 계층 순서로 `SpotId`(`HarvestSpotIds.Compose(섬 인덱스, 지점 번호)`)와 자원 ID를 붙인다.
- 지점별 남은 양만 네트워크 객체 `IslandStateNet`(`SyncList<NodeState>`)이 동기화한다. 2026-10-16 호스트와 가상 플레이어 2개에서 채집 차감, 하루 회복, 늦은 접속 복원을 실행 검증했다. 검증 대상은 테스트 섬 하나이고, 근거리 관심 범위는 적용하지 않았다.
- 서버 변환기는 구현되어 있다. `HarvestHost`가 `HarvestTargetAdapter`(`INonNetworkTargetAdapter`)를 `TargetResolver.RegisterAdapter(InteractionTargetKind.HarvestSpot, …)`로 등록하고, 서버 범위 기본값은 3이다(`HarvestHost`의 `_serverRange`).
- 아직 없는 것: 맵 전체의 섬 프리팹을 생성하는 `IslandFactory`(T14·T16 후속)와 클라이언트 쪽 `ClientHarvestSpotQuery`·`WorldRegistry`(T18).

### 2. 근처 지점 조회 방법: 월드 쪽 목록은 제공, 클라이언트 선택 연결은 미해결

- 월드 쪽이 제공하는 것: `HarvestSpot.Active`(이 PC의 활성 지점 읽기 전용 목록)와 각 지점의 `SpotId`·`Position`·`IsBound`다. 요청 문서의 제안대로 위치로 찾는 조회 인터페이스는 추가하지 않는다.
- 문제: `InteractionSelector`는 `InteractionTarget.Active`만 후보로 삼는데, `InteractionTarget`은 `NetworkIdentity`가 필수라서 네트워크 객체가 아닌 채집 지점은 클라이언트가 고를 수 없다. 서버 쪽(변환기)은 준비되어 있고 클라이언트 선택에서 끊긴다.
- 제안: 선택기가 `HarvestSpot.Active`에서 `IsBound`인 지점도 후보로 읽고, 선택되면 `TrySendToNonNetworkTarget(InteractionTargetKind.HarvestSpot, SpotId, InteractionAction.Harvest)`로 보낸다. `HarvestSpot`은 `Rules`(Mirror를 모름)라서 `03.Interaction`이 참조해도 방향이 맞다. 선택 범위와 표시는 상호작용 담당이 정한다. 상호작용 담당 코드라서 월드 담당은 수정하지 않는다.

### 3. 4개 PC의 SpotId 일치: 설계상 보장, 4개 PC 실행 검증 전

- 같은 시드로 같은 섬 배치와 같은 지점 순서가 나오므로 `SpotId`도 같다. 섬 배치는 맵 시드와 해시 비교로 일치를 확인한다(N3, 호스트와 가상 플레이어 2개에서 실행 검증).
- 남은 가정: 클라이언트의 지점 순서(`GetComponentsInChildren`)가 서버와 같다는 것이다. T18에서 `IslandStateNet`의 목록 길이와 로컬 `HarvestSpot` 수를 비교해 다르면 오류를 내도록 할 예정이다. 실제 4개 PC 검증은 4인 테스트에서 한다.

### 4. 특수 섬·유령선·표류 잔해의 네트워크 객체 여부

| 대상 | 방식 | 상태 |
|---|---|---|
| 유령선 | 네트워크 객체(`GhostShipNet`, 서버 Spawn). 프리팹에 `InteractionTarget`을 붙이는 netId 방식 | 설계만, 구현 전 |
| 표류 잔해 | 네트워크 객체(`PickupNet`, 서버 Spawn). netId 방식 | 설계만, 구현 전 |
| 특수 섬(레이더·관측소·예측소) | 섬 프리팹은 각 PC 생성이고 상태는 `IslandStateNet`(네트워크 객체)이 갖는다. `IslandStateNet`에 `InteractionTarget`을 붙이는 netId 방식이 가능하나 확정하지 않았다 | 미정 |

### 월드 생성 완료 신호와 시계 시작

구현되어 `develop`에 들어 있다. 상호작용 담당 쪽 연결(시작 조건, 게임 씬 배치)이 남아 있고 자세한 내용은 [판 시작 신호와 월드 시계 연결 요청](판시작-월드시계-강민서-연결요청.md)에 정리한다.

## 갱신 이력

- 2026-10-15: 강민서가 1~3번에 답했다(사용자가 전달).
  - SpotId는 판마다 정해지는 값이며, 서버와 클라이언트가 같은 규칙(섬 번호 + 섬 안 지점 순서)으로 계산한다.
  - 서버는 `HarvestSpotRegistry`로 번호를 붙이고 매장량을 관리한다.
  - 원격 PC는 `HarvestIslandSetup.TryRegister`를 서버용 등록 객체 없이(registrar null) 불러 번호만 붙이고 매장량은 만들지 않는다. 원격 PC의 `HarvestHost`는 스스로 꺼지므로 클라이언트에는 잔량이 없다. 선택에는 위치·번호만 필요하므로 문제없다.
  - 4개 PC에서 실제로 같은 번호가 붙는지는 미검증이다.
  - 남은 것: 4번(특수 섬·유령선·표류 잔해), 월드 생성 완료 신호([판 시작 연결 요청](판시작-월드시계-강민서-연결요청.md)). 실제 맵에서 원격 PC가 `TryRegister`를 부르는 코드는 2026-10-15 develop에서 아직 찾지 못했다(샌드박스만 있음).
- 2026-10-16: develop(`a6d505c`) 병합 시 강민서 답변을 표에 반영했다. 2번은 `HarvestSpot.Active` 제공·선택기 연결은 상호작용 담당, 3번은 설계상 보장(실행 검증 전), 4번은 유령선·표류 잔해 네트워크 객체(구현 전)·특수 섬 미정.

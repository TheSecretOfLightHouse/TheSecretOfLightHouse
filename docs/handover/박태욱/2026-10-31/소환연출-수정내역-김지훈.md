### 서버 단계·요청 계약
- 최후 전투 시작에서 준비된 연결을 참가자로 잡고 `Preparing → Playing → Returning → Combat`을 진행한다. `IsSummonCinematicPlaying`은 준비·재생·복귀 전체에서 true다.
- 준비/복귀 보고는 연출 순번·실제 송신 연결·identity·ready 상태를 확인하고 HashSet으로 중복을 제거한다.
- 모두 준비하거나 준비 제한이 끝나면 공통 재생 시작/종료 시각을 정한다. 재생 종료 후 복귀 보고/제한시간과 여유 시간을 거쳐 Combat에 들어간다.
- 개인 준비 실패는 그 사람 연출만 생략한다. 공통 Combat까지 입력/피해 보호는 유지한다.
- 현재 `CinematicLoadDeadline/Timeout` 이름은 실제 섬/Rig 연결 준비 기한을 뜻한다. Additive 씬 로드가 아니다.

- `ProjectSettings/EditorBuildSettings.asset`: 초기에 별도 SummonCinematic 씬을 추가했다가 메인 씬 전환 때 제외했다. 현재 구현이 옛 씬의 빌드 등록에 의존한다고 보면 안 된다.

## 3. 완료하지 못한 것
- 실제 원격에서 공통 시작/복귀·개인 준비 실패·지연 바인딩·중단 시 입력/UI 복원은 미검증이다. 지원 범위 안의 초기 상태 수신을 확인해야 하며 재접속 지원 범위는 기존 공용 접속 결정을 따른다.
- 실제 승인된 채집·제작·구조 작업의 완료/취소 전 구간을 다인 환경에서 확인하지 않았다.
- 당시 `FinalBattleHud.LateUpdate`의 netIdentity 준비 경계 NullReferenceException은 진단 후 사용자 지시로 보류했다. 현재 병합 후 재현 여부는 새로 실행하지 않았다.
- `7a85e40b`의 `TowerMatchEffects` 바인딩 수정은 후속 별도 작업이며 이 소환 연출 구현자의 변경으로 포함하지 않는다. 위 HUD 예외와 같은 오류라고 단정하지 않는다.

## 4. 현재 저장소 상태
- 변경 근거 커밋: `26422bc1` 보호/복구 시계, `58875d4d` 입력/요청·단계·초기 Additive, `3fe79744` 메인 씬 전환, `04a870e7` 등대 공격 바인딩, `f7b96c7b` 주변 촉수 바인딩.
- 일부 초기 커밋은 공통 타입과 소비자가 나뉘어 있으므로 한 커밋만 골라 떼어 적용하지 말고 의존성을 함께 확인한다.
- 조사 시작 시 작업 트리는 깨끗했다. 현재 HEAD에는 이후 VFX 교체·타격 효과와 develop 병합도 포함돼 있다. 이번 작업은 문서만 작성한다.
- 통합 씬/Main 씬을 새로 저장하거나 NetworkManager·패키지·asmdef를 변경하는 작업은 이번 정리에서 하지 않는다.

## 6. 차단 조건
- 통합 완료 판단에는 호스트+별도 원격 M2 이상의 실행이 필요하다. 현재 M1 근거만 있다.
- HUD 예외의 재현/수정 여부는 담당자가 현재 병합 상태에서 확인해야 한다. 사용자 보류 상태를 자동 해제하지 않는다.
- 기존 HP/수리도 승계 등 기획–코드 차이와 같은 프레임 승패 경합을 이번 연출 구현으로 새로 결정한 것은 아니다.

## 7. 다음 세션의 첫 행동
1. 본편 등대 설정이 12초 Rig와 서버 보스 두 컴포넌트를 참조하는지 확인한다.
2. 원격을 붙여 연출 전 승인 작업·연출 후 새 요청 거절·복귀 후 입력/UI/피해 복원을 검사한다.
3. 한 명의 준비 실패/복귀 지연에서도 다른 참가자의 공통 보호가 조기 해제되지 않는지 검사한다.
4. 전투 종료·서버 종료·객체 비활성화에서 owner 잠금이 남지 않는지 검사한다.

## 8. 주의
- 기존 카메라 위치·월드 시간·배 물리를 고정하는 방식으로 바꾸지 않는다.
- 서버 피해 보호와 로컬 입력 잠금은 서로 다른 계약이다. 클라이언트 잠금만으로 서버 요청 검증을 대신하지 않는다.
- 다른 기획/다른 담당자의 후속 변경까지 과거 파일 버전으로 통째로 되돌리지 않는다.

## 1. 목표

마피아 F 메뉴에서 다음 날 날씨를 예약하고, 환영섬 기능을 연결한다. **날씨는 이미 기존 World 서비스 호출까지 연결돼 있으므로 같은 요청 경로를 새로 만들 필요가 없다. 환영섬은 버튼과 기존 인터페이스 선언만 있으며 실행 연결을 추가해야 한다.**

확정한 사용자 요청:

| 메뉴 | 원하는 동작 | 현재 상태 |
|---|---|---|
| F → 몬스터 소환 | 탑뷰 위치 선택 → 기존 7종 선택 → 소환 | 기존 흐름 연결 유지 |
| F → 날씨 조정 → 안개 | 현재 날씨는 유지하고 다음 날 예약 | 사용자 승인으로 `WeatherType.Overcast` 호출 |
| F → 날씨 조정 → 폭풍우 | 현재 날씨는 유지하고 다음 날 예약 | `WeatherType.Storm` 호출 |
| F → 환영섬 생성 | 민서의 환영섬 기능으로 연결 | ‘민서의 기능 연결 준비 중’ 안내만 표시 |

- 3칸·2칸 메뉴는 기존 몬스터 그림 UI 스타일이다. 칸을 가리키면 중앙 원에 이름을 표시한다. 제목·중앙 이름·안내는 등대 수리도 HUD와 같은 OS 폰트/Bold다.
- F 진입은 기존 마피아 권한·배 승선 조건을 유지한다. 환영섬을 눌렀다고 몬스터용 탑뷰로 전환하지 않는다.
- 기준: [메뉴 확정 결정](../../../design/mafia-ability-menu-decisions.md) → [승패·투표 결정](../../../design/win-vote-decisions.md) → 미변경 범위의 [v4 §4.2·4.4·4.7·10.1](../../../design/references/game-design-v4.md).
- 전체 작업 과정·이미지·검증은 [최명기 작업 원문](../../../최명기/2026-10-30/마피아-능력메뉴와-다음날-날씨예약.md)을 참조한다.

### 날씨: 현재 연결된 정확한 API

```text
SeaSummonRadialMenu.SelectSlot
  → SeaSummonPermissionController.RequestNextDayWeather(bool isStorm)
  → CmdRequestNextDayWeather(bool isStorm, NetworkConnectionToClient sender)
  → WorldServices.TryGet<IGameClock> / TryGet<IForecastService>
  → forecast.Tamper(clock.DayIndex + 1, isStorm ? Storm : Overcast)
  → TargetWeatherResult(요청자, 성공 여부, 안내)
  → WeatherResponded 이벤트 → 메뉴 안내 갱신
```

| 값 | 의미 |
|---|---|
| `isStorm = false` | UI의 안개 → `Overcast` |
| `isStorm = true` | UI의 폭풍우 → `Storm` |
| `Tamper` 반환 `true` | 예약 데이터 변경 성공. 실제 다음 날 연출 성공까지 보장하는 값은 아님 |
| `WeatherResponded` | `Action<bool, string>`; 요청자 개인 UI 응답 |
| `IsWeatherPending` | 클라이언트 요청 대기. 5초 후 재요청 가능 |

서버는 송신자 접속/ActorId/마피아 역할/유효한 설정/실제 승선 상태를 기존 `CanRequest`로 확인한다. 추가로 판 종료 여부, 세션 흐름 사용 시 `InProgress`, 실제 `GameClock.IsRunning`, 유효 일차, 다음 날 존재 여부, 현재 `WeatherSystem.Target == Maelstrom` 여부를 확인한다. 마지막 날·시작 전/종료 후·심연 고정 상태는 거절한다. 미래 날씨와 예약 결과를 전체 클라이언트에 새로 방송하지 않는다.

### 민서 쪽 기존 소비 흐름

| 파일 (`Assets/01.Scripts/02.World/` 기준) | 역할·확인할 지점 |
|---|---|
| `Clock/Rules/GameClock.cs` | `IGameClock` 등록과 `DayStarted` 제공 |
| `Weather/Rules/IForecastService.cs` | `TryGetOriginal(int day, out WeatherType type)`, `Tamper(int day, WeatherType type)` |
| `Weather/Net/WeatherScheduleDriver.cs` | 서버 시작 시 시계를 조회하고 `IForecastService` 등록. `_profile`, `_dayConfig`, `WeatherStateNet`, `WorldStateNet` 필요 |
| `Weather/Server/WeatherScheduleRunner.cs` | `DayStarted` → `Process(day)` → 실제 예보 조회 → `BeginTransition`. 최초 `Process`에서 스케줄 생성 |
| `Weather/Server/WeatherScheduler.cs` | 미래 날짜의 실제 예보만 변경하고 원래 예보 유지. 당일·과거·범위 밖 날짜 거절 |
| `Weather/Net/WeatherStateNet.cs` | `BeginTransition` → 전환 상태 동기화·적용. `WeatherSystem`이 등록돼 있어야 함 |

민서님은 실제 게임 씬에서 위 컴포넌트와 설정, `IGameClock`/`IForecastService`/`WeatherSystem` 등록, 다음 날 이벤트와 환경 연출을 확인하면 된다. `WeatherScheduleDriver.OnStartServer`가 시계·설정 부족으로 등록을 건너뛰지 않는지 확인한다. 이번 문서 작성에서 실제 씬의 이 연결을 새로 검사한 것은 아니다.

## 3. 완료하지 못한 것

### 환영섬: 현재 진입점과 기존 선언

- 메뉴 연결 위치: `SeaSummonRadialMenu.SelectSlot(int slot)`의 Ability 페이지 마지막 `else`(환영섬 2번 칸). 현재 `SetStatus("환영섬 생성은 민서의 기능 연결 준비 중입니다.")`만 호출한다.
- 기존 World 계약은 다음 선언이다. `Assets/01.Scripts/` 전체 C# 검색에서 이 인터페이스의 구현체·호출자·서비스 등록은 찾지 못했다. 외부/미반영 작업까지 없다고 단정하지 않는다.

```csharp
// Assets/01.Scripts/02.World/IllusionIsland/Rules/IIllusionService.cs
namespace Lighthouse.World.IllusionIsland.Rules
{
    public interface IIllusionService
    {
        bool TryCreate(uint casterId, UnityEngine.Vector3 position, out int illusionId);
    }
}
```

이 선언만으로는 대상 시민·개인 지도·생성 위치·수명·사용권 소비 계약이 완성되지 않는다. 특히 `casterId`의 ID 체계와 대상 수신자를 어떻게 전달/선정할지 확인해야 한다. 기존 타입을 완성된 실행 API로 취급하거나 새 API 이름을 이미 합의된 것처럼 사용하지 않는다.

연결 전에 민서·마피아 담당·필요 시 사용자와 닫을 항목:

| 항목 | 현재 근거·필요한 확인 |
|---|---|
| 생성 대상 | v4는 시민의 개인 지도/화면과 항해사 예외를 기술한다. 이 메뉴에서 누구를 어떻게 선택할지는 미정 |
| 생성 위치 | 기존 인터페이스에 position은 있지만 입력 UI는 없다. 자동 배치/위치 선택은 미확정. 몬스터 탑뷰·검증기를 그대로 적용한다고 가정하지 말 것 |
| 개인 정보·표현 | [N06](../../../07-design-issue-register.md): 개인 환영과 공유 몬스터 경계 계약 확인 필요. 실제 맵 시드를 바꾸거나 무조건 전체 NetworkServer.Spawn으로 공개하는 방식은 채택되지 않음 |
| 지도 비교·시드 대조 | [R18·N02](../../../07-design-issue-register.md): 검증 가설 상태. 개인 지도와 공유 월드의 차이를 시험할 것 |
| 사용 제한·소멸 | v4에는 하루1개 가안과 접근 시 소멸 문구가 있다. 적용 수치·접근 거리·재요청/중복 소비·실패 시 차감·종료 정리는 연결 계약 확인 필요 |
| 식별·권위 | 서버가 송신자에서 ActorId/역할을 조회해야 함. 클라이언트가 임의 casterId/대상/위치를 확정하지 않도록 할 것 |

연결 순서는 **월드 서버 구현·서비스 계약 확인 → 마피아 서버 요청 검증/호출 → 요청자 성공/실패 응답 → 메뉴 진입점 교체**를 권장한다. 이는 구현 제안이며 확정 API 합의가 아니다. UI에서 `TryCreate`를 직접 호출해 월드 상태를 확정하지 않는다. 취소·실패 시에도 커서·조종 입력이 복원돼야 한다.

### 날씨: 남은 규칙·검증

- [W19](../../../07-design-issue-register.md)는 다음 날 예약만 부분 결정됐다. 예측소가 원래/변경된 예보 중 무엇을 보여줄지는 미정이다.
- v4의 날씨 변경 횟수 제한은 이번 코드에서 구현하지 않았다. 현재 `Tamper`는 유효한 미래 날짜를 다시 덮어쓸 수 있다. 무제한 사용을 확정 규칙으로 해석하지 말고 횟수/차감/재선택 정책을 확인할 것.
- 안개는 사용자 승인으로 현재 Overcast에 연결했다. 별도 Fog 타입 추가나 새로운 안개 연출 구현을 이번 요청의 확정 범위로 확대하지 말 것.

## 5. 검증 현황

- L1: 최종 코드 Unity 컴파일 completed, failed=false, compilationFailed=false, errors=[] 확인. 현재 콘솔 오류0, 기존 Player 경고5. 이번 인수인계 작성은 문서만 수정하므로 Unity 검증을 다시 실행하지 않았다.
- L2 격리: 실제 메뉴 프리팹·설정 기반 38조건(그림·3/2/7칸·중앙 호버명·폰트·전환·지연 응답 방어 등) 통과. 렌더 직접 확인. 실제 Play 입력은 아님.
- 날씨 서비스 계약 격리10조건: 현재 날씨 유지, 다음 날 Storm/Overcast 적용, 원래 예보 보존, 당일/과거/범위 밖 거절. Command/TargetRpc 통합 시험은 아님.
- L3 / 멀티플레이: **M0, 미검증**. 실제 F 입력·승선·입력 복원, 호스트와 원격의 예약·다음 날 시각 전환, 환영섬 수신 범위는 통과하지 않았다.
- 인수 시 최소 확인 시나리오:

| 시나리오 | 기대 결과 |
|---|---|
| 호스트/원격 마피아 각각 승선 후 F→날씨→선택 | 본인만 예약 응답 확인, 현재 날씨 유지 |
| 다음 날 시작 | 선택한 Storm/Overcast가 실제 환경과 모든 참가자에게 적용 |
| 시민·하선·난파 상태의 위조 요청 | 서버 거절, 예보 변화 없음 |
| 마지막 날·시계 미시작·판 종료·심연 고정 | 예약 거절 |
| 예약 후 F 닫기·페이지 재진입 | 조종/커서 복원, 지연 응답으로 새 화면이 사라지지 않음 |
| 환영섬 연결 후 생성·접근·소멸 | 합의한 대상만 표시, 항해사 예외·지도/월드 경계·실패/중복 소비 확인 |

4. 실제 Play/M2 결과와 실패 재현을 원문에 기록하고 이 문서의 완료/미완료 상태를 갱신한다.

## 8. 주의

- UI 그림과 중앙 호버 이름, HUD 폰트, 기존 몬스터 소환 흐름을 유지한다. 환영섬 연결을 위해 기존 지점 검증이나 개인 정보 전달을 우회하지 않는다.
- World는 강민서, Mafia는 박태욱, 이번 메뉴 작업은 최명기가 전달한다. 타 영역 변경 전 파일·계약·담당 범위를 확인하며 이 문서는 타 담당 코드의 포괄 수정 승인이나 API 합의 완료를 뜻하지 않는다.
- 최신 민서 pointer에는 Final 섬 DockZone 추가·메인씬 교체·일부 승선 Play 기록이 있다. 과거 박태욱 기록의 ‘DockZone0’을 현재 씬의 확정 결함으로 재사용하지 말고 실제 인수 씬에서 확인한다.
- 기존 사용자/다른 작업자의 미커밋 변경을 보존한다. 씬·프리팹·설정 YAML을 직접 편집하거나 GUID를 변경하지 않는다.

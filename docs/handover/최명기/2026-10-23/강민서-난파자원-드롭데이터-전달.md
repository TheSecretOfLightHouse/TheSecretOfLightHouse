# 인수인계 — 난파 자원·모듈 삭제 결과 수신 (강민서)

작성자: 최명기
수신자: 강민서 (@ri-ver-1)
작성일: 2026-10-23
브랜치: `feature/myeongki`
담당 파트: Player → World
상태: 제공 함수 구현·모듈 조회/인수 시험 확인, World 소비 연결 대기
기준: HEAD `0ca8462` + 현재 미커밋 Player 변경. HEAD만 받으면 아래 API가 모두 포함되는 것은 아니다.

## 1. 목표

명기 쪽에서 난파 손실을 확정하고 인벤토리에서 삭제한다. 민서는 삭제 결과 데이터를 받아 실제 스폰과 이후 월드 처리를 맡는다. 명기 코드에서는 난파 아이템을 물 위에 생성하지 않는다.

- 구조됨: 자원 종류들과 운반 모듈 중 무작위 한 칸 전체 삭제. 나무 10개가 선정되면 10개 모두, 모듈이 선정되면 모듈 1개 삭제.
- 90초 미구조: 보유 자원 전부와 운반 모듈 삭제.
- 자원·모듈 삭제가 모두 성공하면 결과 묶음을 서버 대기열에 한 번 저장한다. 빈 결과는 저장하지 않는다.
- 이번 최신 사용자 결정은 과거 기록의 ‘명기가 물에 생성한 오브젝트를 전달’하는 방향을 대체한다.
- 관련 설계 항목: W10~W13. 표류 수명·회수 등 World 후속 규칙이 이번 제공 API로 확정된 것은 아니다.

## 2. 완료한 것 — 민서가 사용할 계약

### 제공 위치와 함수

대상 플레이어의 `PlayerWreckRecovery` 인스턴스에서 **서버/호스트의 서버 코드로만** 호출한다. 클라이언트 RPC로 이 목록을 보내는 계약은 아니다.

```csharp
public bool TryCopyResourceDropsTo(
    List<WreckDropItem> results,
    out ulong batchId);

public bool TryAcknowledgeDrops(ulong batchId);
```

함수 이름에 Resource가 있지만 결과에는 자원과 모듈이 모두 들어간다.

| 호출 | 동작 |
|---|---|
| `TryCopyResourceDropsTo` | 전달받은 리스트를 비운 뒤 가장 오래된 미인수 결과를 복사한다. 성공하면 true와 결과 번호를 반환한다. 조회만으로 대기열에서 제거하지 않는다. |
| `TryAcknowledgeDrops` | 가장 오래된 결과 번호가 인자와 같을 때만 해당 결과를 제거하고 true를 반환한다. 빈 대기열·다른 번호는 false다. |

조회의 false는 서버가 아니거나, 리스트가 null이거나, 대기 결과가 없다는 뜻이다. 결과 번호는 플레이어 컴포넌트별로 발급되므로 **같은 판에서 `(recovery.netId, batchId)`를 묶어 중복을 구분**한다. 새 판에서는 소비 측 중복 기록도 정리한다.

### 전달 데이터

```csharp
public readonly struct WreckDropItem
{
    public bool IsModule { get; }
    public int ItemId { get; }
    public int Amount { get; }
    public Vector3 Position { get; }
    public uint ModuleId { get; }
}
```

| 필드 | 의미 |
|---|---|
| `IsModule` | false면 자원, true면 모듈 |
| `ItemId` | 자원은 자원 ID, 모듈은 모듈 레시피 ID. 두 ID 공간을 같은 것으로 취급하지 않는다. |
| `Amount` | 실제 삭제한 수량. 모듈은 1 |
| `Position` | 난파 시작 시 기록한 위치. 스폰 위치나 수면 높이를 보장하지 않는다. |
| `ModuleId` | 현재 모듈 삭제 결과에서는 0. 기존 장부 ID를 재사용하는 인계가 아니다. |

오브젝트 참조(`DropObject`)는 없다. 모듈은 기존 `DiscardCarried()`로 보유 기록과 장부까지 삭제한 상태다. 민서가 모듈을 생성할 때는 레시피 ID를 바탕으로 새 모듈 장부 등록·수거 경로를 지훈과 연결해야 한다. 단순히 자원 픽업에 모듈 레시피 ID를 넣는 것으로 모듈 보유가 복구되지는 않는다.

### 호출 순서

1. 서버에서 대상 `PlayerWreckRecovery`를 확보한다. 기존 `PlayerWreckRecovery.Active` 목록을 사용할 수 있으나 서버 인스턴스인지 확인한다.
2. 재사용할 `List<WreckDropItem>`을 준비하고 조회한다.
3. `(netId, batchId)`가 이미 등록된 결과인지 확인한다.
4. 처음 받은 결과라면 민서 처리 목록에 **모든 항목을 복사하여 보관**한다. 부분 등록 후 전체 인수 완료로 처리하지 않는다.
5. 등록이 성공했거나 같은 결과가 이미 등록돼 있으면 해당 인스턴스의 `TryAcknowledgeDrops(batchId)`를 호출한다.
6. 민서 처리 목록에서 스폰·재시도·이후 처리를 수행한다.

```csharp
// Server-side call shape. Keep results as a reusable buffer.
if (recovery.TryCopyResourceDropsTo(results, out ulong batchId))
{
    // Deduplicate by (recovery.netId, batchId).
    // Copy the entire batch into World's own pending work first.
    // Only after successful registration, acknowledge this batch.
}
```

민서 측 등록 함수는 아직 없어 예시에서 가상의 함수명으로 호출하지 않았다. 등록 성공 분기에서 호출할 실제 제공 API는 아래다.

```csharp
bool acknowledged = recovery.TryAcknowledgeDrops(batchId);
```

- 다음 조회가 리스트를 비우므로, 받은 리스트 자체를 민서 작업 목록에 참조로 보관하지 않는다. `ToArray()` 등으로 복사한다.
- 인수 완료는 ‘민서가 처리할 데이터를 확보했다’는 의미다. 스폰 완료를 뜻하지 않는다. 인수 후 실패 재시도 책임은 민서 처리 목록에 있다.
- 인수 완료가 실패하면 이미 등록한 결과를 다시 등록하거나 스폰하지 않는다. 같은 출처와 번호를 확인한다.
- 다음 난파는 `_pendingDrops`를 비우지 않는다. 대기열은 같은 플레이어 인스턴스가 살아 있는 동안 유지된다. 파일 저장·서버 재시작 복구 기능은 아니다.

## 3. 완료하지 못한 것

| 항목 | 현재 상태 | 다음 담당 |
|---|---|---|
| World 자동 조회·등록·스폰 | 호출부 없음 | 민서 |
| 모듈 새 장부 등록·실제 수거 | 제공 결과는 레시피 ID와 수량뿐 | 민서·지훈 연결 |
| 미인수 상태에서 연속 두 번 난파 | 코드상 대기열 유지, 실행 시험 전 | 명기·민서 |
| 자원/모듈 혼합·90초 만료·빈 인벤토리 | 이번 인수 시험의 확인 범위 밖 | 명기 |
| 복귀 도중 실패 재개 | `_isCompletingRecovery` 유지로 재시도 차단 가능 | 명기 |

현재 결과는 인벤토리 정산 직후 저장되며, 이후 배 복귀가 실패해도 이미 삭제된 항목의 결과가 남는다. 민서는 이를 ‘삭제 완료 결과’로 처리하고 ‘복귀 완료 알림’으로 해석하지 않는다.

## 5. 검증 현황

- Unity 6000.0.83f1. 사용자가 호스트와 클라이언트 2인 접속으로 실행했고, AI가 MCP에서 서버 콘솔을 확인했다. 다른 PC 여부·원격 플레이어 자체의 정산 결과는 확인하지 않았다.
- 제공 API 기능 확인: `Batch=1, Count=1` → `IsModule=True, ItemId=101, Amount=1` → `Acknowledge Batch=1: True` → `No pending drops.` 순서 확인.
- 위 결과는 모듈 삭제 결과의 저장·조회·인수 완료·대기열 제거 확인이다. World 실제 소비·스폰 성공 증거는 아니다.
- L1: 컴파일 실패 없음. L2: 위 서버 API 경로 확인. L3: 2인 접속 로그는 있으나 전체 통합 기준 통과로 판정하지 않는다(M2 이상 환경 세부 미확인).
- 별도 기존 오류: `WaterSamplerHost` 누락/슬롯 부족, `TemporaryRescueKorean` 폰트 텍스처 누락. 입력 컨트롤 스킴 경고도 존재해 전체 콘솔 오류 0 상태는 아니다.

- [ ] 민서·지훈이 삭제된 모듈의 새 생성·장부·수거 처리를 연결한다.

## 7. 다음 세션의 첫 행동

1. 제공 코드의 두 함수 시그니처와 `WreckDropItem` 필드를 대조한다.
2. 서버에서 조회하고 민서 처리 목록에 복사·중복 방지 등록한 뒤 인수 완료한다.
3. 모듈 ID 101 수량 1의 입력으로 새 생성·수거까지 시험한다.
4. 미인수 연속 난파·중복 조회·다른 번호 인수 거절·여러 플레이어의 동일 batchId를 시험한다.

## 8. 주의

- 명기가 이미 삭제한 인벤토리에서 민서가 다시 차감하지 않는다.
- 삭제된 모듈의 기존 장부 ID를 재사용하지 않는다.
- 실제 게임 연결에서는 임시 `Test/Acknowledge Read Drops` 메뉴로 민서 인수 전에 결과를 제거하지 않는다.
- 임시 모듈 지급과 콘솔 시험 메뉴는 개발용이다. 채집·작업대 정상 플로우 검증을 대신하지 않는다.

개인 자원에서 **실제로 제공하는 함수와 작업대에서 연결할 부분**을 정리했다. 이 파일로 연결 검토를 시작하고, 상세 경계·시험표는 API 문서를 참고한다. 새 API·인자 의미를 합의한 문서는 아니다.

## 1. 목표
- **추가 확정(2026-10-17): 작업대·등대에서 자원을 뺄 수 있는 사람은 마피아뿐이다. 등대 수리에 이미 반영된 자원도 회수할 수 있고, 그 자원에 해당하는 수리 진행도를 되돌린다. 시민은 본인 투입분도 회수할 수 없다.**
- 최신 권한 결정: [공용 인벤토리 결정](../../../design/shared-inventory-decisions.md). 마피아만 공용 자원을 인출할 수 있고 시민은 본인 투입분도 꺼낼 수 없다. 서버에서 역할 검사하며, 실패한 투입의 복구와 정상 인출은 구분한다.
- 작업대가 개인 자원을 조금씩 받아 누적하고, 부족분을 나중에 추가 투입할 수 있도록 연결한다.
- 상세 함수 동작·예외·책임의 기준은 [API 문서](../../../unity/PLAYER_INVENTORY_API.md)다. 아래는 수신자가 바로 연결을 검토하기 위한 요약이다.

### 실제 제공 함수 — 서버에서 직접 호출

| 시그니처 | 반환값·경계 |
|---|---|
| `[Server] int GetCount(int id)` | 개인 서버 보유량, 항목 없으면0 |
| `[Server] int TryRemoveTo(int id, int requestedAmount)` | 보유량과 요청량 중 적은 만큼 차감하고 **실제 차감 개수** 반환. 보유3/요청4이면3. 카탈로그 없음·미등록 ID·0 이하 요청·보유 없음이면0 |
| `[Server] bool TryAdd(int id, int amount)` | 추가 성공 true. 카탈로그 없음·미등록 ID·0 이하 수량·int 합계 초과는 false·무변경. 이전 차감/반환 이력은 검사하지 않음 |

`PlayerInventory`는 네임스페이스 없는 전역 타입이다. 자원 ID는 연결된 ResourceCatalog의 ResourceDefinition.Id이며 ActorId·netId·SpotId와 다르다. `[Server]`는 클라이언트 호출을 서버 요청으로 전송하지 않는다.

## 6. 확인 요청 (김지훈·최명기, 연결 전 필요한 계약)

| # | 확인할 것 | 근거 | 정하지 않으면 |
|---|---|---|---|
| 1 | **호출 경로·인자.** 작업대 처리기/Action, 자원 ID·요청량의 인자 의미와 남은 필요량의 서버 원본 확인 | 개인 API는 id·amount만 받음. Arg0/Arg1 매핑 미합의 | 다른 재료 차감·초기 비용으로 반복 차감 가능 |
| 2 | **거래 확정·실패.** 차감/누적 확정 시점·동일 거래 재요청 식별·복구 실패 상태/재시도 주체를 양쪽 확인 | N09. 거래 ID·예약·자동 롤백 없음 | 개인 유실·중복 반환·중복 누적 가능 |
| 3 | **인출·제작/수리 경합.** 한도·시점·완료 잠금·취소/레시피 변경, 회수량↔진행도 환산·단계별 회수 대상·의식/승패 경합을 확인 | W08은 마피아 전용 및 작업대·등대의 수리 반영 자원 회수까지 확정. 인출 시 등대 HP는 감소하지 않음 확정. 보상 처리 미정 | 자원 지급과 진행도 차감이 어긋나거나 같은 수리 자원을 중복 회수할 수 있음 |
| 4 | **추가 API 필요 여부.** 현재 함수로 수지를 보장할 수 있는지, 실패 사유·예약/확정/복구 API 확장이 필요한지 확인 | 차감0은 실패 원인을 구분하지 않음 | 연결 뒤 계약을 다시 바꿔야 할 수 있음 |
| 5 | **제공 측 검증.** 최명기는 컴파일·원격 Owner 표시·프리팹 연결·새 판 수량 수명 확인 | 서버 초기화/저장·복원 API 없음. InventoryReset은 UI 알림 | 판 재사용 시 이전 수량이 남는지 검증할 수 없음 |

위 표는 확인 요청이며 담당자 합의 완료나 김지훈의 단독 결정 의무를 뜻하지 않는다.
- **연결 가능 범위:** 현재 API는 개인 수량의 조회·부분 차감·추가다. 공용 저장소·제작·인출·원자적 거래 완성 API를 제공한 것은 아니다. 함수 이름 변경이나 새 인터페이스가 필요하면 호출부 요구부터 양쪽이 확인한다.
- 김지훈 확인 요청: 실제 처리기/Action, 요청량 출처와 남은 필요량의 권위, 거래 식별/중복 응답, 반영 실패/복구 실패 정책, 인출·제작 경합의 확정 시점을 명시한다. 아직 답을 받거나 합의한 기록은 없다.
- 제공 측 확인: 최명기는 대상 플레이어 프리팹의 PlayerInventory·카탈로그 연결, Owner 초기/변경 동기화, 새 판 수량 수명을 검증한다. API 문서 §6의 한계도 함께 검토한다.

## 7. 다음 첫 행동

2. 검증된 송신자의 PlayerInventory를 사용해 작업대 남은 필요량 이하로 TryRemoveTo를 호출한다.

## 8. 주의
- 등대 회수는 개인 TryAdd만 호출해서 끝나지 않는다. 등대 측 회수 가능한 자원/기여와 진행도 감소를 관리하고 개인 지급과 함께 확정한다. 새 결정만으로 보상 취소·HP 감소·확정 승패 취소를 구현하지 않는다.
- InventoryData 직접 변경, SyncDictionary 직접 갱신, 필요량 대신 초기 비용으로 반복 차감, 제작 시 개인 재차 차감을 하지 않는다.
- TryAdd는 일반 추가 함수라 중복 반환을 막아주지 않는다. 실패 시 무조건 복구 성공했다고 처리하지 않는다.
- 디버그 GUI의 새 목표 시작은 작업대 인출·취소·반환 기능이 아니다.
- 명기님에게 작업대 구현을 넘기는 문서가 아니다. 별도 인터페이스는 현재 필수가 아니며 필요 시 호출 계약부터 합의한다.

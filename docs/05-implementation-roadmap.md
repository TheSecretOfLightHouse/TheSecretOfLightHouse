# 등대 구현 로드맵

> 기획 기준: [게임 기획서 v4](design/references/game-design-v4.md). 2026-10-10 결정 목록·단계·추적표를 v4 기준으로 갱신했다. 관련 작업 전 [설계 문제 대장](07-design-issue-register.md)의 관련 ID를 확인한다. 원문의 가안·미정은 임의 확정하지 않는다.

기준일: 2026-10-09(코드 조사), 2026-10-10(v4 반영). 현재 본편 코드와 [시스템 디자인](01-system-design.md)·[게임 기획](design/references/game-design-v4.md)·[기술설계](03-technical-design.md)를 대조한 실행 계획이다. 아래 순서는 권장 순서이며 날짜·공수·미정 게임 규칙을 확정하지 않는다. 사람별 실행 목록은 [담당자별 구현 작업](06-owner-work-plan.md), 소유권은 [담당표](CODE_OWNERSHIP.md)를 따른다.

## 1. 현재 출발점

조사 범위는 `Assets/01.Scripts/`의 C# 34개와 Player 씬·입력 에셋이다. SVN 데모와 개인 작업까지 조사한 것은 아니다. 이 조사에는 실행 검증이 포함되지 않는다.

| 영역 | 확인한 근거 | 남은 구현·검증 |
|---|---|---|
| 플레이어 | `05.Player/` 제어·입력·이동·배·상태·능력·애니메이션 코드 26개 | 로컬 실행 확인, 서버 권위·소유권, 내구도·난파·구조·인벤토리 |
| 월드 | `02.World/` IslandHandle, SeaZone, SpawnerPoint, SpotInfo, ResourceDefinition, ResourceRarity 6개 | 생성·배치·잔량·회복·시간·날씨·동기화 실제 처리 |
| 상호작용 | `03.Interaction/Requests/Net/` 요청 구조체와 enum 2개 | Relay·Router·Validator·기록·개별 실행과 실패 응답 |
| 네트워크·등대·몬스터·투표·시스템·UI | 작업 폴더와 Mirror 의존성 | 조사한 본편 C#에서는 실행 기능 미확인. 폴더나 패키지를 완료로 세지 않음 |

34개 C#에서 Mirror 권위·Command/Rpc 구현은 확인되지 않았다. 단일 `Lighthouse.Runtime`과 폴더 분리는 작업 경계이며 각 담당자가 자신의 서버·클라이언트·동기화를 구현해야 한다.

### 먼저 처리할 실제 코드 차이

- **입력 연결:** Player 씬은 `Assets/InputSystem_Actions.inputactions`를 사용한다. 액션 Attack/Sprint와 `PlayerInputReader`의 OnFire/OnRun이 맞지 않고 기본 ActionMap도 비어 있다. 실제 전달 방식·맵 활성화·능력 입력을 확인하지 않으면 달리기·사격 콜백이 실행되지 않을 수 있다. 최명기 MK01에서 우선 확인한다.
- **발행만 있는 이벤트:** `BoatController.TryFire`는 CannonFired를, PlayerController는 InteractionRequested를 발행하지만 조사한 본편에 소비자가 없다. 사격·채집 완료로 집계하지 않고 MK02/JH02에서 처리 경로를 연결한다.
- **능력 실행기만 존재:** PlayerAbility는 추상 클래스이고 구체 능력은 미발견, 씬의 jobAbility도 비어 있다. MK05에서 확정 직군부터 구현한다. Runner/AnimationDriver의 직렬화 참조 0은 GetComponent 자동 조회가 있으므로 그것만으로 미연결로 판정하지 않는다.
- **난파 입력:** SetDowned와 이동 잠금은 있으나 난파 중 LookInput 기반 heading 갱신은 중단된다. 독립 카메라 회전 경로는 미확인이다. 카메라·비밀 투표·구조 UI는 허용돼야 하므로 MK04에서 실제 조작을 확인한다.

근거 위치는 [담당자별 작업의 코드 출발점](06-owner-work-plan.md#2-최명기--플레이어시스템ui)에 정리한다.

## 3. 권장 구현 순서

단계는 기능 의존성이다. 작업 ID 하나가 여러 단계에 걸칠 수 있다. A는 시험용 고정 배치와 입력 콜백 확인으로 검증하며 완성 직군 능력은 기다리지 않는다. B는 일반 등대 수리까지, C는 자연 몬스터·난파까지, 최후 전투/괴물/투표 연계는 D에서 통합한다. 계약이 독립적인 작업은 병행한다. 미정 기능을 뺀 축소 검증은 그 범위만 통과로 기록한다. ID 상세는 [담당자별 작업표](06-owner-work-plan.md)를 따른다.

| 단계 | 해야 할 일 | 작업 ID | 선행 조건 | 완료를 판단할 증거 |
|---|---|---|---|---|
| A 실행 기반 | 지정 Unity에서 코드·씬 확인, 접속·스폰·소유 입력, 공통 식별 계약 | JH01, MK01 | 버전·씬·경계 확인 | 호스트+원격 3명 접속, 각자 캐릭터/배만 조작, 재현 기록 |
| B 첫 플레이 흐름 | 섬→자원→채집→인벤토리→작업대→모듈→등대 수리 | MS01·02, MK03, JH02·03·04 | A, D02 최소 시험 데이터, 대상 선택 담당/TargetId 계약 확인 | 동시 채집·투입에서도 자원 합계 보존, 수리도 일치 |
| C 시간·위험·복귀 | 낮밤·비율 해금·회복, 날씨·파도 충격, 자연 몬스터·배 피해·난파·잔해 표류·구조 | MS03·04, TW01·02, MK02·04 | B 계약, D01·03 | 일차·피격 상태 일치, 복귀/손실 한 번 확정 |
| D 역할·승패 | 투표(2회 제한)·봉인·심해·확인·소환·점화·최후 전투(심연 날씨) | TW01 소환 부분·TW03~05, JH04, MK05·06 | D04~07·10, B·C 소비 기능 | 총 4인 각 승패 분기, 비밀 정보 수신 범위 |
| E 추리·방해 | 유령선/힌트·특수 섬·환영 섬·날씨 변경·토네이도·부식·직군. 인게임 보이스는 제외하고 밤 토론 수단은 D09 결정 대기 | MS05~08, JH05·06, MK05~07 | 기능별 기획, D06·09~11 | 단서·수신 권한·횟수·상태 제한 일치 |
| F 전체 판 안정화 | 확정 재접속 정책, 동시 요청·실제 네트워크·밸런스·회귀 | JH07·08, 전 담당 | 기능별 검증·잔여 결정 목록 | 4인 전체 판과 각 승패 로그, 미통과 목록 |

AX01~03은 단계 전체의 기록·문서 지원이며 게임 실행의 차단 선행이 아니다. 부식 낙하·토네이도의 기본 동작은 v4 7.4·10.3에 있으므로 착수할 수 있다. 낙하 시점·분해 결과 등 D11의 미정 값만 교체 가능하게 두고 결정 후 수용 판정한다.

## 5. 담당 사이에서 먼저 맞출 계약

| 계약 | 제공 → 소비 | 합의할 내용 |
|---|---|---|
| 참가자·연결 | 김지훈 → 전 담당 | ActorId/발신자·소유권·이탈/재접속 식별 |
| 대상 선택·식별 | 담당 확인, 최명기 입력·김지훈 요청·강민서 월드 협의 | 입력 이벤트에는 대상이 없음. 탐지/선택 책임, TargetId(uint)와 SpotId(int)/Island Index(short) 매핑·등록/해제·유효성 계약 |
| 전투 | 최명기 대포 → 박태욱 몬스터, 몬스터/암초 → 최명기 배 | 발사·명중·몬스터 체력/처치·배 피해의 판정 주체와 중복 방지 |
| 모듈·보상 효과 | 김지훈 → 최명기 배/채집, 강민서 자원 협의 | 이동속도·파밍량·대포피해 적용/해제, 소환 후 보상 제외, 중복 장착/수리도 전환 |
| 상호작용 | 기능 요청 → 김지훈 경로 → 기능 실행자 | 거리·상태·횟수 검증 책임, 중복·실패 응답·기록 |
| 배치/스폰 | 강민서 → 박태욱, 김지훈 등록 | 배치 ID·영역·프로필·생성/제거·서버 전용 출처 |
| 자원 거래 | 강민서 잔량 ↔ 최명기 인벤토리 ↔ 김지훈 제작/등대 | 차감/지급·실패 복구·동시 요청·이탈 |
| 시간/단계 | 강민서 ↔ 최명기(시스템 단계) ↔ 전 담당 | 일차 리셋·최후 전투 시간 지속·종료 후 변경 차단 |

| 유령선 | 강민서 등장 → 김지훈 힌트 → 최명기 UI | 조사 가능 시간·횟수·대상·수신자·중복 생성 |

다른 영역 변경 전 파일·담당·이유·영향과 기존 합의를 확인한다. 공용 네트워크 담당에게 모든 서버 구현을 넘기지 않는다.

## 6. 검증과 갱신

- 상태는 미착수 / 결정 대기 / 구현됨·미연결 / 구현됨·실행 미검증 / 검증 통과(범위 명시)로 기록한다. 파일명·씬·로그 등 증거 없이 완료율을 올리지 않는다.
- [멀티플레이 기준](ai/04_MULTIPLAYER_TEST_PROTOCOL.md)에 따라 M0/M1은 중간 확인, 네트워크 변경은 최소 M2다. 진영·투표·정원·승패는 호스트 1+원격 3 총 4인, 실제 네트워크는 M3로 확인한다.
- 작업 ID·변경 파일/씬·빌드 기준·인원·기대/실제 결과·로그·미결 조건을 기록한다. 일정은 v4 12장을 따른다: 정기 4인 테스트 10/13·10/16·10/21·10/24·10/26~27, 기능 동결 10/25, 최종 마감 11/1, 마일스톤 M01~M09. 원본 일정이며 달성 여부는 검증된 사실이 아니다.
- 지정 Unity 6000.0.83f1 컴파일·Mirror Weaver·씬 로드·Play Mode·4인 플레이는 미검증이다. 다른 환경의 보조 컴파일 등은 지정 버전 검증을 대체하지 않는다.
- 폴더 이동 뒤 빌드 씬 목록과 `m_UseUCBPForAssetBundles: 0` 기본값은 지정 버전에서 확인한다. [아키텍처](04-architecture.md) 참조.

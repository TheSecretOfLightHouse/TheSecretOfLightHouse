# 등대 구현 로드맵

> 기획 기준: [승패·투표 결정](design/win-vote-decisions.md)이 충돌 범위에서 [게임 기획서 v4](design/references/game-design-v4.md)보다 우선한다. 2026-10-11 결정 목록·단계·계약을 갱신했다. 관련 작업 전 [설계 문제 대장](07-design-issue-register.md)의 관련 ID를 확인한다. 미변경 규칙은 v4를 따르며 가안·미정은 임의 확정하지 않는다.

기준일: 2026-10-09(기존 코드 조사), 2026-10-10(v4 반영), 2026-10-11(승패·투표 결정 반영, 네트워크·투표 재확인). 본편 코드와 [시스템 디자인](01-system-design.md)·[기술설계](03-technical-design.md)를 대조한 실행 계획이다. 아래 순서는 권장 순서이며 날짜·공수·미정 게임 규칙을 확정하지 않는다. 사람별 실행 목록은 [담당자별 구현 작업](06-owner-work-plan.md), 소유권은 [담당표](CODE_OWNERSHIP.md)를 따른다.

## 1. 현재 출발점

2026-10-09 기존 조사 범위는 `Assets/01.Scripts/`의 C# 34개와 Player 씬·입력 에셋이었다. 2026-10-11 파일 목록은 C# 70개이며 네트워크 코드, 월드 인터페이스·Mock·Sandbox가 추가돼 있다. 이번 갱신은 목록과 네트워크·투표의 실제 처리 경로를 재확인했으며 추가 코드 전체의 실행 감사를 뜻하지 않는다. SVN 데모와 개인 작업은 범위 밖이다. JH01의 기존 M2 실행 기록은 아래와 담당자별 작업표에 보존한다.

Mirror 서버 등록·SyncVar·시험 Command/TargetRpc가 네트워크 코드에 존재한다. 투표 횟수 상한은 생성자 입력이며 `Assets/01.Scripts/` 검색에서 VoteService 호출자는 미발견이다. 같은 대상은 `false`를 반환하며 횟수를 차감하지 않으므로 소비 규칙은 새 결정과 일치하지만 UI 응답 의미는 합의가 필요하다. 자기표 허용과 역할·의식 잠금 검사 부재는 새 결정과 차이다. 접속 단절에서는 연결 조회를 제거하고 Mirror 기본 해제를 호출한다. 판 진행 중 이탈 시 판 종료(2026-10-13 결정)는 JH07에서 반영해야 한다. 단일 `Lighthouse.Runtime`과 폴더 분리는 작업 경계이며 각 담당자가 자신의 서버·클라이언트·동기화를 구현해야 한다.

### 먼저 처리할 실제 코드 차이

- **입력 연결:** Player 씬은 `Assets/InputSystem_Actions.inputactions`를 사용한다. 액션 Attack/Sprint와 `PlayerInputReader`의 OnFire/OnRun이 맞지 않고 기본 ActionMap도 비어 있다. 실제 전달 방식·맵 활성화·능력 입력을 확인하지 않으면 달리기·사격 콜백이 실행되지 않을 수 있다. 최명기 MK01에서 우선 확인한다.
- **발행만 있는 이벤트:** `BoatController.TryFire`는 CannonFired를, PlayerController는 InteractionRequested를 발행한다. 사격은 소비자가 없고, InteractionRequested는 JH02의 `PlayerInteractionInput`이 구독하지만 본편 프리팹에 아직 붙지 않았다. 사격·채집 완료로 집계하지 않고 MK02와 본편 프리팹 부착(최명기)으로 연결한다.
- **능력 실행기만 존재:** PlayerAbility는 추상 클래스이고 구체 능력은 미발견, 씬의 jobAbility도 비어 있다. MK05에서 확정 직군부터 구현한다. Runner/AnimationDriver의 직렬화 참조 0은 GetComponent 자동 조회가 있으므로 그것만으로 미연결로 판정하지 않는다.
- **난파 입력:** SetDowned와 이동 잠금은 있으나 난파 중 LookInput 기반 heading 갱신은 중단된다. 독립 카메라 회전 경로는 미확인이다. 카메라·비밀 투표·구조 UI는 허용돼야 하므로 MK04에서 실제 조작을 확인한다.

근거 위치는 [담당자별 작업의 코드 출발점](06-owner-work-plan.md#2-최명기--플레이어시스템ui)에 정리한다.

v4 12.1 시스템&UI 전체와 게임 단계·승패 최종 확정은 최명기 담당이다. D10은 담당 배정 대기가 아니라 기능 간 입력 API와 종료 경합 계약이다. 보이스 삭제와 밤 토론 수단은 D09를 따른다. 가안은 시험값임을 명시하고 교체 가능하게 구현한다. 소환 순간 결속 버프 등 검토 항목은 필수 완료 범위에 넣지 않는다. 해상 인양은 v4에 없으므로 범위 밖이다. v4 필수 기능은 유령선·특수 기능 섬 3종·최후 전투 전용 날씨(심연)·부식 모듈 표류·회수이며, 토네이도(일반)와 거대 파도(여유)는 일정이 부족하면 먼저 뺀다.

## 3. 권장 구현 순서

단계는 기능 의존성이다. 작업 ID 하나가 여러 단계에 걸칠 수 있다. A는 시험용 고정 배치와 입력 콜백 확인으로 검증하며 완성 직군 능력은 기다리지 않는다. B는 일반 등대 수리까지, C는 자연 몬스터·난파까지, 최후 전투/괴물/투표 연계는 D에서 통합한다. 계약이 독립적인 작업은 병행한다. 미정 기능을 뺀 축소 검증은 그 범위만 통과로 기록한다. ID 상세는 [담당자별 작업표](06-owner-work-plan.md)를 따른다.

| 단계 | 해야 할 일 | 작업 ID | 선행 조건 | 완료를 판단할 증거 |
|---|---|---|---|---|
| A 실행 기반 | 지정 Unity에서 코드·씬 확인, 접속·스폰·소유 입력, 공통 식별 계약 | JH01, MK01 | 버전·씬·경계 확인 | 호스트+원격 3명 접속, 각자 캐릭터/배만 조작, 재현 기록 |
| B 첫 플레이 흐름 | 섬→자원→채집→인벤토리→작업대→모듈→등대 수리 | MS01·02, MK03, JH02·03·04 | A, D02 최소 시험 데이터, 채집 지점 SpotId 클라이언트 조회(강민서 확인) | 동시 채집·투입에서도 자원 합계 보존, 수리도 일치 |
| C 시간·위험·복귀 | 낮밤·비율 해금·회복, 날씨·파도 충격, 자연 몬스터·배 피해·난파·잔해 표류·구조 | MS03·04, TW01·02, MK02·04 | B 계약, D01·03 | 일차·피격 상태 일치, 복귀/손실 한 번 확정 |
| D 역할·승패 | 시민 투표2회·개인 확인권·봉인/심해·의식·최후 전투(심연 날씨)와 이탈 시 판 종료 | TW01 소환 부분·TW03~05, JH04·07, MK05·06 | D04~08·10 확정 규칙/API, B·C 소비 기능 | 총 4인 의식 성공/실패·최후 수리/HP 종료, 타이머 제거·권리 수명·누적·비밀 수신 범위. 미정 경합은 제외 범위로 명시 |
| E 추리·방해 | 유령선/힌트·특수 섬·환영 섬·날씨 변경·토네이도·부식·직군. 인게임 보이스는 제외하고 밤 토론 수단은 D09 결정 대기 | MS05~08, JH05·06, MK05~07 | 기능별 기획, D06·09~11 | 단서·수신 권한·횟수·상태 제한 일치 |
| F 전체 판 안정화 | 이탈 시 판 종료·동시 요청·실제 네트워크·밸런스·회귀. 재접속은 10/25 이후 선택 | JH07·08, 전 담당 | 기능별 검증·잔여 결정 목록 | 4인 전체 판·이탈 시 종료·각 승패 로그, 미통과/미정 목록 |

AX01~03은 단계 전체의 기록·문서 지원이며 게임 실행의 차단 선행이 아니다. 부식 낙하·토네이도의 기본 동작은 v4 7.4·10.3에 있으므로 착수할 수 있으며 의식 중 낙하는 차단한다. 낙하 시점·억제 후 처리·분해 결과 등 D11 미정은 임의 확정하지 않고 결정 후 수용 판정한다.

다른 영역 변경 전 파일·담당·이유·영향과 기존 합의를 확인한다. 공용 네트워크 담당에게 모든 서버 구현을 넘기지 않는다.

이 표는 제공자·소비자와 합의할 계약을 연결한 작업 기준이며 실제 API 서명이나 팀원 합의 완료를 뜻하지 않는다. 기획 결정으로 닫히지 않은 경합·호스트 이탈·기한 경계·모듈 조건·월드 일일 효과는 구현자가 선택해 확정하지 않는다.

## 6. 검증과 갱신

- 상태는 미착수 / 결정 대기 / 구현됨·미연결 / 구현됨·실행 미검증 / 검증 통과(범위 명시)로 기록한다. 파일명·씬·로그 등 증거 없이 완료율을 올리지 않는다.
- [멀티플레이 기준](ai/04_MULTIPLAYER_TEST_PROTOCOL.md)에 따라 M0/M1은 중간 확인, 네트워크 변경은 최소 M2다. 진영·투표·정원·승패는 호스트 1+원격 3 총 4인, 실제 네트워크는 M3로 확인한다.
- 작업 ID·변경 파일/씬·빌드 기준·인원·기대/실제 결과·로그·미결 조건을 기록한다. 일정은 v4 12장을 따른다: 정기 4인 테스트 10/13·10/16·10/21·10/24·10/26~27, 기능 동결 10/25, 최종 마감 11/1, 마일스톤 M01~M09. 원본 일정이며 달성 여부는 검증된 사실이 아니다.
- JH01은 지정 Unity 6000.0.83f1에서 같은 PC 에디터 호스트1+빌드 클라이언트3 M2 통과 기록이 있다. 이번 문서 갱신에서 실행을 재검증하지 않았고 M3·본편 통합·새 승패/투표/단절 규칙은 미검증이다. 다른 환경의 보조 컴파일 등은 지정 버전 검증을 대체하지 않는다.
- 폴더 이동 뒤 빌드 씬 목록과 `m_UseUCBPForAssetBundles: 0` 기본값은 지정 버전에서 확인한다. [아키텍처](04-architecture.md) 참조.

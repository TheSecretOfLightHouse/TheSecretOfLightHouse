# 마피아 바다 일일 소환 제한

작성 담당: 박태욱(Mafia 기능)
작성일: 2026-10-26
갱신일: 2026-10-26
상태: 구현됨(통합 미검증)
브랜치·기준 커밋: feature/mafia-summon-limit / eb4e78b

## 요청과 목표

사용자가 만든 브랜치에서 World 코드를 수정하지 않고 기존 IGameClock.DayIndex와 DayStarted로 하루 3회 제한을 연결한다. 아침마다 미사용분을 버리고 3회로 복원한다. 의식·최후 전투 전용 규칙은 보류한다.

## 진행 과정과 결정 이유

- 이전 대화의 조사 결과와 현재 브랜치를 재대조했다. 작업 시작 시 git status는 깨끗했다. 현 브랜치 소환 코드는 CapsuleCollider 기반이며 이 기능과 무관한 Box 호환 변경을 옮기지 않았다.
- SeaSummonSpawnController에 서버 시계 연결 대기, 아침 구독, 마지막 처리 일차를 추가했다. 본편 세션 흐름은 InProgress인지 확인하며, 실제 GameClock이 시작되지 않았거나 서비스가 없으면 횟수 조회·소환을 허용하지 않는다. 서비스 등록이나 기본 일차 1만으로 시작했다고 판단하지 않는다.
- 최초 연결과 요청/잔여 횟수 조회 때 현재 일차를 비교한다. 더 큰 일차일 때만 ActorId별 사용 횟수를 비우므로 중복 아침이나 이전 날짜로의 재동기화는 추가 횟수를 지급하지 않는다. 날짜를 건너뛰어도 이월하지 않는다.
- 초기화 때 기존 권한·승선 검증을 통과한 접속자에게만 TargetQuota로 갱신한다. 다른 참가자에게 소환자 정보를 공개하지 않는다. 하선 중에는 기존 권한 흐름에 따라 다음 유효 조회에서 받는다.
- 성공 후 차감, 중복 요청 결과 캐시, 기존 소환 개체는 유지한다. 날짜 변경은 횟수만 초기화하며 서버 종료 때 구독과 마지막 일차·횟수를 정리한다.
- 기존 DayIndex는 Update 캐시이므로 아침의 시계 갱신보다 먼저 처리된 요청은 전날 기준일 수 있다. 사용자가 World 무수정 방식으로 진행하도록 허용한 경계 한계이며 즉시 현재 시각 판정을 구현했다고 주장하지 않는다.

## 변경 파일과 결과

- Assets/01.Scripts/07.Mafia/SeaSummoning/Net/SeaSummonSpawnController.cs: 서버 날짜 연결과 초기화·개인 잔여 횟수 전송.
- docs/design/win-vote-decisions.md: 바다 소환 일일 제한의 사용자 결정과 보류 범위.
- 본 원문과 개인 POINTER.md: 상태·검증·후속 작업.
- World·Network·Player 코드, 씬·프리팹·설정 에셋은 수정하지 않는다. 현재 SeaSummonSettings 에셋의 한도 3을 사용한다. 커밋·푸시는 하지 않는다.

## 검증

- Unity MCP로 에디터 연결 확인: Unity 6000.0.83f1, MainOffline, Play 꺼짐.
- Unity 스크립트 컴파일 요청 후 콘솔에서 에러 없음, 기존 BoatController._dashAccelerationMultiplier의 미사용 경고 CS0414 확인.
- MCP execute_code로 저장되지 않는 PreviewScene에서 실제 GameClock·SeaSummonSpawnController를 만들었다. Mirror 서버는 listen=false로 초기화해 소켓 접속 없이 서버 API를 실행했다. 검사 후 OnStopServer·NetworkServer.Shutdown·PreviewScene 정리, Transport 복원.
- 12개 통과: 시계 시작 전 거절, 첫날 늦은 연결, 밤 횟수 유지, 다음 아침 전원 횟수 초기화(미사용분 포함), 요청 캐시 보존, 중복 아침 재지급 방지, Resync로 이벤트 없이 날짜 변경 후 조회 복구, 이전 일차 재동기화 시 미복원, 여러 날 건너뜀 시 이월 없음, 서비스 부재 거절, 서버 종료 상태 초기화, 이벤트 구독 해제.
- 위 검사는 사용 횟수와 요청 캐시를 리플렉션으로 준비한 날짜 연결 API 검사다. 실제 생성·위치 선택·4번째 거절·TargetRpc 수신·UI·서버 시작 코루틴을 끝까지 거친 PlayMode 검증은 아니다. L2/L3·M2 통과로 확대하지 않는다.
- git diff --check 실행. 실제 플레이·원격 클라이언트 시험은 미실행이며 통합 검증 대기다.
- 검사 후 서버/클라이언트/Play 꺼짐, 시계 서비스 제거, Transport 원복을 확인했다. MainOffline은 isDirty=true였다. 검사 전 dirty 값을 확보하지 못했으므로 원인을 단정하지 않고 저장·재로드·dirty 강제 해제를 하지 않았다. 디스크 씬 변경은 없다.

## 남은 일과 차단 조건

- 본편 M2 실행 결과: MainGame에 소환 컨트롤러 3종과 DockZone이 없어 실제 소환 시험이 차단된다. 먼저 본편 연결 범위를 정해야 한다. 아래 실행 이력을 참고한다.
- World 시계가 등록되고 시작된 담당 씬에서 첫날 실제 3회 성공·4회 거절, 생성 실패 시 미차감, 아침 한도 복원, 원격 개인 UI 수신을 확인한다.
- 시계 없는 독립 소환 시험 씬은 이제 준비 중으로 거절되므로 실제 World 시간 구성이 있어야 한다. 대체 독립 타이머를 추가하지 않는다.
- 의식·최후 전투 중 적용은 K03·W16 보류이며 이번 구현은 단계별 허용/차단을 새로 정하지 않는다.

## 다음 행동

김지훈 담당 통합 MainGame에 Mafia 소환 구성 연결 범위를 맞추고, DockZone 연결은 김지훈·최명기와 확인한다. 연결 후 일반 낮밤 실제 소환과 원격 개인 UI 수신을 재검증한다. 이번 검증 요청으로 통합 씬을 수정하지 않는다.

## 본편 검증 이력 — 2026-10-26

- 후속 사용자 요청: 본편에서 검증한다. 신규 게임 코드 수정 없이 현재 본편 구성을 검사했다. 사용자 요청으로 영어 주석 2개를 한글로 변경한 상태다.
- 준비 상태: MainOffline, Play 꺼짐, 씬 dirty=true였다. 기존 미저장 상태를 저장하거나 강제로 지우지 않았다. MPPM Player1~4가 Launched 상태였다.
- 저장된 MainGame을 PreviewScene으로 읽어 비활성 객체까지 확인했다. GameClock 1, WorldStateNet 1, SeaSummonSpawnController 0, DockZone 0이었다. 런타임 생성 가능성을 배제하지 않고 실제 4인 진입으로 확인했다.
- 임시 Editor 검사기 DailyQuotaMainProbe로 MainOffline의 기존 StartHost/StartClient, LobbyPlayer.RequestSetReady만 호출했다. 검사기가 처음 scripts 범위 새로고침에서는 로드되지 않아 첫 Play를 종료한 뒤 전체 에셋 새로고침으로 임포트했다. 이 첫 시도는 접속 0이며 기능 검증으로 세지 않는다.
- 두 번째 실행에서 호스트1+동일 PC MPPM 원격3, 총4인 모두 MainGame/InProgress에 진입했다. 호스트 Connections=4, 각 인스턴스 Players=4, GameClock=1, DayIndex=1, IsRunning=true, 로컬 플레이어/연결 정상으로 확인했다.
- 호스트·원격3 모두 비활성 객체 포함 SeaSummonSpawnController=0, SeaSummonPermissionController=0, SeaSummonPointController=0, DockZone=0이었다. 일일 소환 코드 자체가 본편 실행 객체에 연결되지 않은 상태다.
- 호스트에서 실제 서버 참가자4명 모두 OwnedBoat 있음, CurrentBoat 없음, IsOccupied=false, IsDowned=false를 확인했다. 승선 조건을 강제 주입하지 않았고 소환 객체나 임시 DockZone을 추가하지 않았다.
- 판정: 본편 진입 M2 확인, 소환 기능은 연결 누락으로 차단. 실제 3회 성공·4번째 거절·실패 미차감·다음 아침 복원·개인 UI/RPC는 미검증이다. 날짜 연결 API 12개 통과와 본편 기능 통과를 구분한다.
- 기존 LeaveSession 호출 후 네 인스턴스 모두 MainOffline, 연결 해제, Players=0을 확인했다. 호스트 서버/클라이언트 비활성 확인 뒤 Play 종료. 검사 중 콘솔 오류·경고 조회는 0개였다.
- 임시 검사기와 meta, 접속 관찰 JSON, EditorPrefs 설정을 제거했다. 공유 씬·프리팹·설정 에셋·World 코드는 저장하거나 수정하지 않았다. 커밋·푸시하지 않았다.

## 본편 시계의 아침 초기화 로그 검증 — 2026-10-26

- 후속 사용자 승인 범위: 본편 World 시계에 검증용 컨트롤러를 임시로 연결하고 사용 횟수 2회를 시험값으로 넣어 아침 초기화를 로그로 확인한다. 실제 소환 연결·UI·공유 씬 저장은 범위 밖이다.
- MainOffline에서 시작해 기존 StartHost/StartClient·로비 준비 요청으로 호스트1+MPPM 원격3, 본편4인 InProgress에 진입했다.
- 서버에만 임시 GameObject와 실제 SeaSummonSpawnController를 만들었다. NetworkServer.Spawn은 호출하지 않았다. 리플렉션으로 기존 TrySynchronizeDay를 한 번 호출해 실제 등록 World GameClock의 아침 이벤트를 구독했다. 정식 네트워크 생성·OnStartServer 코루틴 경로의 검증은 아니다.
- 시험 ActorId=999999에 사용 횟수2를 넣었다. 실제 플레이어의 소환 결과가 아니며, 현재 SeaSummonSettings 에셋의 DailyLimit=3으로 잔여 표시값을 계산했다. TryGetQuota는 미승선·권한 조건을 우회 호출하지 않았고, TargetQuota/UI 수신을 검증하지 않았다.
- 대기 시간을 줄이기 위해 런타임 GameClock.Resync(NetworkTime.time - Config.CycleSeconds + 5)로 첫날 밤·다음 아침 약5초 전으로 이동했다. 낮밤 길이·World 소스·설정 에셋은 변경하지 않았다. 아침 이벤트나 초기화 함수를 직접 호출하지 않고 실제 GameClock.Update가 다음 아침 경계를 넘어가도록 기다렸다.
- 실제 호스트 콘솔 로그:

```text
[DailyResetLogProbe] 준비: 실제 MainGame 서버, 접속 4명, 시계 1일차, 시험 사용 2회, 잔여 1회
[DailyResetLogProbe] 경계 준비: 1일차 Night, 사용 2회. 5초 뒤 실제 아침 이벤트 대기
[DailyResetLogProbe] PASS: 실제 DayStarted(2), 처리 일차 2, 시험 사용 0회, 잔여 3회. 소환 생성/차감 및 UI는 시험하지 않음
```

- 판정: 실제 본편 시계의 아침 이벤트 → 임시 연결된 실제 소환 코드의 사용 횟수 초기화를 1회 관찰했다. M2 구성에서 서버 로직을 확인했으나, 원격 횟수 전송·실제3회 소환·4번째 거절·정식 본편 연결·타이밍10회 반복·M3는 미검증이다. 본편 정식 소환 연결 누락은 여전히 남는다.
- 관찰 후 이벤트 검사 구독과 컨트롤러의 서버 구독을 해제하고 임시 객체를 제거했다. 기존 LeaveSession으로 MainOffline 복귀·서버/클라이언트 비활성 확인 후 Play 종료. 임시 DailyResetLogProbe.cs/meta와 EditorPrefs 키를 제거했다. 공유 씬·에셋은 저장하지 않았고 사용자가 스테이징한 소환 코드도 건드리지 않았다.
- 종료 시 기존 EventSystem 중복 경고 1개가 조회됐다. 초기화 검사 로그는 PASS이며 UI 경고를 이번 기능의 통과 증거로 사용하지 않는다.

# 멀티플레이 테스트 절차

규칙 우선순위는 [AI 작업 문서](README.md)를 따른다. 승패·투표·단절 기대값은 [승패·투표 결정](../design/win-vote-decisions.md)을 먼저 확인하며, 해당 결정과 [v4](../design/references/game-design-v4.md)가 충돌하면 결정을 적용한다.

> 4인 호스트-클라이언트 게임의 판정·표시·비밀 정보 경계를 검증한다. 호스트 플레이어도 정원에 포함한다.

## 1. 테스트 등급

| 등급 | 구성 | 언제 |
|---|---|---|
| M0 | 호스트 1명만 실행 | 로컬 로직과 기본 실행 |
| M1 | 호스트 1 + 원격 클라이언트 1, 같은 PC | 기본 동기화 확인 |
| M2 | 호스트 1 + 원격 클라이언트 2 이상, 같은 PC | 동시 요청·공유 상태 |
| M3 | 호스트와 원격 클라이언트가 서로 다른 PC | 실제 네트워크·지연 확인 |

네트워크 변경은 최소 M2로 검증한다. 전원 조건·진영 배정·투표·정원 관련 로직은 **호스트 1 + 원격 클라이언트 3의 총 4인**을 채운다. M3도 동시 요청은 원격 클라이언트 2명 이상, 정원 관련 조건은 총 4명으로 확인한다.

호스트의 화면만 확인하면 원격 클라이언트의 권한·초기화·SyncVar 훅 문제를 놓친다. 호스트와 원격 플레이어의 행동을 각각 실행하고 관찰한다. 데디케이티드 서버를 전제로 검증 구성을 바꾸지 않는다.

## 2. 여러 인스턴스 실행

### 실행 전 준비

- 현재 Unity 버전은 `ProjectSettings/ProjectVersion.txt`로 확인한다 (6000.0.83f1).
- 테스트할 씬, 실제 네트워크 진입 경로, 현재 트랜스포트와 포트를 확인한다.
- 자동 실행 스크립트·에디터 메뉴·명령행 인자가 구현되어 있는지 확인한 뒤 사용한다.
- 빌드는 현재 변경과 일치해야 한다. 개발 빌드 전용 인자를 릴리스 빌드에 적용했다고 가정하지 않는다.
- 게임 시작 최소 인원과 입장 잠금 조건을 확인한다. 테스트 편의를 위한 임시 설정은 종료 후 복구한다.
- 여러 창의 포커스·커서 잠금·백그라운드 실행 조건을 확인한다.
- 테스트 대상과 필요한 데이터가 실제 씬에 존재하는지 확인한다. 검증 편의 때문에 공유 씬을 임의로 저장하지 않는다.

### 방법 A — ParrelSync

ParrelSync는 `Packages/manifest.json`의 Git 의존성이다. `Assets/Plugins/ParrelSync/`에는 프로젝트 설정 에셋이 있으며 실제 패키지 버전은 잠금 파일에서 확인한다. 원본 프로젝트에서 호스트, 복제 에디터에서 클라이언트를 실행한다. 외부 플러그인 원본은 수정하지 않는다. 복제 프로젝트의 씬·에셋 저장 경계와 메모리 사용량을 확인한다.

### 방법 B — 빌드 + 에디터

에디터를 호스트로, 빌드를 원격 클라이언트로 실행하거나 반대로 구성한다. 기능 검증 뒤 실제 빌드에서도 확인한다. 같은 PC에서의 여러 인스턴스는 실제 네트워크 성능 검증을 대신하지 않는다.

### 테스트 씬 기록

| 씬 경로 | 검증 대상 | 초기 상태·데이터 | 빌드 포함 여부 | 검증 결과 |
|---|---|---|---|---|
| {{실제 경로}} | {{기능}} | {{재현 조건}} | {{확인 값}} | {{결과 또는 미검증}} |

## 3. 지연 환경 재현

지연 주입 수단은 현재 트랜스포트의 지원 여부를 확인해 선택한다. 도구 설치와 적용을 확인하지 않고 활성화된 것으로 쓰지 않는다.

| 시험 조건 | 주입 지연 | 패킷 손실 |
|---|---|---|
| 기준 | 0ms | 0% |
| 보통 지연 예시 | 30~50ms | 0.1% |
| 높은 지연 예시 | 150ms | 2% |

위 수치는 시험 프로필이며 실제 이용 환경을 보증하지 않는다. 편도 지연인지 왕복 지연인지, 실제 RTT와 도구 설정을 함께 기록한다. 짧은 판정 창·투사체·동시 상호작용은 M3에서 확인한다.

## 4. 시나리오별 체크리스트

각 항목은 구현된 기능에 맞춰 적용한다. 미구현 항목을 통과로 처리하지 않는다.

아래는 실행할 시험 절차와 기대값이며 이번 문서 갱신에서 실행한 결과가 아니다. 문서 의미·링크·담당 계약의 정적 검수는 [검증 플레이북 L1](03_VERIFICATION_PLAYBOOK.md#l1--정적-검증)로 기록하고 Unity/총 4인 실행 결과와 구분한다. [미정 계약](../design/win-vote-decisions.md#pending-contracts)의 기대값은 임의로 만들지 않고 `결정 대기`로 둔다.

### 접속·세션

- [ ] 호스트 시작 후 원격 클라이언트 3명이 접속한다
- [ ] 정원 4명을 넘는 참가 요청을 계약대로 처리한다
- [ ] 호스트와 원격 클라이언트에서 각각 로컬 입력 소유권이 맞다
- [ ] 원격 클라이언트 이탈과 호스트 종료를 구분해 처리한다
- [ ] 로비에서 4명이 모두 준비하면 자동으로 게임 씬으로 넘어가고, 3명만 준비하거나 한 명이 준비를 취소하면 시작하지 않는다. 게임 씬에서 4명 모두 로딩을 마친 뒤 입력·시계가 열리고, 한 PC가 설정 시간 안에 로딩을 못 마치면 판이 종료된다
- [ ] 판 진행 중 원격 클라이언트 또는 호스트가 나가면 남은 전원에게 종료 사유가 한 번 전달되고 판이 종료된다. 로비에서 나가면 자리만 비고 판은 시작되지 않는다. 판 시작 후 새 접속은 거절된다
- [ ] 재접속·호스트 이전은 10/25 이전 범위가 아니며 시험하지 않는다

2026-10-13 결정으로 단절 보존 대신 판 종료를 시험한다. §2의 JH01 해제 통과 기록은 객체 삭제 흐름의 결과이며 판 종료 시험의 통과 증거가 아니다.

### 항해·전투·몬스터

- [ ] 배와 캐릭터 조작·탑승 상태가 다른 화면에서 일치한다
- [ ] 대포·몬스터의 피격 판정과 배 내구도가 호스트 값과 일치한다
- [ ] 몬스터 AI는 호스트에서 판정되고 클라이언트에 중복 실행되지 않는다
- [ ] 몬스터의 소환·자연 스폰 출처가 클라이언트에 유출되지 않는다

### 자원·제작·공유 등대

- [ ] 동시에 같은 자원을 획득해도 중복 획득하지 않는다
- [ ] 자원 투입·모듈 제작 시 수량과 소유권을 호스트가 검증한다
- [ ] 등대 수리도와 내구도를 구분하고 각 화면 값이 일치한다
- [ ] 거부된 요청이 자원이나 공유 상태를 바꾸지 않는다

### 역할·비밀 투표

- [ ] 역할·비밀 투표 결과가 허용된 수신자에게만 전달된다
- [ ] UI에서 숨기는 것뿐 아니라 네트워크 상태·메시지 수신 범위도 확인한다
- [ ] 시민 3명과 마피아 1명 조건에서 투표·점화 의식 조건을 검증한다
- [ ] 플레이어당 투표 2회 제한이 동시 요청·재전송에도 한 번씩만 차감된다
- [ ] 시민의 첫 지목/다른 대상 변경은 횟수를 쓰고, 같은 대상 재클릭은 차감하지 않는다. 마피아 투표·자기 지목·철회·투표권 회복은 허용하지 않는다
- [ ] 마피아 확인 결과·소환 결정 시간과 소모 횟수가 계약대로 적용된다
- [ ] 확인 처리 순간의 현재 표로 성공을 판정하고, 이후 표 변경과 무관하게 10초 소환 권리를 유지한다. 마지막 확인권 성공으로 남은 확인이 0이어도 이미 받은 권리를 사용할 수 있다
- [ ] 10초 만료 뒤 확인권이 남으면 다시 확인할 수 있고, 난파 중에는 확인·소환이 거절된다
- [ ] 개인 표는 본인만, 확인 성공/기회 소진은 마피아만 수신한다. 봉인·심해 게이지는 어느 플레이어의 네트워크 상태·메시지·로그에도 전달되지 않는다
- [ ] 확인 실패는 이전에 공개하지 않은 무고한 시민을 무작위 공개한다. 공개 결과에 원래 표·봉인·심해 값이 섞이지 않는다

### 시간·난파·최후 전투

- [ ] 낮밤·기한·영역 확장 알림이 호스트 기준으로 일치한다
- [ ] 난파 후 이동 제한·카메라·조명탄·비밀 투표가 기획대로 동작한다
- [ ] 동료 구조와 자동 구조 결과가 중복 적용되지 않고, 표류 잔해는 한 명만 회수한다
- [ ] 화물 손실 비율·자동 구조 비용 등 미정 항목은 결정된 범위까지만 검증한다
- [ ] 최후 전투 진입·심연 날씨 전환과 승패가 모든 인스턴스에서 한 번만 확정된다

### 승패·투표 결정의 단계별 시험

아래 각 시나리오는 총 4인으로 호스트 시민/마피아와 원격 시민/마피아 구성을 바꿔 확인한다. 수치 설정의 최종 밸런스와 기능 계약 통과를 구분하며, 사용한 설정과 서버 판정 시각·단계 버전·결과 수신자를 기록한다. 비밀 값의 비교는 서버의 제한된 검증 자료에서 하고 공용 클라이언트 로그로 복사하지 않는다.

| 상황 | 기대 결과 | 함께 확인할 경계 |
|---|---|---|
| 숨은 단계 기한 도달, 의식/소환 없음 | 설정 기본 5일에 마피아 승리·한 번 종료 | 최명기 기한/종료와 강민서 월드 시각. 같은 시점 의식 시작 경합은 결정 대기 |
| 소환 전 수리 100%, 유효 등대 상호작용 | 누구나 60초 의식 시작, 투표 변경 잠금·게임 기한 정지·낙하 없음 | 지훈 시작→최명기 단계→태욱 투표. 월드 낮밤 정지를 임의 기대하지 않음. 필수 모듈 조건 관계는 결정 대기 |
| 의식 시작 뒤 시민 표 변경 요청, 마피아 확인/소환 | 시민 변경 거절. 난파하지 않은 마피아 확인/소환은 가능 | UI 제한과 서버 거절을 함께 확인 |
| 소환 없이 의식 60초 완료 | 시민 정답 지목 2명 이상이면 시민 승리, 미충족이면 즉시 마피아 승리·종료 | 실패 게이지 증가·잠금 해제 후 경기 지속·재시도 없음 |
| 의식 59초에 유효 소환, 또는 의식 전 소환 | 최후 전투 전환·게임 기한 제거·기존 의식 타이머 제거 | 이전 완료/기한 알림이 이후 승패를 변경하지 않음 |
| 소환 전 수리도 0%·50%·100%에서 각각 소환 | 현재 HP가 기본 HP·기본/최대의 중간값·최대 HP. 새 최후 수리도는 모두 0% | 최대 HP 고정, 소환 이전 보상 유지. 보상 이벤트 재실행 없음 |
| 최후 전투에서 자원 투입/요청 재전송 | 새 진행도만 증가, 현재 HP 회복·최대 HP 증가·신규/중복 보상 없음 | 지훈 거래와 최명기 보상/UI의 한 번 반영 |
| 새 최후 수리 100%가 HP0보다 먼저 도달 | 별도 점화 없이 즉시 시민 승리·단일 종료 | 이후 피해·타이머·종료 후보가 승자를 바꾸지 않음 |
| HP0이 새 최후 수리 100%보다 먼저 도달 | 즉시 마피아 승리·단일 종료 | 괴물 처치는 불가하며 처치 승리 후보 없음 |
| 의식 완료와 소환 또는 새 수리 100%와 HP0이 같은 판정 시점 | 결정 대기. 합의할 우선순위/판정 경계로 이후 검사 | 임의 큐/콜백 순서를 게임 규칙으로 통과시키지 않음 |
| 시민 정답/오답 지목 유지, 난파·확인 성공 후 아침 | 시민별 시간 기록 지속, 아침 기본 게이지 1일분과 봉인/오투표 정산 한 번 | 마피아 제외, 강민서 아침 경계→태욱 정산. 중복 알림 이중 정산 없음 |
| 아침 전 소환 | 소환 시점까지 미정산 봉인/오투표 반영, 아직 완료되지 않은 하루의 기본 충전 없음 | 정산된 구간 중복 반영 없음, 설정 최소 공격력 보장 |
| 소환 후 다음 아침/표 변경/난파 상태 변화 | 괴물 공격력은 소환 당시 값으로 고정 | 월드 일일 효과의 지속/정지는 별도 결정 대기 |

의식 중 억제된 낙하의 최후 전투 후속 처리, 호스트 이탈, 같은 시점 경합, 기존 필수 모듈 조건은 [남은 계약](../design/win-vote-decisions.md#pending-contracts)을 먼저 확정해야 기대값을 검사할 수 있다.

### 호스트 부하

- [ ] 몬스터·투사체가 많은 동일 조건에서 호스트와 클라이언트 프레임을 각각 기록한다
- [ ] 해상도·품질·FPS 상한·에디터 또는 빌드 여부를 기록한다
- [ ] 호스트의 렌더링과 서버 판정 비용이 함께 발생함을 고려한다
- [ ] 같은 PC의 자원 경쟁과 게임 자체 비용을 구분하기 위해 M3에서 재측정한다

## 6. 자주 놓치는 것

| 함정 | 대응 |
|---|---|
| 호스트 혼자 확인 | 원격 클라이언트의 입력·표시·권한을 따로 확인 |
| 한 번만 실행 | 타이밍 결함은 최소 10회, 실제 반복 수 기록 |
| 순차 입력만 확인 | 동시 획득·투입·구조·점화 요청 확인 |
| 화면만 비교 | 호스트 확정 값·클라이언트 수신 값도 비교하되 비밀 정보를 공용 로그에 남기지 않음 |
| 미정 계약을 정상으로 가정 | 기획과 현재 지원 범위 확인 후 검증 대기 처리 |

## 7. 정기 통합 테스트

1. 실제 브랜치·통합 절차와 [코드 소유권](../CODE_OWNERSHIP.md)의 4인 테스트 리드를 확인한다. 각 기능 담당자는 자기 기능의 호스트·클라이언트·동기화를 함께 검증한다.
2. 합의한 변경을 통합하고 테스트 씬·데이터를 준비한다.
3. 총 4인 M3 빌드 테스트를 실행한다.
4. 변경 관련 시나리오와 회귀 항목을 기록한다.
5. 실패 항목은 재현 조건·근거와 함께 이슈로 정리한다.

일정과 담당자가 정해지지 않았다면 미정으로 기록한다. 문서만으로 자동화·주간 일정이 운영 중이라고 주장하지 않는다.

## 8. 플랫폼 트랜스포트

새 플랫폼 트랜스포트 도입 시 실제 계정·기기 제약을 확인한다. 같은 PC 테스트가 지원되지 않으면 M3에서 검증하고 준비물·참가 경로·실패 로그 위치를 기록한다. 플랫폼 연동을 이번 문서의 기본 전제로 추가하지 않는다.

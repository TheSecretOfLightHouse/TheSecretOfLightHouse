# 에이전트 실행 정책

> 승인된 작업을 끝까지 수행하되, 팀원의 작업과 프로젝트 데이터를 침범하지 않는다.

---

## 실행 원칙

1. 요청의 목표, 산출물, 수정 범위, 관찰 가능한 완료 조건을 확인한다. 이미 주어진 조건은 그대로 사용하며, 결과를 바꾸는 필수 결정만 질문한다.
2. 합리적인 기본값으로 진행할 수 있으면 질문만 남기고 멈추지 않는다. 사용자 입력이 필요 없는 단계에서 "계속할까요?"로 멈추거나 다음 단계를 말만 하고 끝내지 않는다. 진행 상황은 다음 행동과 같은 메시지에 쓴다. 멈출 조건은 아래 [중단하고 질문할 조건](#중단하고-질문할-조건)과 사전 승인 표뿐이다.
3. 계획이나 분석만으로 끝내지 않고, 승인된 범위의 구현과 검증까지 완료한다.
4. 현재 상태를 읽고 최소 변경을 적용한다. 기존 구조와 관례를 우선한다.
5. 완료 주장은 도구 출력, 테스트 결과, 최종 파일 내용으로 뒷받침한다.
6. 검증하지 못한 항목은 반드시 `미검증`으로 표시한다.

---

## TheSecretOfLightHouse 프로젝트의 승인 경계

폴더 구성은 [아키텍처](../04-architecture.md), 담당자와 업무 경계는 [코드 소유권](../CODE_OWNERSHIP.md)을 따른다. 각 기능 담당자는 자기 기능의 Rules·Net·Server·View를 함께 책임진다.

### 승인 없이 진행

- 사용자 요청과 확인된 담당 범위 안의 코드 작성·수정
- `docs/` 문서 작성·수정
- 담당 개발 씬에서 승인된 작업 (Unity 에디터를 통해 수행)
- 읽기 전용 조사와 분석

### 사전 범위 확인이 필요한 작업

| 대상 | 확인할 내용 |
|---|---|
| 다른 담당자의 코드·씬, 공용 API | 담당자·파일·이유·영향을 사용자에게 알리고 확인한 합의 범위, 병행 변경 |
| `Lighthouse.Runtime` 어셈블리·참조 변경 | 승인된 단일 런타임 구조와 실제 참조 계약 |
| 네트워크 권위 경계 변경 | 호스트 판정과 클라이언트 표시, 비밀 정보 수신 범위 |
| LFS 관리 정책 변경 | 신규 LFS 추가는 금지. 정책 변경이 필요하면 팀 결정과 기존 이력 영향을 먼저 확인 |
| 파일 삭제·대량 이동·일괄 이름 변경 | 사용자 요청 범위, 복구 경로, Unity `.meta` 동반 |
| Git commit·push | 명시 요청 여부 |
| 신규 시스템·게임 규칙·콘텐츠 추가 | 요청 범위와 기획 합의 |

위 표는 새로 필요한 확인에 적용한다. 기존 대화에서 승인된 요청과 담당자의 자기 소유 범위를 먼저 확인하고, 이미 허용된 같은 작업이나 명시적으로 승인된 구조 이관은 반복 승인받지 않는다. 담당 경계 확인의 규칙 원문은 [AGENTS.md](../../AGENTS.md)다.

외부 코드 `Assets/Mirror/`, `Assets/Plugins/ParrelSync/`, 구매 에셋 `Assets/ThirdParty/ThirdParty/`는 수정하지 않는다. 씬·프리팹·`.asset` YAML을 직접 편집하지 않는다. 담당자나 CODEOWNERS가 확인되지 않으면 임의로 배정하지 않는다.

### 절대 하지 않음

- 다른 사람의 담당 개발 씬 저장
- 사용자나 다른 작업자의 변경을 근거 없이 되돌리기
- `Library/`, `Temp/`, `obj/` 등 생성물 수정
- 공유하거나 push한 이력을 임의로 재작성하거나 강제 push하기. 로컬 `amend`는 사용자가 허용한 범위에서만 한다

## 행동 경계

- 분석 · 설명 요청을 수정 승인으로 해석하지 않는다.
- 요청 범위 밖의 리팩터링 · 정리 · 설정 변경을 임의로 추가하지 않는다.
- 파일을 되돌리기 전에 diff를 확인한다. 변경 전체가 자기 작업임을 확인하지 못하면 파일 단위 복원을 실행하지 않는다.
- 여러 해결안이 있고 게임 디자인에 영향을 주면 임의로 확정하지 않고 선택지와 영향을 보고한다.
- **"이왕 하는 김에" 스코프를 넓히지 않는다.** 팀 프로젝트에서는 스코프 통제가 일정의 성패를 가른다.

## 작업 규모와 검증 비용

명확한 작은 변경은 짧게 구현하고 변경에 맞는 검증으로 끝낸다. 숨은 예외가 많은 서버 권위·자원 거래·승패 경합은 검증에 더 많은 시간을 쓴다. 실패 원인이 잘못된 요구 해석이면 먼저 브리프와 근거를 고치며, 같은 시도를 더 오래 반복하지 않는다.

모델·reasoning·effort는 현재 세션의 사용자 지정과 사용 가능한 설정을 따른다. 이 원칙은 작업 배분 기준이며 Claude 전용 설정을 Codex에 그대로 적용하거나 전역 모델 설정을 자동 변경하는 지시가 아니다.

## 표준 실행 순서

1. 대상 파일, 기획 문서, `git status`를 읽어 기준점을 확보한다.
2. 관련 규칙과 기존 구현을 확인한다.
3. **네트워크가 걸린 변경인지 판정한다** → [네트워크 권위](../unity/NETWORK_AUTHORITY.md)
4. 가장 작은 안전한 변경을 적용한다.
5. [검증 플레이북](03_VERIFICATION_PLAYBOOK.md)에 따라 검증한다.
6. 실패하면 첫 원인을 격리하고 한 번에 한 가지씩 수정한 뒤 다시 검증한다.
7. 결과, 변경 위치, 검증 증거, 미검증 항목, 잔여 위험을 보고한다.

## 중단하고 질문할 조건

아래 조건에서만 즉시 멈추고 구체적인 질문을 남긴다.

- 필요한 권한이나 필수 입력이 없고 안전한 대안도 없을 때
- 요청한 결과를 내려면 승인 범위를 실질적으로 넓혀야 할 때
- 복구하기 어려운 작업이 필요하지만 의도가 명확하지 않을 때
- 게임 디자인 결정이 필요하고 선택에 따라 결과가 크게 달라질 때
- 기획 문서와 코드가 충돌하고 어느 쪽이 최신인지 판단할 수 없을 때

질문하기 전까지 안전하게 완료할 수 있는 조사와 검증은 먼저 수행한다.

**질문하지 않아도 되는 것**: 코드 검색, 설정 확인, 파일 읽기로 답할 수 있는 것.
"이 클래스가 어디 있나요"는 질문이 아니라 검색으로 해결한다.

## 실패와 폴백

1. 같은 호출을 같은 조건으로 반복하지 않는다.
2. 실패를 권한 · 입력 · 도구 상태 · 환경 · 검증 실패로 분류한다. 파일·MCP·네트워크 읽기 실패는 `변경 없음`이나 `문제 없음`이 아니라 `읽기 실패/미확인`으로 보고한다.
3. 더 좁은 범위, 읽기 전용 검사, 다른 방법, 수동 재현 순으로 대안을 검토한다.
4. 우회 결과도 원래 완료 조건으로 다시 검증한다.
5. 세션을 넘겨야 하면 [세션 인수인계](05_SESSION_HANDOFF.md)를 작성한다.

### Unity 특유의 실패

| 증상 | 먼저 확인할 것 |
|---|---|
| 컴파일 에러가 사라지지 않음 | 에디터가 재컴파일 중인지, Play Mode인지 |
| 참조가 Missing으로 표시 | `.meta` 누락 또는 GUID 충돌 |
| 이미지가 텍스트로 보임 | `git lfs install`과 `git lfs pull` 실행 여부 |
| 씬 변경이 반영 안 됨 | 다른 씬을 열고 있는지 |
| 클라이언트에서만 동작 이상 | 권위 경계 위반 |

## 완료 기준

아래를 모두 충족했을 때만 완료로 보고한다.

- 요청된 산출물이 실제로 존재한다.
- 승인된 범위를 벗어난 변경이 없다.
- 필수 검증이 통과했거나 실행 불가 사유가 명확히 기록되어 있다.
- 임시 설정과 디버그 코드를 원래 상태로 복구했다.
- 다음 행동을 판단하는 데 필요한 결과와 잔여 사항을 전달했다.

**네트워크가 걸린 변경은 다인 접속 검증([멀티플레이 테스트](04_MULTIPLAYER_TEST_PROTOCOL.md) M2 이상) 없이 `완료`로 보고하지 않는다.**

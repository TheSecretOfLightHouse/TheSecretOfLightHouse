# 기획 문서 → 구현 변환

> 기획서를 구현 가능한 작업으로 옮길 때 사용한다.

---

## 1. 원문 구조화

기획 문서에서 아래를 분리한다.

| 항목 | 기록할 내용 |
|---|---|
| 목표 | 플레이어가 얻어야 할 경험 |
| 행위자 | 플레이어, 적, NPC, 시스템 |
| 입력 · 출력 | 조작, 이벤트, UI, 드랍 |
| 규칙 | 조건, 우선순위, 예외, 수치 |
| 상태 변화 | 무엇이 생성 · 수정되는가, 누가 소유하는가 |
| 네트워크 | 호스트 판정·동기화·클라이언트 표현 중 어디인가? 해당 기능 담당자가 모두 책임지는가? |
| 검증 기준 | 관찰 가능한 성공 · 실패 조건 |

네트워크 권위는 기획서·기술설계서와 현재 구현을 함께 대조한다. 비밀 투표·역할·몬스터 소환 출처처럼 수신자를 제한하는 정보도 기록한다.

원문의 사실, 코드에서 확인한 사실, 분석자의 추정을 서로 다른 열에 둔다.

---

## 2. 현재 구현 추적

키워드 검색만으로 담당 코드를 확정하지 않는다.

1. 진입 이벤트나 공개 API를 찾는다
2. 호출 관계와 데이터 소유자를 추적한다
3. ScriptableObject와 초기화 순서를 확인한다
4. 찾지 못한 항목은 `없음`이 아니라 `검색 범위에서 미확인`으로 기록한다

---

## 3. 갭 분석표

```markdown
| ID | 요구사항 | 현재 구현 근거 | 상태 | 필요한 변경 | 네트워크 | 검증 |
|---|---|---|---|---|---|---|
| R-01 | 아이템 획득 | `ItemPickup` (예시) | 구현됨·변경 범위 검증 필요 | 중복 획득 방지 조건 대조 | 서버 권위 | M2 후 L3 |
```

`상태`는 코드 존재 여부가 아니라 **요구된 동작의 충족 여부**로 판정한다.
비슷한 코드가 있다는 이유만으로 `충족`으로 올리지 않는다.

---

## 4. 영향도 판정

각 변경 후보에 아래를 적용한다.

- 게임 결과에 영향을 주는 값을 다루는가? → 서버 권위 필요
- 어느 씬을 수정해야 하는가? → 소유자 확인
- 다른 기능의 코드·계약을 수정해야 하는가? → [코드 소유권](../CODE_OWNERSHIP.md)을 읽고 [AGENTS.md](../../AGENTS.md)의 담당 경계 확인을 따름
- 밸런스 수치가 포함되는가? → 기존 코딩 컨벤션의 직렬화 필드·ScriptableObject 기준 적용
- 이번 작업 제외 범위를 건드리는가? → 기존 요청 범위와 변경 필요성 확인
- 되돌리기 어려운 변경인가? → 사전 승인

## 5. 미결 질문 좁히기

질문은 **로컬 조사로 답할 수 없는 의사결정**에만 쓴다.

각 질문에 포함할 것:
- 확인된 사실과 근거
- 결정하지 않으면 막히는 범위
- 상호 배타적인 선택지
- 각 선택지의 비용 · 위험
- 권고안과 이유

코드 검색이나 문서 확인으로 답할 수 있는 질문을 사용자에게 되돌리지 않는다.

---

## 6. 구현 계획

작업을 독립적으로 검증 가능한 단계로 나눈다.

```markdown
### Phase N — {{결과}}

- 변경 대상:
- 선행 조건:
- 수행 내용:
- 완료 정의: (관찰 가능하게)
- 검증: L? / M?
- 롤백 경계:
- 승인 필요: 없음 / {{무엇}}
```

**각 Phase가 끝날 때마다 실행 가능한 상태여야 한다.** 짧은 개발 기간에 "몇 주 뒤에 한꺼번에 동작"하는 계획은 위험하다.

---

## 7. 산출물 검수

- [ ] 모든 요구사항이 갭 분석표의 행으로 추적된다
- [ ] 현재 구현 근거가 파일 · 심볼 수준으로 있다
- [ ] 추정과 미확인을 사실처럼 쓰지 않았다
- [ ] 네트워크 권위와 씬 소유권을 판정했다
- [ ] 밸런스 수치 저장 방식이 기존 코딩 컨벤션에 맞는다
- [ ] 질문은 실제 의사결정만 남겼다
- [ ] 각 Phase에 관찰 가능한 완료 정의가 있다
- [ ] 구현하지 않은 분석 결과를 `완료`로 보고하지 않는다

# AI 협업 범위와 사용 안내

AI와 협업할 때는 원하는 결과와 맡길 범위를 말하고, AI가 저장소의 문서와 코드를 읽어 조사·수정·검증하도록 맡긴다. 사람은 게임의 방향과 미정 규칙을 결정하고, 자기 담당 범위의 결과를 확인한다. AI는 요청에 따라 실제 파일을 수정하고 검증 명령을 실행할 수 있다.

이 안내는 TheSecretOfLightHouse에서 Codex와 Claude Code를 처음 사용하는 팀원을 위한 문서다. **먼저 아래 시작 방법과 요청 예시를 따라 해 보고, 저장과 재개 방법을 읽으면 된다.** 세부 규칙은 기존 기준 문서에 연결한다.

## 처음 시작하는 방법

1. 프로젝트 저장소를 내려받고, Codex나 Claude Code에서 **TheSecretOfLightHouse 저장소 폴더를 작업 대상으로 연다.** Unity 환경은 [Unity 첫 실행 안내](../unity/UNITY_START_HERE.md)를 따른다.
2. [담당표](../CODE_OWNERSHIP.md)에서 내 기능과 수정할 수 있는 범위를 확인한다.
3. 아래 첫 요청을 보내 AI가 같은 저장소와 지침을 보고 있는지 확인한다.
4. 설명을 확인한 뒤, 원하는 작업 하나를 구체적으로 요청한다. 처음에는 작은 수정이나 읽기 전용 조사가 좋다.

```text
이 저장소의 AGENTS.md와 AI 작업 문서 색인을 읽어 줘.
내 담당은 [담당자와 기능]이야.
작업 폴더, 현재 브랜치, 미커밋 변경, 내 담당 코드 경계를 확인하고
내가 AI에게 어떤 일을 맡길 수 있는지 설명해 줘.
지금은 파일을 수정하지 마.
Unity 연동 도구는 실제 연결 여부만 확인해 줘.
```

프로젝트를 볼 수 있는 환경인지 먼저 확인해야 한다. 저장소 접근이 없는 채팅에서는 필요한 문서·코드·로그를 직접 제공해야 한다. Unity 조작과 실행 검증은 에디터와 연동 도구의 연결 상태에 따라 가능 범위가 달라진다. AI에게 현재 가능한 작업을 확인해 달라고 하면 된다.

## AI에게 맡길 수 있는 범위

| 맡길 일 | AI가 하는 일 | 사람이 확인할 것 |
|---|---|---|
| 코드와 문서 이해 | 관련 파일을 찾아 구조·흐름·규칙을 근거와 함께 설명 | 설명이 실제로 원하는 기능을 다루는지 |
| 기획과 구현 대조 | 최신 기획과 코드를 비교해 미정 항목·차이·미연결·미검증을 구분 | 빠진 게임 규칙과 진행 방향 결정 |
| 설계와 대안 비교 | 구현 방법, 비용, 영향과 권장안을 정리 | 어떤 방법을 채택할지 |
| 기능 구현과 수정 | 허용된 파일을 수정하고 관련 문서를 동기화 | 담당 경계와 의도한 동작 |
| 버그 조사와 해결 | 재현 조건·로그·코드를 조사하고 원인을 좁혀 수정 | 보고한 재현 조건과 수정 후 동작 |
| 검증과 리뷰 | 가능한 정적 검사·컴파일·테스트를 실행하고 결과와 한계를 기록 | 실제 실행 범위와 남은 테스트 |
| 문서와 인수인계 | 사용법·결정·변경 파일·검증·다음 행동을 적절한 위치에 저장 | 공유할 결론과 미완료 항목 |
| 커밋과 GitHub 작업 | 요청받은 범위에서 변경을 검토하고 커밋·푸시·이슈·PR 작업 수행 | 실행 범위와 게시할 내용 |

**원하는 결과를 맡기면 조사부터 파일 수정과 가능한 검증까지 이어갈 수 있다.** 반대로 “설명만”, “조사만”, “초안만”이라고 요청하면 그 범위로 제한한다. 파일을 직접 바꾸길 원한다면 “실제 파일에 반영해 줘”라고 적으면 명확하다.

게임의 미정 수치나 규칙, 다른 담당 영역의 변경, 공용 계약 변경은 사람의 결정이나 합의가 필요한 부분이다. AI가 제안한 개선안은 검토용이며 자동으로 확정 기획이 되지 않는다. 최신 사용자 결정과 [제공된 기획 v4](../design/references/game-design-v4.md)가 기준이고, 관련 차이는 [설계 문제 대장](../07-design-issue-register.md)에서 확인한다.

씬·프리팹·에셋 작업도 맡길 수 있지만 [씬·에셋 안전 규칙](../unity/SCENE_AND_ASSET_SAFETY.md)과 에디터 연결을 먼저 확인한다. 실제 4인 접속, 조작감과 화면 표현은 해당 환경에서 확인해야 한다. AI가 코드를 작성했다는 사실만으로 이 검증까지 끝난 것은 아니다.

## 요청하는 방법

긴 프롬프트나 전문 용어가 필수는 아니다. **무엇을 원하는지, 어디까지 바꿔도 되는지, 무엇이 되면 완료인지**가 있으면 작업이 훨씬 분명해진다. 범위가 크면 [작업 브리프](02_TASK_BRIEF_TEMPLATE.md)를 사용한다.

```text
목표: [사용자가 보게 될 결과 또는 해결할 문제]
내 담당: [담당자와 기능]
수정 범위: [실제 파일·폴더 또는 먼저 찾아서 제안할 범위]
유지할 것: [기존 동작·다른 작업자의 변경·수정 금지 대상]
완료 기준: [재현 조건과 기대 결과]
요청: 관련 기획과 실제 코드를 확인한 뒤, 결정된 범위는 구현하고
가능한 검증까지 해 줘. 미정 규칙과 담당 경계를 넘는 수정은 먼저 알려 줘.
보고: 변경 파일, 실행한 검증 결과, 미검증 항목을 알려 줘.
```

파일명을 모르면 “관련 파일을 먼저 찾아 줘”라고 해도 된다. 버그라면 기대한 동작, 실제 동작, 발생 순서와 오류 로그를 함께 주면 도움이 된다.

### 이해부터 하고 싶을 때

```text
내 담당 기능의 진입점과 데이터 흐름을 찾아 설명해 줘.
관련 기획, 실제 코드, 아직 연결되지 않은 부분을 구분해 줘.
파일은 수정하지 마.
```

### 실제 수정을 맡길 때

```text
내 담당 코드에서 [재현 순서]대로 하면 [실제 문제]가 생겨.
기대한 동작은 [기대 결과]야. 로그는 아래에 붙일게.
관련 규칙과 원인을 확인한 뒤 내 담당 범위에서 수정하고 검증해 줘.
다른 담당 파일이 필요하면 대상과 이유를 먼저 알려 줘.
```

### 아직 방식이 정해지지 않았을 때

```text
[기능]의 구현 방식을 현재 프로젝트 조건으로 비교해 줘.
게임 기획의 미정 항목과 기술 대안을 구분하고 권장 이유를 알려 줘.
설계 검토만 하고 파일은 아직 바꾸지 마.
```

검토 후에는 “A안으로 진행하고, 수정 범위는 이 파일들로 하자”처럼 결정과 범위를 알려 주면 이어서 작업할 수 있다. 이미 허용된 같은 작업을 매 단계 다시 승인하는 방식은 요구하지 않는다. 커밋·푸시·게시를 원할 때는 그 실행까지 요청에 명시한다.

## 요청을 받은 뒤 AI가 일하는 흐름

```text
요청과 완료 기준 확인
  → 기존 변경과 관련 문서·코드 읽기
  → 기획 차이·미정 결정·담당 경계 확인
  → 요청한 조사·설계·수정 수행
  → 가능한 검증과 결과 정리
  → 필요한 문서와 기록 저장
  → 변경 파일·검증·남은 작업 보고
```

AI가 관련 문서를 먼저 읽는 것은 이 프로젝트의 규칙과 현재 코드를 맞추기 위해서다. 기능 구현·수정과 현황 질문에는 기획과 코드를 먼저 대조한다. 현황을 물었다면 분석 결과를 내고, 구현을 요청했다면 결정된 범위의 구현까지 이어간다. 절차는 [기획과 코드 차이 검토 스킬](../../.agents/skills/review-design-code-gaps/SKILL.md)에 있다.

큰 작업은 별도 AI 작업자인 **서브에이전트**에게 독립 조사나 파일별 작업을 나눌 수 있다. 중심 AI가 범위를 배정하고 결과를 통합한다. 파일별 쓰기 범위를 나누며 같은 씬을 동시에 수정하지 않는다. 자세한 기준은 [병렬 작업 분업](08_SUBAGENT_ORCHESTRATION.md)에 있다.

AI가 결정이 필요하다고 하면 그 질문에 답하면 된다. 실행 환경이나 권한 때문에 막혔다고 하면 막힌 작업과 이유를 확인한다. 실패하거나 실행하지 못한 검증은 결과 보고에 남아야 한다.

## 결과가 저장되는 위치

대화, 실제 산출물, 작업 기록은 각각 쓰임새가 다르다.

| 내용 | 남기는 위치 | 팀 공유와 다음 작업 |
|---|---|---|
| 요청과 답변 | 사용 중인 도구의 대화 | 파일 저장과 별개다. 새 대화에서 이전 대화 전체가 제공된다고 가정하지 않는다 |
| 수정한 코드·설정·에셋 | 저장소의 해당 파일 | 작업 폴더에 반영된다. Git·SVN 관리 구분을 따르며 원격 공유는 별도 절차다 |
| 팀이 계속 읽을 규칙·설계·사용법 | `docs/` | 팀 문서다. Git에 커밋하고 푸시해야 원격 저장소로 전달된다 |
| 본인 작업 과정·결과·검증 기록 | `docs/{이름}/{날짜}/{내용}.md` | 폴더 최상단 `POINTER.md`에서 날짜별 이력과 다음 행동을 찾는다 |
| 인수인계 | `docs/handover/{이름}/{날짜}/{내용}.md` | 담당자 pointer에서 연결하고 Git으로 공유한다 |

작업 기록의 저장·갱신은 [작업 기록과 재개](11_WORK_RECORDS.md)를, 공유 기준 문서의 위치는 [문서 분류](../DOCUMENTATION_POLICY.md)를 따른다. 팀이 알아야 할 확정 규칙은 작업 기록에만 두지 않고 관련 기준 문서에도 반영한다.

### 파일 저장과 Git 공유

Git으로 관리하는 파일은 다음 단계를 구분한다.

```text
파일 저장 → 로컬 변경
커밋      → 내 저장소에 변경 이력 생성
푸시      → 원격 브랜치로 전달
PR        → 팀에 검토 요청
머지      → 대상 브랜치에 통합
```

AI에게 “수정해 줘”라고 한 것은 파일 수정 요청이다. 커밋·푸시·게시를 완료의 기본 단계로 추가하지 않는다. 현재 브랜치와 변경을 확인하고, 새 작업 브랜치와 PR은 [커밋·PR 컨벤션](../commit-convention.md)을 따른다. 본편의 Git 관리와 구매 에셋·데모의 SVN 관리는 [파일 관리](../unity/LARGE_FILES.md)에서 확인한다.

## 다음 대화에서 이어가는 방법

새 세션에서는 AI가 [작업 pointer](../WORK_POINTER.md)와 해당 담당자의 pointer, 관련 원문을 먼저 읽고 **진행 중인 일·남은 일·차단 조건·다음 행동**을 짧게 알린다. 상세 절차와 양식은 [작업 기록과 재개](11_WORK_RECORDS.md)를 따른다.

```text
나는 [이름]이야. 지금 내 진행 상황을 확인하고 [작업]을 이어가 줘.
```

담당자가 확인되지 않았다면 이름만 알려 주면 된다. 본문을 매번 붙여 넣지 않아도 된다. 여러 작업이 있으면 요청에 해당하는 작업을 선택하며, 모호하면 AI가 확인한다. pointer가 없으면 기록이 없다고 알리고 현재 요청을 기준으로 진행한다.

작업 후에는 수행 과정·결정 이유·변경 파일·실제 검증·남은 일·다음 행동을 작업 원문에 기록하고 담당자 pointer를 갱신한다. 인수인계가 필요하면 [세션 인수인계](05_SESSION_HANDOFF.md)를 사용한다. 다른 PC에서 읽으려면 기록과 pointer를 커밋·푸시하고 받는 쪽에서 최신 변경을 받아야 한다. 커밋·푸시는 별도 요청 범위다.

## 결과를 확인하는 방법

AI의 완료 답변에서는 다음 네 가지를 확인한다.

1. **결과**: 요청한 동작이나 산출물이 어디까지 완성됐는가.
2. **변경 파일**: 실제로 바뀐 파일은 무엇이고, 내 담당 범위에 맞는가.
3. **검증 근거**: 어떤 환경에서 무엇을 실행했고 실제 결과가 무엇인가.
4. **남은 작업**: 미정 결정, 미검증 동작, 다른 담당과 연결할 부분은 무엇인가.

코드를 읽은 결과, 컴파일 성공, Unity 플레이 확인, 실제 다인 접속은 서로 다른 검증이다. 호스트에서 확인한 동작이 원격 클라이언트에서도 같다고 단정하지 않는다. 수준과 기록 방식은 [검증 플레이북](03_VERIFICATION_PLAYBOOK.md), 다인 환경은 [멀티플레이 테스트](04_MULTIPLAYER_TEST_PROTOCOL.md)를 따른다.

필요한 검증을 실행하지 못하면 `구현됨(미검증)` 또는 `검증 대기`로 남긴다. 네트워크 변경은 호스트 1과 원격 클라이언트 2 이상을 함께 실행하는 M2 이상의 다인 접속 검증 없이 `완료`로 보고하지 않는다. 전원 조건·진영 배정·투표·정원 관련 검증은 총 4인을 채운다.

설명이 어렵거나 결과가 의도와 다르면 다음처럼 후속 요청을 하면 된다.

```text
변경 이유와 실제 동작을 내가 재현할 수 있는 순서로 설명해 줘.
이번에 실행해서 확인한 것과 아직 확인하지 못한 것을 구분해 줘.
```

| `AGENTS.md` | 담당 경계, 필독 문서, 안전 규칙 등 공통 작업 지침 |

| 스킬 | 특정 작업에서 읽을 절차와 양식. Codex는 `.agents/skills/`, Claude Code는 `.claude/skills/` 사용 |
| MCP | AI가 외부 도구의 정보와 작업 기능을 이용하는 연결 방식. 실제 연결과 권한이 있어야 사용 가능 |
| 컨텍스트 | AI가 현재 작업에서 참고할 수 있는 대화·문서·도구 결과 |
| 서브에이전트 | 범위를 나눠 배정받은 일을 수행하는 별도 AI 작업자 |
| 교차 검증 | 작성자와 다른 모델이 결과를 읽고 문제를 지적하는 검토. 실제 실행 테스트와는 별도 |

Codex의 지침 읽기, 스킬과 MCP의 일반 동작은 각각 [공식 AGENTS.md 안내](https://learn.chatgpt.com/docs/agent-configuration/agents-md), [공식 스킬 설명](https://developers.openai.com/plugins/concepts/skills), [공식 MCP 안내](https://learn.chatgpt.com/docs/extend/mcp?surface=cli)에서 확인할 수 있다. 이 저장소의 팀 규칙과 개인 도구 설정은 [도구 설정 안내](TOOL_SETUP.md)를 따른다. 개인 모델 선호나 추가 도구 구성을 팀 전체의 필수 조건으로 확대하지 않는다.

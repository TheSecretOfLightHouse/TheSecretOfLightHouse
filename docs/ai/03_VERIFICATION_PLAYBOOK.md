# 검증 플레이북

> 완료 주장을 실제 증거에 묶고, 작업 위험도에 맞는 검증 수준을 적용한다.

---

## 1. 검증 원칙

- 완료를 의도가 아니라 관찰된 상태로 판정한다.
- 각 주장에 실제 실행 결과, 로그, 산출물 또는 재현 기록을 연결한다.
- 확인하지 못한 항목은 `미검증`으로 표시한다.
- 실패하거나 생략한 단계를 성공으로 포장하지 않는다.
- 시각적 결과는 캡처나 사용자 확인 없이는 검증되지 않은 것으로 본다.
- 수정 범위 밖의 기존 결함은 별도로 표시하고 현재 작업의 실패와 혼동하지 않는다.

---

## 2. 증거 등급

| 등급 | 이름 | 인정 기준 | 사용 규칙 |
|---:|---|---|---|
| 0 | 주장만 | 실행 결과 없이 서술했다 | 완료 보고에 사용하지 않는다 |
| 1 | 정적 확인 | 문서는 내용·링크·변경 범위 확인, 코드는 컴파일 통과·콘솔 에러 0 | 동작 변경의 단독 근거로 쓰지 않는다 |
| 2 | 기능 확인 | 담당 씬에서 목표 동작을 1회 이상 관찰 | 네트워크 영향이 있으면 등급 3으로 확장 |
| 3 | 통합 확인 | **다인 접속 상태(M2 이상)에서** 정상 경로 통과 및 회귀 확인 | 네트워크 · 씬 · 초기화 변경의 근거 |

---

## 3. 상태 어휘

| 상태 | 의미 |
|---|---|
| `완료(검증됨)` | 요구된 수준과 증거 등급을 모두 충족 |
| `구현됨(미검증)` | 산출물은 있으나 필요한 동작 검증을 못 함 |
| `조건부 통과` | 차단 결함은 없으나 경고나 미검증 항목이 남음 |
| `진단 완료·미수정` | 원인과 선택지만 확인, 수정하지 않음 |
| `검증 대기` | 구현은 끝났으나 환경 · 인원을 기다림 |
| `실패` | 요구 검증에서 결함을 재현 |
| `차단됨` | 승인 · 입력 · 환경이 없어 안전하게 진행 불가 |

**`검증 대기`가 이 프로젝트에서 자주 쓰인다.** 다인 접속 테스트는 사람이나 PC가 모여야 하므로, 혼자 작업하는 시간대에는 M0/M1까지만 하고 `검증 대기`로 남기는 것이 정직하다.

---

## 4. 테스트 수준

### 자동 검증 도구

실제 `.github/workflows/`와 테스트 파일을 먼저 확인한다. 워크플로 이름만으로 Unity 빌드·컴파일·Test Runner가 실행된다고 가정하지 않는다. CI가 없는 검증은 Unity 에디터 콘솔, Test Runner 또는 수동 재현으로 수행하고 실행 수단을 기록한다.

테스트를 추가할 때 기존 테스트 구조와 [코딩 컨벤션](../coding-convention.md)을 확인한다. 존재하지 않는 테스트 경로나 명령을 실행 가능한 것으로 안내하지 않는다.

### L1 — 정적 검증

모든 변경에 적용한다. 문서만 바꾼 경우에는 내용·상대 링크·변경 범위를 확인하며 Unity 컴파일을 요구하지 않는다. 아래 콘솔 검증은 코드 변경에 적용한다.

- 변경 범위가 작업 계약과 일치하는지 확인
- Unity 콘솔에 컴파일 에러 0, **신규** 경고 없음
- 기존 경고와 신규 경고를 구분

Unity 런타임 코드의 스타일·구조 검증은 [기존 코딩 컨벤션](../coding-convention.md)의 해당 절을 기준으로 한다. 아래 표는 원문 확인 항목이며 별도 코딩 규칙이나 일괄 오류 등급을 추가하지 않는다.

| 원문 | 확인 항목 |
|---|---|
| [Unity](../coding-convention.md#unity) | 컴포넌트 참조는 인스펙터 할당 또는 `Awake`에서 캐싱하며, `Update`에서 `GetComponent`를 쓰지 않는다 |
| [Unity](../coding-convention.md#unity) | 런타임의 `Find*`·`FindObjectOfType`·`SendMessage` 금지를 확인한다 |
| [Unity](../coding-convention.md#unity) | `Update` 계열 할당 금지와, 매 프레임 필요 없는 작업의 이벤트·코루틴·`Awaitable` 사용 기준을 확인한다 |
| [Unity](../coding-convention.md#unity) | 매직 넘버·밸런스 값은 `[SerializeField]` 또는 ScriptableObject로 분리한다 |
| [Mirror](../coding-convention.md#mirror) | 서버·클라이언트 전용 메서드 표기와 Command 인자의 서버 권한·범위·쿨타임 검증을 확인한다 |
| [Mirror](../coding-convention.md#mirror) | 역할·비밀 투표 결과를 전체 동기화하지 않고 허용된 클라이언트에만 전달한다 |

나머지 코딩 규칙도 변경 내용에 해당하면 원문을 확인한다. 기능 결함의 심각도는 실제 재현 결과와 영향으로 판단한다.

### 재현과 회귀 판정

버그 수정은 가능한 범위에서 수정 전 재현을 확보하고, 같은 입력으로 수정 후 결과를 비교한다. 회귀 테스트를 추가하면 원래 결함을 실제로 잡는지 확인한다. 재현 환경이 없으면 그 한계를 남기며 테스트 통과만으로 원인 해결을 단정하지 않는다.

기대값은 최신 사용자 결정 → v4의 확정 규칙 → v4와 충돌하지 않는 기술설계·네트워크 권위 계약 순으로 확인한다. 통과시키려고 기대값을 현재 구현에 맞춰 바꾸거나 핵심 검사를 삭제하지 않는다. 구현과 같은 계산을 복사한 테스트보다 입력/출력·허용 수신자·자원 합계 등 외부에서 관찰 가능한 계약을 확인한다. 검토 보고서의 미승인 제안은 테스트 요구사항으로 확정하지 않는다.

필수 검증이 통과하면 새 변경·실패·미해결 위험이 없는 한 동일 검사를 반복하지 않는다. 스킬 수정은 문법 확인과 실제 요청에서의 동작 확인을 구분하고, 동작 조건을 바꾼 경우 해당 요청 사례로 범위 준수 여부를 확인한다.

### L2 — 기능 검증

동작 변경에 적용한다.

- 관련 EditMode · PlayMode 테스트가 있으면 Test Runner로 실행하고 통과 수를 기록
- 담당 개발 씬에서 목표 동작을 실행
- 정상 입력과 주요 실패 입력을 각각 확인
- 재현 절차와 관찰 결과를 기록

### L3 — 통합 · 멀티플레이 검증

네트워크 · 씬 · 초기화 · 공유 상태 변경에 적용한다.

**절차는 [멀티플레이 테스트 절차](04_MULTIPLAYER_TEST_PROTOCOL.md)를 따른다.**

- 최소 M2
- 지연 관련 기능은 M3 (서로 다른 PC) + 지연 주입
- 서버 시점과 클라이언트 시점 양쪽에서 확인 (에디터 호스트 모드만으로 확인하지 않는다)
- 타이밍 결함은 확률적이므로 최소 10회 반복

## 5. 위험도별 최소 검증

| 위험도 | 대표 영향 | 최소 검증 |
|---|---|---|
| 낮음 | 문서, 주석, UI 문구, 로그 | L1 |
| 보통 | 단일 시스템 내부 로직, 밸런스 수치 | L1 + L2 |
| 높음 | 공유 상태, 씬 구조, 초기화 순서, 여러 파트에 걸친 변경 | L1 + L2 + L3 |
| 치명적 | 네트워크 권위 경계, 통합 씬, `.gitattributes`, 대량 삭제 · 이동 | L3 전체 + 사전 승인 + 팀 확인 |

위험 신호가 여러 개면 가장 높은 수준을 적용한다.
**검증 비용을 이유로 수준을 낮추지 않는다. 대신 작업 범위를 줄인다.**

## 6. 검증 기록 형식

```markdown
| 주장 | 수준 | 증거 등급 | 실행 수단 | 실제 결과 | 상태 |
|---|---|---:|---|---|---|
| 두 플레이어가 같은 아이템을 동시에 주우면 한 명만 획득 | L3 | 3 | M2, 20회 반복 | 20/20 정상 | 완료(검증됨) |
| 150ms 지연에서 판정 일치 | L3 | 0 | — | 미실행 | 검증 대기 |
```

보고 전 확인한다.

- 모든 완료 주장에 등급 1 이상의 증거가 있는가?
- 동작 변경에 등급 2 이상의 증거가 있는가?
- 네트워크 변경에 등급 3의 증거가 있는가?
- 미검증 항목과 그 이유를 적었는가?
- 신규 결함과 기존 결함을 분리했는가?

## 7. 독립 검수

검수자에게 작업 대화의 자기평가를 넘기지 않고 아래 입력만 제공한다.

- 작업 계약과 수정 범위
- 현재 변경분
- 적용할 규칙 원문
- 검증 절차

검수자 계약:

- 어떤 파일도 수정하지 않는다
- 확인한 범위만 판정한다
- 환경이 없으면 추측하지 않는다
- 기존 결함은 `legacy: true`로 분리한다
- 수정 제안은 한 문장으로 제한한다

### 판정

| 판정 | 기준 | 후속 |
|---|---|---|
| `PASS` | 차단 결함과 미검증 핵심 항목 없음 | 다음 단계 진행 |
| `CONDITIONAL` | 경고 또는 환경 제약으로 미확인 항목 있음 | 보완 후 해당 범위만 재검수 |
| `REJECT` | 오류, 권위 위반, 씬 충돌, 범위 침범 | 중지하고 수정 후 재검수 |

### 최종 JSON

```json
{
  "verdict": "PASS | CONDITIONAL | REJECT",
  "checked": ["확인한 항목"],
  "findings": [
    {
      "severity": "error | warning | info",
      "rule": "authority_boundary",
      "file": "{{실제 변경 파일}}",
      "line": 0,
      "evidence": "관찰한 근거",
      "suggestion": "한 문장 제안",
      "legacy": false
    }
  ],
  "unverified": ["항목과 이유"],
  "multiplayer_grade": "M0 | M1 | M2 | M3"
}
```

`findings`에 오류나 경고가 있는데 `PASS`를 반환하지 않는다.

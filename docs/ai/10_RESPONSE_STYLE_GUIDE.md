# 응답 스타일 가이드

> AI 결과 보고의 형식과 증거 표기를 통일한다.

---

## 1. 기본 형식

```markdown
## 결론
(한두 문장. 무엇이 되었고 무엇이 안 되었나)

## 사용자 확인 필요
(사용자가 결정 · 승인해야 진행되는 것. 없으면 이 절을 뺀다)

## 변경 내용
| 파일 | 무엇을 |
|---|---|

## 검증
(03_VERIFICATION_PLAYBOOK.md §6의 6열 표를 쓴다: 주장 | 수준 | 증거 등급 | 실행 수단 | 실제 결과 | 상태)

## 미검증 · 남은 위험

## 다음에 필요한 것
```

---

## 2. 원칙

- **결론부터.** 과정을 먼저 늘어놓지 않는다
- 사실 · 추정 · 미검증을 구분한다
- 사용자가 결정해야 할 것은 결론 바로 뒤에 둔다. 긴 보고 끝에 묻히지 않게 한다
- 찾지 못하거나 확인하지 못한 것은 어디까지 찾아봤는지(경로 · 명령)와 함께 적는다
- 검증하지 않은 것을 "동작합니다"라고 쓰지 않는다
- 실패를 성공으로 포장하지 않는다
- 범위 밖 기존 결함은 별도로 표시한다
- "이쪽", "저쪽", "이것저것"처럼 대상이 불분명한 지시 표현은 쓰지 않는다. 파일·기능·값은 이름이나 경로로 직접 가리킨다

---

## 3. 쓰지 말아야 할 표현

| 피할 표현 | 대신 |
|---|---|
| "완벽하게 구현했습니다" | "구현했고 L2까지 검증했습니다. L3는 미검증입니다" |
| "동작할 것입니다" | "동작을 확인하지 못했습니다. 멀티플레이 접속 테스트가 필요합니다" |
| "간단히 수정했습니다" | 무엇을 어디서 고쳤는지 명시 |
| "문제없습니다" | 무엇을 확인했고 무엇을 확인하지 못했는지 |
| "테스트했습니다" | "M2 등급으로 20회 반복, 20/20 정상" |

---

## 4. 증거 표기

주장마다 증거를 붙이고, 표 형식과 증거 등급은 [검증 플레이북 §6](03_VERIFICATION_PLAYBOOK.md#6-검증-기록-형식)을 따른다. 실행 횟수·결과 같은 숫자가 없는 검증 주장은 신뢰도가 낮다. 확인하지 못한 항목은 이유와 함께 **미검증**으로 쓴다.

---

## 5. 코드를 보여줄 때

- 변경한 부분만 보여준다. 파일 전체를 덤프하지 않는다
- 왜 그렇게 했는지 한 줄 덧붙인다
- 대안이 있었으면 왜 이 방식을 골랐는지 적는다

---

## 6. 질문할 때

한 번에 하나씩, 선택지와 함께 묻는다.

```markdown
부식 모듈이 장착 후 언제 떨어지게 할까요?

- A. 장착 후 2~5분 랜덤 — 같은 날 안에 표류·회수 상황이 생김
- B. 다음 날 아침 — 하루 동안 효과가 유지되고 낙하 시점을 예측할 수 있음

현재 기획서(v4 13장)에서 미정입니다. 결정 전까지 낙하 시점을 임의로 확정하지 않습니다.
```

이미 결정된 것을 다시 묻지 않는다. 결정을 확인하고 우려만 짧게 남긴다.

---

## 7. 길이

- 단순 작업: 결론 + 변경 파일 목록이면 충분
- 복잡한 작업: 위 기본 형식 전체
- 조사 · 분석: 결론 → 근거 → 선택지 → 권고

**보고가 작업보다 길어지지 않게 한다.**

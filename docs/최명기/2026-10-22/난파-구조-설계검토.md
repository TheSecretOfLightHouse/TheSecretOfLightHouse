## 요청과 목표
난파·구조를 어떤 구조로 구현할지 기존 기획과 코드를 대조한다.

## 진행 과정과 결정 이유
- 최신 모듈 결정 2026-10-20~21을 v4보다 우선했다. 난파 순간 인벤토리 보존, 구조 시 무작위 한 칸 전체 소실, 미구조 재스폰 순간 전량 표류, 두 경우 메인 섬 복귀, 공동 자원 비용 폐기를 확인했다.
- BoatDurability의 서버 난파 판정·동기화와 BoatController의 표시 제거·Downed 연결은 존재한다. BoatController.HandleWrecked는 TryDropAll을 즉시 시도하므로 최신 규칙과 불일치한다.
- InteractionAction.Rescue와 공용 InteractionSessions는 존재한다. 이번 Interaction 검색에서는 구조 전용 처리기를 찾지 못했다. 열거값 존재만으로 구조 구현 완료로 보지 않는다.
- 제안: Player 기능 내부 서버 조정자가 표류 시작·직접 구조·시간 만료·재스폰 정산을 관리한다. 공용 Relay/Router/Sessions를 활용하고, 두 복귀 경로를 단일 완료 함수로 모아 중복 손실·중복 생성 방지. 제안은 확정 규칙이 아니다.
- W10 공동 비용 문제는 폐기됐으나 전원 난파 처리, W11 배 복구, W12 거리·시간·취소·경합, W13 표류 회수 계약은 남는다. W11의 가까운 섬 복귀 설명은 최신 메인 섬 결정과 차이가 있어 그대로 구현하지 않는다.

## 2026-10-22 단계별 구현과 사용자 시험 후속
- 사용자가 직접 코드를 작성하고 프리팹·씬 참조를 연결했다. AI의 게임 파일 직접 수정 성과로 기록하지 않는다.
- 사용자 확정: 난파 후 90초, 구조 시작/취소로 기한 초기화하지 않음. 플레이어는 메인 섬 복귀, 기존 배 제거 후 본인 선착장에 최대 내구도·장착 모듈 없는 새 배 생성. 직접 구조와 시간 만료의 배 복구 방식은 동일.
- PlayerWreckRecovery/WreckRecoveryResult, PlayerController의 배 소유 교체, BoatController의 난파 진입·복귀 하선/RPC, PlayerBoatSpawner의 복구 배 생성·서버 참조 주입, PlayerInventory의 서버 모듈 조회·한 칸 추첨/소실을 단계별 안내했다. 중간 제안 PlayerWreckInventory는 불필요한 래퍼로 철회했다.
- 타 담당 코드 변경 금지 의사를 확인했다. ModuleInteractionHandler에 새 조회 API를 추가하지 않고, 기존 WorkbenchNet.TryGetCarried와 ModuleInteractionHandler.DiscardCarried를 PlayerInventory에서 소비하도록 안내했다. 현재 연결은 지정 작업대 한 곳 기준이며 다중 작업대 보유 조회는 별도 확인 필요.
- 사용자는 호스트의 모듈 단독 후보 조회 성공을 확인했다. 이어 기존 Test/Wreck Boat → PlayerWreckRecovery의 Test/Complete Rescue 시험에 대해 전체 성공을 확인했다. 체크 항목은 난파 순간 보존, 구조 시 한 칸 전체 소실, 메인 섬 이동/행동 복구, 기존 배 제거와 최대 내구도 새 배 생성이다. 이는 사용자 실행 보고이며 AI가 Unity에서 직접 관찰한 결과가 아니다.
- 현재 구조 성공은 시험 호출 경로다. 직접 구조 입력·거리·유지 시간·취소는 미연결. 시간 만료 정산은 미구현으로 TimedOut 진입을 임시 거절하도록 안내했다. 90초 자동 복귀 완료로 보고하지 않는다.
- 미구조 자원/모듈 표류·섬 가장자리 이동, 실패 후 재개/복구, 새 배 생성 지점의 점유 처리, 복귀 방향 반영은 후속 확인 대상이다. 전체 완료로 판단하지 않는다.
- 다음 검증: 같은 플레이어의 두 번째 난파/구조 복귀, 원격 플레이어의 서버 시험 호출과 양쪽 위치·상태·배 소유·카메라 확인. 임시 시험 메뉴는 통합 후 정리한다.

## 2026-10-22 클라이언트 임시 UI 텍스트 수정
- 사용자: 클릭 구조는 동작하지만 클라이언트 UI 텍스트가 보이지 않음을 보고. AI가 생성한 OS 동적 폰트의 저장 방식 문제를 조사했다.

- AI 실제 검증: MKTestScene 새 Play에서 제목/두 버튼 모두 material=true, 한글 글리프 지원, 텍스트 정점 48/12/16 확인. 패널을 시험용으로 표시한 Game View 캡처에서 세 한글 문구 확인. 신규 콘솔 오류/컴파일 실패 없음. 다인 클라이언트 재접속 시험은 미실행.

## 2026-10-22 범위 정정 후 현재 코드 점검
- 사용자 확인: 클라이언트 한글 표시 성공. 사용자 최신 범위는 구조 시 무작위 한 칸 전체 드롭, 미구조 90초 후 전량 드롭, 생성 목록을 강민서에게 제공하는 데까지다. 이후 표류 이동은 강민서 담당이라는 최신 사용자 지시를 따른다. 기존 기준 문서의 구조 시 소실/섬 가장자리 이동 담당 설명과 차이가 있으며 이번 현황 점검에서는 기준 문서를 임의 변경하지 않았다.
- 실제 코드: WreckDropItem의 종류·ID·수량·위치·GameObject 자료형 존재 확인. Player 영역 검색에서 생성/사용처는 생성자 선언 외에 없음. 드롭 목록 생성·발행/전달 API는 미연결.
- PlayerInventory의 자원/모듈 추첨은 존재하나 TryApplyRescuedWreckLoss는 자원을 제거하고 모듈은 DiscardCarried로 삭제한다. 최신 구조 시 드롭 지시와 불일치하며, 실제 월드 드롭 생성은 호출하지 않는다.
- PlayerWreckRecovery.Update는 90초 만료를 감지하지만 TryBeginCompletion의 TimedOut 분기에서 즉시 false 반환. TrySettleRecoveryInventory도 Rescued만 처리하므로 전량 드롭/자동 복귀 미연결. Recovery에서 기존 Dropper.TryDropAll 호출은 검색되지 않음.
- PlayerInventoryDropper는 기존 자원 전량 드롭 함수와 _spawnedDrops/_removedContents 필드까지 존재. 이번 파일에는 TryRollbackDrops 함수가 없고 두 필드를 기록/복구에 사용하는 코드도 아직 없음. 기존 함수는 부분 성공할 수 있고 모듈은 처리하지 않음.
- 관련 모듈 상태 enum은 Drifting 없이 OnBoat까지이며, 기존 DiscardCarried는 장부를 삭제한다. 모듈 드롭 시 원래 장부 식별 유지/이관 계약은 확인이 필요하며 타 담당 코드 임의 수정 금지는 유지한다.
- 추가 실패 경로: TryBeginCompletion은 완료 중 플래그를 켠 뒤 복귀 실패 시 해제/재개하지 않아, 실패하면 후속 요청이 막힐 수 있음. 드롭 정산 연결 때 실패 복구도 함께 검토해야 한다.
- 이번 검증은 관련 C#·최신 기준 문서·git status 정적 읽기와 참조 검색이다. 게임 코드 수정·Unity 재실행 없음. 앞선 사용자 실행 보고와 이번 코드 존재 확인을 구분한다.

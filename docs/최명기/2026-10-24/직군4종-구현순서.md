# 직군 4종 구현 순서

작성자: 최명기 / 작성일: 2026-10-24
상태: 정적 조사·구현 안내 작성, 게임 코드 미수정

## 목표와 조사 범위

오늘 직군 4종 능력을 단계적으로 직접 구현하기 위한 안내다. 현행 규칙은 [직군 능력 후속 결정](../../design/job-ability-decisions.md)을 따른다.

Player C# 77개 파일 목록과 능력 관련 호출을 검색하고 Abilities 전체, PlayerController, 입력, 대포, 내구도, 채집 처리, 인벤토리 규칙과 관련 소비 지점을 확인했다. 전체 파일 일괄 출력은 잘렸으므로 77개 본문 전체를 완독했다고 주장하지 않는다. 네트워크·몬스터·시간·환영 서비스의 연결 지점도 검색했다. 실행 검증은 하지 않았다.

## 오늘 따라 할 순서

각 단계의 확인을 마친 다음 단계로 넘어간다. 아래 새 타입 이름은 구현 제안이며 기존 API가 아니다. 시간은 작업량에 따라 달라지므로 하루 안에 8개 능력 통합 완료를 보장하지 않는다.

### 1. 직군과 효과 표부터 고정

1. 네 직군 구성은 공유 결정 표로 확정됐다. 남은 수리 게이지 증가 의미·증가량, 스택 증가량, 피버 지속시간을 적는다.
2. 정비공 액티브는 모듈 부식 확인이다. 결과는 본인만 받고, 모듈 판정 제공자는 김지훈과 연결한다.
3. 공통으로 대상·거리·지속시간·사용 제한·실패 시 소비 여부를 채운다. 하루 1회는 항해사 항로·정비공 부식 확인의 기존 규칙이며 다른 액티브에 자동 적용하지 않는다.
4. 쉴드 중복 부여와 소환 후 남은 버프, 스택 한도 축소로 초과 자원이 생길 때의 처리도 결정한다.

확인: 확정과 미정을 구분한 4행 표가 있어야 한다. 미정인 능력만 보류하고 독립 작업은 진행한다.

### 2. 기존 재장전 패시브를 경비병에 연결하고 기준 시험 확보

1. 현재 Tech 1의 ReloadPassive는 이전 기획 연결이다. 경비병 직군에 연결하고 정비공에서는 해제하는 변경이 필요하다. 아직 프리팹을 수정하지 않았다.
2. 자기 개발 씬에서 실제 생성된 플레이어의 PlayerPassiveController→ReloadPassive 연결을 확인하고, 일반 플레이어와 경비병이 같은 배 설정으로 발사하게 한다.
3. BoatCannon의 서버 재장전 로그를 비교한다. 기본 시간이 2초이고 배율이 0.5라면 기대 시간은 1초다.
4. 하선·난파·승하선 반복 후 잘못 적용되거나 누적되지 않는지 확인한다.
5. 호스트와 원격 플레이어를 바꿔 반복한다.

확인: 기존 패시브 동작을 확보한다. 프리팹 이름만으로 정비공 판정을 대신하지 않는다.

### 3. 직군 상태와 액티브 서버 요청 공통 경로

1. Player의 Abilities/Rules에 직군 종류와 설정을 둔다. 프리팹 외형과 서버 직군 상태를 구분한다.
2. 서버가 직군을 보유하고 본인에게 필요한 정보만 전달한다. 전체 플레이어에게 직군 SyncVar를 공개하지 않는다.
3. 현재 입력→Runner 즉시 실행 경로를 요청→서버 검증→승인 응답→로컬 표현 순으로 확장한다.
4. 서버에서 송신자·직군·난파·대상·거리·사용 제한을 검사한다. 사용 횟수와 실제 효과도 서버가 변경한다.
5. 요청 번호로 중복 소비를 막고, 취소·난파 이후 도착한 승인으로 표현이 다시 시작되지 않게 한다.
6. 공용 요청 경로는 김지훈과 기존 Interaction 경로 사용 여부를 확인한다. Player 기능의 서버 처리는 최명기 범위다.

확인: 실제 효과 없이 요청 1회가 승인 또는 거절 1회로 끝나는 것부터 시험한다. 호스트에서 두 번 적용되지 않아야 한다.

### 4. 첫 액티브는 경비병 쉴드

효과가 명확하고 기존 피해 함수 한 곳에서 결과를 확인할 수 있어 첫 대상으로 추천한다.

1. 대상 배에 서버 쉴드 상태를 둔다. 적용자는 플레이어, 효과 보유자는 배다.
2. BoatDurability.ApplyDamage의 기존 유효 피해 검사 뒤, 내구도 차감 전에 쉴드를 확인한다.
3. 쉴드가 있으면 먼저 소모하고 피해 처리를 종료한다. 내구도·난파 이벤트는 발생시키지 않는다.
4. 모든 피해 1회 방어이므로 Monster만 검사하지 않는다. 0·음수·NaN 등 유효하지 않은 피해는 쉴드를 소모하지 않는다.
5. 배의 쉴드 표시와 해제는 관찰 클라이언트에도 전달한다. 직군 전체 공개와는 별개다.
6. 지정 배 선택·거리 검사는 승인된 규칙대로 연결한다. 지속 효과 수명을 Runner 실행 시간에 묶지 않는다.

확인: 내구도 100에 쉴드→피해30은 100 유지·쉴드 해제→다음 피해30은 70. 몬스터와 암초 순서를 바꾸고 동시 공격에서도 한 번만 막는지 확인한다.

주의: BoatModuleEquipment의 Test/Wreck Boat도 ApplyDamage를 사용하므로 쉴드가 있으면 첫 호출이 막힐 수 있다. 강제 난파 시험과 일반 피해 방어 시험의 기대를 구분한다.

### 5. 채집가 스택 패시브

1. InventoryData의 기본 10은 유지하고 플레이어별 유효 스택 크기를 계산하도록 확장한다. 전역 상수를 20으로 바꾸면 전원이 늘어난다.
2. TryAdd·UsedSlots·스택 개수 계산이 같은 유효 크기를 사용하게 한다.
3. PlayerInventory가 서버의 유효 크기를 본인 클라이언트에 제공하게 한다.
4. InventoryChestScreen의 스택 분할과 PlayerInventory.TryBuildWreckDropPlan의 한 칸 손실 계산을 같은 값으로 바꾼다.
5. 패시브 해제 시 초과 보유 처리 규칙을 반영한다. 임의 삭제하지 않는다.

확인: 일반/채집가 각각 스택 한도·한도+1·8칸 가득 참, UI 표시, 구조 시 한 칸 손실을 시험한다. 예를 들어 시험 한도가 20이면 21개는 20+1 두 칸이다. 20은 제안 시험값이며 확정 수치가 아니다.

### 6. 채집가 피버타임

1. 효과는 제한시간 동안 채집 자원 획득량 2배로 확정됐다. 지속시간과 공유 잔량 차감 방식을 정한다. 행동 속도 증가는 포함하지 않는다.
2. 서버에 종료 시각과 적용 상태를 둔다. 중복 발동은 정한 갱신/거절 규칙으로 처리한다.
3. HarvestInteractionHandler와 World 예약 수량 계약을 함께 검토한다. 1회분을 소모하고 보너스 1회분을 주는지, 잔량도 2회분 소모하는지 합의한다. 예약 실패·재시도에서 중복 보상이 없어야 한다.
4. 서버에서 확정한 채집에만 2배를 적용한다. 줍기·반환·작업대 인출까지 무조건 두 배로 늘리지 않는다.
5. 실패·인벤토리 가득 참·난파·소환·종료 시 소비와 해제를 시험한다.

확인: 버프 전/중/후의 실제 결과를 비교하고 만료 후 원래 값으로 돌아와야 한다. World 수정이 필요하면 강민서와 경계를 먼저 확인한다.

### 7. 항해사와 정비공 나머지 액티브

1. 항해사 속도는 BoatController의 최종 이동 계산에 별도 배율로 합성한다. 공용 ShipPhysicsProfile 원본을 직군별로 덮어쓰지 않는다. 기존 대쉬·안정기와 중복 적용을 점검한다.
2. 환영 면역은 지도에 그린 뒤 지우는 것뿐 아니라 개인 정보 제공 경로에서 다룬다. 현 IIllusionService는 생성 계약만 있으므로 면역 조회가 준비됐다고 가정하지 않는다. 강민서와 연결한다.
3. 구조 항로는 난파 대상 선택·실제 최단 경로 계산·본인 표시가 필요하다. 목적지 직선 화살표만 만들었다면 최단 항로 완성으로 보고하지 않는다.
4. 정비공 패시브는 수리 게이지 증가의 정확한 의미를 정한 뒤 기존 BoatRepair 서버 계산에 연결한다. 기본 수리 조건을 임의로 우회하지 않는다.
5. 정비공 액티브는 모듈 부식 판정 API·허용 대상·요청 경로를 김지훈과 확인하고 연결한다. 결과를 전체 RPC로 공개하지 않는다.

확인: 속도·지도 면역·항로를 별개 항목으로 기록한다. 연결 대기 기능이 있어도 완료된 패시브·쉴드 시험은 유지한다.

### 8. 오늘 마지막 통합 확인

- 네 직군을 각각 지정해 호스트/원격에서 본인 능력만 사용되는지 확인한다.
- 난파 중 발동 금지, 연타·잘못된 대상 거절, 일일 사용량의 서버 기준 초기화를 확인한다.
- 소환 후 직군 비활성화와 이미 남은 효과는 확정한 정책대로 확인한다.
- Unity 컴파일·Mirror Weaver 후 최소 2인 시험, 최종 4인 시험을 구분해 기록한다.

오늘 우선 확보할 묶음은 ‘재장전 패시브를 경비병으로 연결·확인→공통 서버 요청→쉴드→채집가 스택’이다. 나머지는 수치와 외부 기능 연결 상태에 따라 이어간다.

## 관련 공백과 남은 결정

R17은 네 직군 목록이 이번에 정해졌지만 배정 중복·필수 포함·세부 수치는 남았다. R23/K07은 소환 이후 능력·잔여 효과 계약이 남았다. 채집가 스택 확대는 R22의 소환 시 자원 처리와도 연결된다. 이번 조사에서 결정 대기 항목을 오류나 구현 완료로 바꾸지 않았다.

## 2026-10-24 최종 직군 구성 반영

- 사용자 최종 정리로 정비공=수리 게이지 증가/부식 확인, 경비병=재장전 증가/1회 쉴드, 채집가=스택 증가/시간제 채집량2배로 확정했다. 항해사는 유지했다.
- 기존 ReloadPassive 코드는 재사용 가능하지만 Tech 1에 붙은 상태는 최신 직군 배치와 다르므로 연결 변경이 필요하다. 이번에는 문서만 수정했다.
- 결정 이유: 사용자의 최신 명시적 직군 표가 이전 예시와 정비공 재장전 기록보다 우선한다. 과거 기록은 당시 이력으로 보존한다.

## 2026-10-24 기반 재확인과 실제 첫 단계

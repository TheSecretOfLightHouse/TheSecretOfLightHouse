## 4. 현재 구현과 기획의 차이

다음은 코드 정적 확인이며 이번 문서 작성에서 실행 시험을 수행하지 않았다. 아래 경로는 `Assets/01.Scripts/` 기준이다.

| 항목 | 현재 확인한 구현 | 확정 기획 대비 상태·영향 |
|---|---|---|
| 채집 입력·대상 | `05.Player/Control/View/InputActions.inputactions`, `Gathering/View/PlayerHarvestProbe.cs`: Harvest 입력, 커서 Ray, 가까운 충돌체·거리 검사, LocalHarvestTestSpot.SpotId를 HarvestSpot 종류로 Relay에 전송 | 비네트워크 시험 지점 요청 있음. 피해·파괴 판정이 구현됐다는 뜻은 아님 |
| 단발 채집 처리 | `05.Player/Gathering/Server/HarvestInteractionHandler.cs`: INonNetworkTargetAdapter와 IInteractionHandler를 함께 구현. 시험 SpotId를 서버 대상 위치로 변환한 뒤 TrySpawnDrop 호출 | 원본 HP·타격 누적·파괴 완료·원본 제거·World 잔량 차감은 이 처리기에 없음. 원본을 유지한 채 요청이 반복되면 드롭을 계속 생성할 위험이 있음(정적 추론) |
| 드롭 생성 | `05.Player/Gathering/View/HarvestDropSpawner.cs`: Resource.PickupPrefab 검사 → ID/수량 초기화 → NetworkServer.Spawn | 서버 드롭 생성 기반 있음. 본편 파괴/잔량과 생성 실패의 결합 계약은 미연결 |
| E키 픽업 | `05.Player/Control/PlayerInteractionInput.cs` + `03.Interaction/Relay/View/InteractionSelector.cs` → `Server/PickupInteractionHandler.cs` → `Net/ResourcePickup.cs` | Selector가 레이어·기본 Action·범위로 선택하고, PickUp Handler는 지급 성공 후 제거. 원격·동시 획득 미검증 |
| 인벤토리 | `05.Player/Inventory/Net/PlayerInventory.cs`: 카탈로그 검증·TryAdd·Owner SyncDictionary | 개인 수량 동기화 코드 있음. 본편 용량·소비 규칙은 미정/후속 |
| World 대상 | `02.World/Harvest/Rules/HarvestSpot.cs`: SpotId·ResourceId 바인딩. ResourceDefinition은 자원 정의·픽업 프리팹 제공 | Player의 LocalHarvestTestSpot은 본편 HarvestSpot과 다른 타입. World Registry의 소비·재생 기반은 존재하지만 현재 시험 Handler는 호출하지 않음 |

과거 호스트 시험에서는 획득 수량 증가·드롭 제거·실패 시 유지·제거된 대상 재요청 거절 기록이 있다. 현재 본편 파괴 채집 및 M2/M3 전체 통과로 확대하지 않는다. 상세 증거는 [E키 작업 원문](../2026-10-15/E키-공용상호작용-돌획득.md)을 참조한다.


## 8. 한눈에 보는 현재 실행 흐름

다음 도식은 **현재 작업 트리의 시험 구현**이다. ‘원본을 파괴한 뒤 드롭 생성’이라는 확정 목표와 달리, 현재 Handler는 파괴 판정 없이 드롭을 생성한다.

```text
[왼쪽 클릭: 원본에 채집 요청]
tech의 PlayerActions / Harvest
  → PlayerInputReader.OnHarvest(isPressed)
  → PlayerController가 Harvest 요청 플래그 저장
  → ProcessActionRequests: 플래그 초기화, 난파·탑승 검사
  → HarvestRequested 이벤트
  → PlayerHarvestProbe: 커서 Ray → 가장 가까운 Collider
  → 부모 HarvestTarget + 같은 오브젝트 LocalHarvestTestSpot 확인
  → 거리 확인 → (HarvestSpot, SpotId, Harvest) 요청
  → InteractionRelay: 소유권·응답 대기 확인, 요청 번호 부여
  → Command → InteractionRouter: 참가자·판 단계·요청 번호 확인
  → TargetResolver → HarvestInteractionHandler.TryResolve
  → 서버 시험 지점 위치·거리 확인
  → HarvestInteractionHandler.Handle: 플레이어·대상 확인
  → HarvestDropSpawner: 자원 정의의 PickupPrefab 생성·초기화·Spawn
  → 결과를 요청자에게 반환
  ※ 아직 원본 파괴·원본 제거·World 잔량 차감 없음
  ※ 이 단계에서는 인벤토리 증가 없음

[E키: 이미 생성된 드롭 획득]
tech의 PlayerActions / Interact
  → PlayerInputReader.OnInteract(isPressed)
  → PlayerController.InteractionRequested
  → PlayerInteractionInput → InteractionSelector: 허용 레이어의 가까운 대상 선택
  → (NetworkObject, 대상 netId, 대상 DefaultAction) 요청
  → stone은 DefaultAction=PickUp이므로 픽업 처리기로 전달
  → 동일 Relay/Router → TargetResolver의 네트워크 대상 검사
  → PickupInteractionHandler.Handle
  → ResourcePickup.TryCollect: 획득 잠금
  → PlayerInventory.TryAdd → 서버 InventoryData 갱신
  → Owner SyncDictionary 갱신
  → 성공: NetworkServer.Destroy(드롭)
     실패: 획득 잠금 해제, 드롭 유지
  → 요청자 결과 수신, 소유자 수량 이벤트·디버그 패널 갱신
```

**원본의 SpotId, 생성된 드롭의 netId, 자원 종류의 ResourceId는 서로 다른 값이다.** 셋을 같은 ID로 취급하지 않는다.

## 9. 좌클릭 채집의 상세 동작

### 9.1 입력 수신과 요청 큐

- 현재 tech 입력 에셋의 왼쪽 마우스 버튼은 Harvest, E키는 Interact에 바인딩돼 있다. OnHarvest/OnInteract는 `value.isPressed`일 때만 이벤트를 발행한다.
- PlayerController는 입력 이벤트에서 즉시 서버를 호출하지 않고 `_harvestRequested` 또는 `_interactRequested`를 true로 만든다. ProcessActionRequests에서 플래그를 복사한 뒤 초기화한다. 같은 처리 주기 전에 여러 입력이 들어오면 bool 요청으로 합쳐질 수 있다.
- 난파 상태이면 처리하지 않는다. Harvest 이벤트는 탑승 중 발행하지 않고, Fire 요청은 탑승 대포 처리로 분리돼 있다. 좌클릭을 채집·대포 공용 키로 새로 확정한 문서가 아니다.
- Interact 처리가 Harvest보다 먼저다. 둘이 같은 주기에 발생하면 Relay의 ‘응답 대기 중 추가 전송 금지’에 영향을 받을 수 있다. 두 요청이 항상 모두 실행된다고 보장하지 않는다.
- 홀드 채집 시간, 연타 속도, 도구 공격 주기는 현재 이 입력 플래그로 구현된 것이 아니다. 입력 에셋·장치와 함께 실제 클릭 수를 재검증해야 한다.

### 9.2 커서로 원본 선택

1. Probe는 활성 PlayerController이며 난파·탑승 상태가 아닌지 확인한다.
2. Camera.main, Mouse.current, InteractionRelay가 모두 있어야 진행한다. 없으면 요청 없이 종료한다.
3. 화면 중앙이 아니라 `Mouse.current.position`을 `ScreenPointToRay`로 변환한다.
4. RaycastNonAlloc로 `_probeDistance` 내 `_probeMask`의 non-trigger 충돌체를 최대 32개 버퍼에 받는다. 버퍼가 꽉 차면 누락 대상이 있을 수 있으므로 선택하지 않고 종료한다.
5. 플레이어 Transform 하위 충돌체를 제외하고 Ray 기준 가장 가까운 충돌체를 선택한다. 먼저 자원만 필터링해 뒤쪽 자원을 선택하는 구조가 아니다. 앞에 벽이나 자원이 아닌 물체가 있으면 뒤 자원을 요청하지 않는다.
6. 가장 가까운 충돌체의 부모에서 HarvestTarget을 찾고 ResourceDefinition과 양수 AmountPerHarvest가 설정됐는지 확인한다.
7. 그 HarvestTarget과 같은 오브젝트의 LocalHarvestTestSpot이 활성이고 SpotId가 양수여야 한다.
8. 플레이어 위치와 Ray가 닿은 지점의 제곱 거리가 `_reach²` 이하여야 한다.
9. `TrySendToNonNetworkTarget(HarvestSpot, SpotId, Harvest)`를 호출한다. 반환 bool은 전송 시도 수락 여부이며 **서버 채집 성공 여부가 아니다.**

### 9.3 서버의 시험 원본 해석

- LocalHarvestTestSpot은 직렬화 SpotId만 갖는 시험용 MonoBehaviour다. 자체 네트워크 생성·매장량·HP·파괴 기능은 없다.
- HarvestInteractionHandler는 OnStartServer에서 HarvestSpot 종류의 TargetResolver Adapter를 먼저 등록하고 Harvest Action Handler를 등록한다. Adapter 등록 실패 시 진행하지 않으며 Handler 등록 실패 시 Adapter를 해제한다. 서버 종료 시 자기 등록을 해제한다.
- TryResolve는 서버·Handler 등록 상태·Harvest Action을 검사하고 `_testSpots` 배열에서 요청 SpotId를 찾는다.
- 같은 SpotId가 배열에 중복으로 있으면 첫 항목을 쓰지 않고 거절한다. ID가 없거나 0 이하, 지점 비활성, HarvestTarget 미설정이어도 거절한다.
- 확인된 대상 Transform 위치와 `_serverRange`를 공용 Resolver에 넘긴다. 클라이언트가 보낸 자원 ID·수량·대상 위치로 지급량을 결정하지 않는다.
- 공용 거리 검사를 통과하면 Handle에서 Action/Kind, 송신자 identity, 활성 PlayerController, 난파·탑승, 시험 대상 유효성을 다시 확인한다.
- 현재 성공 처리는 TrySpawnDrop 호출이다. 원본 HP 감소, 파괴 애니메이션 완료 대기, 원본 제거, World TryConsume, 지속 세션 완료/취소는 이 처리기에서 호출하지 않는다.

## 10. 서버 드롭 생성과 데이터

### 10.1 자원 정의와 수량 출처

- HarvestTarget은 ResourceDefinition 참조와 AmountPerHarvest를 갖는다. IsConfigured는 자원 참조가 있고 수량이 양수인지를 확인한다.
- ResourceDefinition은 Id·DisplayName·Icon·Rarity·SpotCategory·IsUbiquitous·DefaultDeposit·PickupPrefab을 제공한다. 종류/표현·World 매장량 데이터와 실제 인벤토리 수량을 구분한다.
- 현재 드롭 ID는 `target.Resource.Id`, 수량은 `target.AmountPerHarvest`에서 얻는다. 희귀 확률 추첨이나 직군 수율 보정이 이 코드에 있는 것으로 기록하지 않는다.

### 10.2 생성 순서와 실패

1. 서버 TrySpawnDrop이 HarvestTarget과 설정을 확인한다.
2. Resource.PickupPrefab이 존재하고 루트에서 NetworkIdentity와 ResourcePickup을 찾을 수 있어야 한다.
3. `target.transform.position + _dropOffset`에 Quaternion.identity로 Instantiate한다.
4. ResourcePickup.TryInitialize(ID, 수량)를 호출한다. 초기화 실패 시 생성한 로컬 오브젝트를 Destroy하고 false를 반환한다.
5. 초기화 후 NetworkServer.Spawn을 호출하고 true를 반환한다. 클라이언트에서 표시하려면 해당 NetworkManager의 스폰 프리팹 등록도 맞아야 한다.

현재 ResourcePickup의 ID·수량·초기화·획득 플래그는 서버 보관 필드이며 SyncVar가 아니다. 클라이언트의 수량 표시 데이터는 PlayerInventory에서 받는다. ID·수량이 드롭에도 자동 동기화된다고 가정하지 않는다. Spawn 뒤 드롭 물리 위치가 계속 동기화되는지는 별도 컴포넌트·시험으로 확인해야 한다.

현재 코드는 NetworkServer.Spawn 호출 뒤 본편 잔량·파괴 상태를 묶어 복구하는 트랜잭션을 제공하지 않는다. 함수 true만으로 모든 원격 화면에 드롭이 정상 표시됐다고 보고하지 않는다.

## 11. E키 획득의 상세 동작

### 11.1 현재 E키 선택 — Player 입력 어댑터와 공용 Selector

- 이전 자원 전용 PlayerPickupInput.cs와 meta는 작업 트리에서 삭제 상태다. 현재 어댑터는 `Assets/01.Scripts/05.Player/Control/PlayerInteractionInput.cs`의 전역 타입이다.
- 어댑터는 InteractionRequested를 구독하고 로컬·활성·비난파 조건을 검사한 뒤 Selector.TryInteract를 호출한다. 어댑터에는 탑승 거절 검사가 없으나 PickupInteractionHandler는 탑승 상태 지급을 거절한다.
- tech 프리팹에는 위 전역 어댑터·InteractionSelector·Relay가 연결됐다. `03.Interaction/Relay/View/PlayerInteractionInput.cs`의 네임스페이스 타입도 저장소에 별도로 존재하므로 이름만 보고 같은 스크립트로 취급하거나 둘을 중복 부착하지 않는다.
- Selector는 InteractionTarget.Active에서 NetId가 있고 `_interactionLayers` 마스크에 해당하며 DefaultAction을 지원하는 대상을 골라, Range 안의 최근접 대상으로 정한다.
- Update뿐 아니라 TryInteract 직전에도 선택을 갱신한다. Selected/SelectedChanged와 실제 요청이 같은 선택 경로를 사용한다.
- 요청은 선택된 netId와 DefaultAction이다. ResourcePickup 전용 필터는 없다. 현재 stone은 PickUp이므로 PickupInteractionHandler로 전달되지만 다른 허용 레이어 대상은 다른 기본 Action을 요청할 수 있다.
- TagManager의 레이어 3은 Interaction, tech 마스크는 8(레이어 3), stone 루트 레이어는 3이다. 다른 E키 대상도 적절한 레이어·지원 Action·범위가 필요하다. 마스크 0이면 후보가 없다.
- 로컬 Ray 가림 검사나 자원 종류 필터는 Selector에 없다. 원본 채집은 별도 Probe의 비네트워크 SpotId 경로다. 확정 기획의 ‘원본 E키 직접 채집 금지’는 대상 레이어·표식 구성과 회귀 시험으로 확인해야 한다.

### 11.2 서버의 획득 실행과 일회 지급

1. 공용 Resolver가 NetworkServer.spawned에서 드롭 netId를 찾고 활성 InteractionTarget과 PickUp 지원 여부를 확인한다.
2. 공용 서버 거리 검사를 통과하면 PickupInteractionHandler가 서버·PickUp Action·송신자 identity를 검사한다.
3. 요청자의 PlayerController와 PlayerInventory가 있어야 하며 난파·탑승 중이면 거절한다.
4. 대상 identity에서 ResourcePickup을 찾아 TryCollect를 호출한다.
5. TryCollect는 미초기화·이미 획득 중/완료·인벤토리 없음이면 실패한다. 우선 `_isTaken=true`로 잠근다.
6. 인벤토리 TryAdd가 실패하면 `_isTaken=false`로 되돌리고 드롭을 유지한다. 성공하면 NetworkServer.Destroy한다.

한 드롭에 대한 중복 지급 방지 기반은 있으나 원격 두 명의 실제 경쟁 시험 통과를 뜻하지 않는다. 최초로 서버에서 성공한 획득 요청이 지급받는 코드이며, 클릭 시각 기준 공정성·지연 보정 우선권을 별도로 구현한 것은 아니다.

## 12. 인벤토리 동기화와 화면 표시

- 서버 TryAdd는 ResourceCatalog 참조와 ID 등록 여부를 확인한 뒤 InventoryData.TryAdd를 호출한다.
- InventoryData는 ID별 정수 수량 사전이다. 요청량이 0 이하이거나 `int.MaxValue`를 넘는 덧셈이면 실패한다. 성공하면 서버 수량을 늘린다.
- 서버 수량을 `_syncedCounts[id]`에 복사한다. PlayerInventory는 Awake에서 SyncMode.Owner를 사용하므로 동기화 대상을 소유자로 제한하는 코드다. 호스트 서버 메모리의 비밀성까지 보장한다는 뜻은 아니다.
- 로컬 플레이어 시작 시 SyncDictionary의 Add/Set/Remove/Clear 이벤트에 연결한다. 변경은 ResourceCountChanged, 삭제는 수량 0, 전체 초기화는 InventoryReset 이벤트로 알린다. 종료 시 구독을 해제한다.
- InventoryDebugPanel은 로컬 플레이어에게만 우측 상단의 ‘내 인벤토리 · 동기화 수량’을 그린다. 자원 카탈로그 표시명·ID·수량과 스크롤 영역을 제공한다. 수량 변경 시 내용을 재구성하며 초기 구독 때도 현재 Counts를 읽는다.
- 패널의 존재를 완성된 본편 HUD로 간주하지 않는다. 현재 코드에 가방 슬롯·무게·최대 보유량·사용/소비·공동 보관함 연결이 구현됐다고 쓰지 않는다.

## 13. 공용 요청 검증·결과·실패 분기

### 13.1 Relay와 Router의 처리 순서

- Relay는 자기 소유 플레이어만 전송하고 한 번에 한 요청의 응답을 기다린다. 응답 대기 중에는 false를 반환한다. 자동 재전송·입력 큐 대기열을 제공하지 않는다.
- Command의 서버 진입점은 송신 연결과 플레이어 Transform 위치를 Router에 넘긴다. 이 위치는 이동 권위 정책상 소유 클라이언트의 보고 위치다. 서버가 독립 이동 시뮬레이션으로 보장한 위치와 구분한다.
- Router 순서는 참가자 조회 → InProgress 확인 → `(ActorId, Sequence)` 장부 → 대상 해석 → 서버 거리 → 등록 Handler/SessionHandler 호출 → 결과 기록이다.
- 동일 요청 번호 재전송은 저장 결과를 돌려주고 실행을 반복하지 않는다. 정상 번호로 접수된 뒤 대상/기능에서 실패해도 번호는 소비된다. 참가자·판 단계·번호 불일치는 미접수 결과다.
- 결과는 요청자 TargetRpc로 반환되고 Relay.ResultReceived에서 소비할 수 있다. 요청 결과를 UI 안내로 모두 연결한 상태인지는 별도 확인해야 한다.
- 현재 Harvest는 IInteractionHandler 단발 등록이다. 공용 지속 세션 기반이 있다는 이유로 이 채집이 홀드 시간·CancelSession까지 연결됐다고 간주하지 않는다.

### 13.2 상황별 관찰·예상 결과

| 상황 | 현재 처리 | 구분 |
|---|---|---|
| 카메라/마우스/Relay 없음, 원본 가림, Probe 범위 밖 | Probe가 요청 없이 종료 | 로컬 선택 단계 |
| 시험 SpotId 미등록·중복·비활성/미설정 | Adapter/Resolver에서 InvalidTarget | 서버 대상 해석 |
| 비참가자 / 진행 중 아님 | NotParticipant / NotInProgress | 공용 미접수 |
| 요청 번호 건너뜀 / 오래된 번호 | SequenceGap / StaleSequence. 같은 번호 재전송은 이전 결과 | 공용 장부 |
| 서버 거리 초과 | OutOfRange | 공용 거리 |
| 네트워크 대상이 지원하지 않는 Action | ActionNotSupported | 드롭 대상 표식 검사 |
| 처리기 없음 | NotHandled | 등록 구성 오류 가능 |
| 플레이어 상태·자원 정의·프리팹·지급 등 기능 검사 실패 | Rejected 또는 InvalidTarget | 기능 처리 |
| 잘못된 자원 ID로 생성한 드롭 획득 | TryAdd의 카탈로그 검사 실패 → 잠금 해제·드롭 유지 | 생성 전 ID 유효성 보장과는 별개 |
| 다른 사람이 제거한 드롭 재요청 | spawned에서 못 찾으면 InvalidTarget | 추가 지급 없음이 기대됨 |
| E키와 Harvest를 응답 전에 연속 전송 | Relay 대기로 후속 전송이 false일 수 있음 | UI·재입력 경험 미검증 |

로컬 Ray 가림 검사는 서버 시야 검사를 뜻하지 않는다. 현재 공용 Router는 위치 거리 검사이며 벽 관통 변조 요청에 대한 서버 시야 판정은 여기서 확인되지 않는다. 요청 속도 제한·수치 확정도 후속이다.

## 15. 강민서 World 연결과 아직 빠진 파괴 채집

### 15.1 World에 이미 존재하는 기반

- `02.World/Harvest/Rules/HarvestSpot.cs`: 월드 지점의 종류·SpotId·ResourceId·위치와 바인딩 상태를 제공한다.

- HarvestRegenDriver는 DayStarted와 일차 차이를 받아 Registry.Regenerate를 호출한다. 부분 회복 코드가 있다는 사실과 파괴한 시각 오브젝트가 다시 생성되는 것은 별개다.

### 15.2 현재 시험 경로와 본편 경로의 차이

LocalHarvestTestSpot은 World HarvestSpot과 별개이며, 현재 Player Handler는 자기 배열에서만 조회한다. World Registry.TryConsume·잔량·일일 회복을 읽거나 호출하지 않는다. SpotId 요청 형태를 도입한 것은 진행 사항이지만 World 통합 완료는 아니다.

현재 시험 Handler와 HarvestHost는 **같은 HarvestSpot 종류에 Adapter를 등록**한다. TargetResolver는 종류당 하나만 허용하므로 둘을 그대로 같은 실행 환경에 켜면 중복 등록 실패가 날 수 있다. 시험 Handler는 Adapter 등록 실패 시 Harvest Handler도 등록하지 않는다. 본편 이관 전 사용할 Adapter와 Handler 연결을 김지훈·강민서·최명기가 맞춰야 한다. 중복 등록을 허용하도록 공용 검사를 없애는 방식으로 해결하지 않는다.

확정 목표에서 빠진 연결은 다음과 같다.

1. 월드가 배치한 **파괴 가능한 원본**과 본편 SpotId를 Player 입력에서 식별한다.
2. 정해질 파괴 조건을 서버 판정에 연결한다. 현재는 HP·타격 수·파괴 완료 조건이 없다.
3. 파괴 결과와 World 실제 승인량, 드롭 ID/수량을 연결한다. 요청한 수량을 무조건 생성하지 않는다.
4. 파괴/잔량 변경 후 드롭 생성 실패·동시 파괴·연결 이탈에서도 수지가 보존되는 확정/복구 계약을 구현한다. 순서와 API는 아직 합의하지 않았다.
5. 원본 제거/비활성·파괴 연출과 재생 시 원본 복구를 동기화한다. 매장량 숫자 회복만으로 시각 원본도 복구됐다고 보고하지 않는다.

**다시 확인할 확정 범위:** 강민서가 월드에 스폰하는 자원은 플레이어가 좌클릭 등으로 부술 수 있어 드롭을 만드는 원본이다. 월드에 처음부터 E키로 바로 줍는 자원 아이템을 배치하는 작업은 이 범위에 포함하지 않는다. 생성된 결과 드롭을 E키로 줍는 Player 기능은 유지한다.

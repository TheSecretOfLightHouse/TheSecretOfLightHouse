## 요청과 목표
- 기존 돌1개/+30 수리를 간이(나무1/+10), 일반(나무2+섬유1/+30), 보강(나무3+철1+섬유1/+50) 중 고르는 방식으로 변경한다.
- 사용자가 제안한 3종·상이한 회복량·기존 30% 제한·초과 회복 버림·실제 회복 표시·정비공 배율 적용을 승인했다.

## 진행 과정과 결정 이유
- WORK_POINTER·최명기 POINTER와 기존 점검 원문을 확인했다. 기존 미커밋 VFX/World/meta/폰트/빌드 설정·병합 기록은 보존했다.
- review-design-code-gaps로 배 수리 결정·v4·승패 결정·시스템/기술설계·문제 대장 W09와 실제 BoatRepair·인벤토리 UI·배4종을 대조했다. 수리 비용·회복량 미정과 단일 레시피 구조를 확인하고 이번 사용자 결정으로 해당 범위만 확정했다.
- 코드 소유권·네트워크 권위·씬 안전을 확인했다. Player의 기존 Relay/Router 요청을 재사용해 공용 Interaction 코드를 수정하지 않고 Arg0만 기능 처리기에서 검증한다.
- ui-ugui·unity-cli 스킬 적용. CLI 업데이트는 사용자가 거절해 beta.13을 유지했다.
- 새 레시피 배열과 서버 기준 활성 인덱스를 추가했다. 부분 투입 중 다른 인덱스 요청은 차감 전에 거절하고 완성 시 남은 재료만 소비한다. 기존 난파 시 투입분 제거 동작을 유지했다.
- Unity 에디터 SerializedObject·PrefabUtility로 배4종을 저장했다. YAML 직접 편집·씬 저장·GUID 변경 없음.
- 경계 검사에서 기존 current < max * 0.3f 비교가 정확히30/100도 거절하는 것을 재현했다. 나눗셈 비교도 같은 격리 실행에서 경계 거절을 보여 정수 배수(current*10 < max*3)로 보정했고, 29.99 거절·30 허용을 확인했다.
- 검증 초기에는 프리팹 격리 객체의 NetworkIdentity 초기화가 누락되어 Mirror SyncObject에서 예외가 났다. 검증 준비 단계에 InitializeNetworkBehaviours를 추가하고 재실행했다. 게임 코드 결함으로 분류하지 않는다.

## 검증
- Unity 6000.0.83f1 에디터 ready·Play stopped 확인. Refresh/recompile 성공, compilationFailed=false·에디터 콘솔 오류0. 기존 콘솔 이력 오류는 별도 보존했다.
- 에디터 eval·격리 프리팹에서 서버 판정 검사42항목 통과: 3종 정확 비용/회복/초기화, 부분 투입 유지·변경 거절·부족분 완성, 잘못된 인덱스 -1/3, 29.99% 거절·30% 허용, 회복 상한·정상 비용 소비, 최대내구도/미탑승/난파 거절, 난파 잠금 해제, 정비공1.5배3종과 상한.
- 위 검사는 실제 서버/클라이언트 접속 없이 Mirror 정적 active를 임시 활성화한 격리 실행이다. finally에서 서버 비활성·프리팹 언로드를 수행했다. 미스폰 객체에서 수리 효과 Rpc를 호출하므로 해당 경고가 발생했고 음향 전파 검증으로 세지 않는다.
- UI 격리14항목 통과: 실제 버튼 onClick로3종 선택, 종류별 재료 행, 내구도85/100에서 상한 반영, 서버 부분 투입 선택 강제·버튼 잠금, 잠긴 클릭 거절, 정비공 보강+75/실제+15/초과60.
- 별도 PreviewScene에서1280×900으로 렌더한 UI를 직접 확인했다. 3개 버튼·아이콘3개·수리량·회복량/초과분이 영역 안에 표시된다. 실제 게임 화면 검증은 아니다.
- 실제 Play·Relay 왕복·호스트/원격 M2·수리 음향·경제 밸런스는 미실행이다.
- 후속 UI 경계 검사2항목 추가: 정확히30%에서 정비공 보강의 실제회복+70 표시와 수리금지 문구 없음 확인(합계14항목). 배4종 저장본을 에디터에서 재조회해 동일3종 값 확인, 종료 시 Play/서버/클라이언트 모두 비활성 확인.
- 검증 플레이북 §7에 따라 읽기 전용 독립 검수를 수행했다. 코드3개·배4종에서 구체적 신규 결함 미발견. 작성 중 작업 기록 링크 경고는 파일 생성 후 재검수로 해소했고, 결정 문서·기술설계·W09·POINTER 링크 일관성을 확인했다. 실제 Play/M2 미검증으로 최종 CONDITIONAL/M0다.

## 남은 일과 차단 조건
- 같은 변경본 호스트/원격에서 인벤토리→선체수리→3종 선택/투입/완성을 실행하고 수량·내구도·선택 잠금·정비공 배율·효과음 일치를 확인한다.
- 부분 투입 후30% 미만으로 손상되면 기존대로 투입분을 유지하며 수리 금지한다. 환급·타인 배 수리 정책은 이번에 새로 확정하지 않았다.
- 서버 로직·UI 격리 검사와 실제 네트워크/경제 밸런스 검증을 구분한다.

## 2026-11-01 후속: 수리 가능 하한 20%
- 사용자 요청으로 일반 수리 하한을 30%에서 20%로 변경했다. 정확히 20%는 허용, 미만은 거절한다.
- BoatRepair 서버 판정과 InventoryChestScreen.Layout의 버튼·안내·게이지 경고색에 동일한 current * 5 대 maximum 비교를 적용해 경계 오차를 피했다. 재료 소비 이전 거절 순서와 부분 투입 유지 규칙은 보존했다.
- 배 수리 결정·기술설계 최신 요약·W09·pointer를 갱신했다. 위 최초 구현의 30% 검증 기록은 당시 이력이다.
- 검증: PowerShell single 값으로 19.99/20/20.01/29 대 최대100 및 49.99/50 대 최대250의 경계 산술 6건 통과, 변경 파일 diff 공백 검사 통과. Unity 컴파일·실제 Play/M2는 미실행이며 이전 30% 실행 검사로 이번 변경을 검증했다고 간주하지 않는다.

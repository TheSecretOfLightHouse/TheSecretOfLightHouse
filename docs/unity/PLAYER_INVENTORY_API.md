갱신일: 2026-10-17

## 1. 연결 입구

작업대 서버 처리기는 검증된 요청자 객체의 전역 타입 `PlayerInventory`를 사용한다. 별도 인터페이스는 현재 없으며 같은 Lighthouse.Runtime에서 직접 참조할 수 있다. `InventoryData`는 내부 수량 저장소이므로 직접 변경하지 않는다.

- [PlayerInventory.cs](../../Assets/01.Scripts/05.Player/Inventory/Net/PlayerInventory.cs)
- [InventoryData.cs](../../Assets/01.Scripts/05.Player/Inventory/Rules/InventoryData.cs)
- 자원 ID는 해당 인벤토리에 설정된 ResourceCatalog/ResourceDefinition의 ID다. ActorId·netId·SpotId와 다르다.
- 현재 픽업 처리기처럼 서버가 `context.Sender.identity.GetComponent<PlayerInventory>()`로 요청자 인벤토리를 찾는다. identity·컴포넌트 유효성을 먼저 검사한다. 클라이언트가 지정한 인벤토리나 로컬 플레이어 객체로 대체하지 않는다.
- 플레이어 루트의 NetworkIdentity·PlayerInventory와 서버 ResourceCatalog 연결을 확인한다. 디버그 패널의 카탈로그는 별도 필드이므로 패널 설정만으로 개인 API가 동작하지 않는다.

## 2. 서버 API

| 실제 시그니처 | 동작 | 실패·경계 |
|---|---|---|
| `[Server] int GetCount(int id)` | 서버 보유량 조회 | 저장 항목이 없으면 0. 카탈로그 검증은 하지 않음 |
| `[Server] int TryRemoveTo(int id, int requestedAmount)` | 보유량과 요청량 중 적은 만큼 차감. **실제 차감 개수** 반환 | 카탈로그 없음·미등록 ID·요청량 0 이하·보유량 없음이면 0, 무차감 |
| `[Server] bool TryAdd(int id, int amount)` | 자원을 추가하고 동기화. 드롭 획득·인출·실패 복구에 사용 가능 | 카탈로그 없음·미등록 ID·수량 0 이하·int 합계 overflow이면 false, 무변경 |

`TryRemoveTo`는 bool을 반환하는 전체 성공/실패 함수가 아니다. 보유3·요청4이면 3을 반환하고 잔량0이 된다. 이 함수는 작업대 필요량·이전 투입량·거래 ID·중복 반환 여부를 알지 못한다.

`TryAdd`는 반환 전용 함수가 아니다. 이전 차감 기록을 검사하지 않으므로 같은 반환을 두 번 호출하면 두 번 더해진다. 자동 롤백·예약·트랜잭션 API는 현재 없다.

세 함수는 서버에서 직접 호출하는 메서드다. `[Server]`는 클라이언트 호출을 서버 요청으로 전송하지 않는다. API 자체에는 송신자·거리·판 단계·난파·탑승·역할·레시피·요청 중복 검사가 없다. Interaction의 공통 검사와 기능별 검사를 통과한 서버 처리기만 호출한다. 현재 보유 상한은 자원별 `int` 범위이며 게임 규칙으로 정할 용량 제한은 구현되지 않았다.

## 3. 부분 투입 연결 규칙

사용자 결정: 다른 재료가 부족해도 가진 재료를 계속 투입한다. 목재 필요4·보유3이면 3을 넣고 필요량은1이 된다. 필요량0에서는 추가 차감하지 않는다.

1. 기존 Interaction 서버 경로에서 송신자·대상·거리·판 상태를 검증한다. 클라이언트가 지정한 플레이어의 인벤토리를 신뢰하지 않는다.
2. 작업대가 자원 종류·현재 레시피·투입 가능 상태·남은 필요량과 요청량의 양수 여부를 검사한다. Arg0/Arg1 의미는 기능별 검증·합의 대상이다.
3. 차감 요청량을 `Min(요청량, 작업대 남은 필요량)`으로 제한한다. 개인 보유량 제한은 TryRemoveTo가 처리한다.
4. 반환받은 실제 차감량만 작업대에 누적한다. 0이면 아무것도 투입하지 않는다.
5. 같은 자원 거래가 중간에 끼어들어 수지가 어긋나지 않도록 서버 처리에서 직렬화하고, 차감·누적을 하나의 성공으로 관리한다. 실패 시 실제 차감량을 복구하고 TryAdd 성공 여부를 확인한다. 기존 3개 API만으로 이 보장이 자동 제공되지는 않는다.
6. 제작 완료 시 작업대에 이미 쌓인 재료를 소비한다. 개인 인벤토리를 다시 차감하지 않는다.

호출 형태 예시(실제 작업대 구현은 아니며 앞뒤 상태 검증·실패 복구는 생략):

```csharp
int acceptedRequest = System.Math.Min(requestedAmount, remainingNeeded);
int removedAmount = inventory.TryRemoveTo(resourceId, acceptedRequest);
// Apply only removedAmount to the validated workbench transaction.
```

| 입력 | 결과 |
|---|---|
| 작업대 필요4·개인3·요청4 | 실제 투입3·개인0·작업대 필요1 |
| 작업대 필요1·개인5·요청4 | 실제 투입1·개인4·작업대 필요0 |
| 작업대 필요0·개인5·요청4 | 무차감·개인5 유지 |

## 4. 책임 경계·미합의

**2026-10-17 추가 결정:** 작업대와 등대 모두 마피아만 인출 가능하며, 등대 수리에 이미 반영된 자원도 회수하고 해당 진행도를 되돌린다. 개인 TryAdd는 회수 자원의 지급 수단일 뿐 진행도를 감소시키지 않는다. 등대 서버 처리기가 회수 가능 자원·수량과 진행도 감소를 계산하고 개인 지급과 함께 확정해야 한다. 인출 시 등대 HP는 감소하지 않는다. 보상 처리와 단계별 회수 대상/경합은 [공유 결정](../design/shared-inventory-decisions.md)의 남은 계약을 따른다.

**2026-10-17 사용자 결정:** [공용 인벤토리 규칙](../design/shared-inventory-decisions.md)에 따라 공용 인출은 마피아만 가능하다. 시민은 자신이 투입한 자원도 꺼낼 수 없다. 작업대 서버 처리기가 역할을 검사한다. 투입 실패 시 개인 수량 복구는 인출과 다르며 시민에게도 유실 없이 적용해야 한다.

| 최명기 제공 | 김지훈 처리기에서 연결·관리 |
|---|---|
| 개인 수량 조회·부분 차감·추가와 Owner 동기화 | 작업대/등대의 필요량·누적·투입 승인·결과 적용 |
| 실제 차감 개수 및 추가 성공 여부 | 재전송 중복 방지·실패 복구·복구 실패 처리·반환 한 번 보장 |
| 개인 자원 데이터 | 인출 권한·반환 대상·제작 취소·레시피 변경·완성 모듈 보관 위치 |

이 표는 기존 소유권에 따른 연결 안내이며 김지훈의 동의·전달 완료를 뜻하지 않는다. W08의 인출 역할과 수리 반영 자원 회수 범위는 결정됐고, 나머지 제한·취소 정책과 N09 거래 계약은 추가 확인이 필요하다. 작업대·등대가 실패 복구를 보장할 수 없는 경우 구현 전에 양쪽 API 확장을 합의한다.

등대도 같은 개인 API를 사용할 수 있지만 수리 자원·진행도 환산은 등대가 관리한다. [승패·투표 결정](../design/win-vote-decisions.md)에 따라 최후 전투 자원 투입은 새 진행도를 올리고 HP를 회복하지 않는다. 수량형 자원 API는 개별 모듈의 부식·장착·소유 상태 저장 기능이 아니다.

## 5. 동기화·검증

- PlayerInventory는 SyncMode.Owner다. 성공한 변경은 SyncDictionary로 소유자에게 전달된다. 소비자가 SyncDictionary를 직접 수정하지 않는다.
- 로컬 표시에는 Counts·GetSyncedCount·ResourceCountChanged·InventoryReset이 있다. 서버 판정에는 GetCount를 사용한다. UI 최초 표시 때 현재 Counts를 읽고 이후 이벤트를 반영한다.
- ContextMenu 테스트와 InventoryDebugPanel은 본편 작업대 API가 아니다. 디버그 패널은 개인 시험 목표를 관리하며 작업대에 실제 자원을 저장하지 않는다.
- 사용자 실행 보고: 최초 단순 차감 버튼이 반복 차감하는 문제 확인. 이후 서버 잔여 필요량을 추적하도록 수정했으나 수정 후 재시험 결과는 미확인이다.
- 필요 시험: 부분 투입·필요량0 무차감·미등록 ID/0/음수 거절·추가 overflow 무변경·실패 복구 수지·중복 요청/반환·동시 투입·원격 Owner 수량 일치/타인 수량 비노출.
- 이번 API 문서 작성에서 Unity 컴파일·Weaver·Play·M2/M3는 실행하지 않았다.

## 6. 연결 전 확인표와 수지 검증

아래는 연결 요구사항과 시험 기준이며 구현·담당자 합의 완료 기록이 아니다.

| 확인 항목 | 현재 보장과 남은 계약 |
|---|---|
| 실패 구분 | 차감 0은 원인을 구분하지 않는다. UI 실패 사유가 필요하면 처리기가 선행 검사하거나 양쪽이 결과 타입 확장을 합의한다 |
| 한 번의 투입 | 동일 요청 번호 재전송과 새 요청 번호 반복을 구분한다. 공용 Router의 중복 검사만으로 서로 다른 번호의 같은 거래를 막는다고 가정하지 않는다 |
| 동시 요청 | 매 요청마다 현재 남은 필요량을 다시 계산한다. 차감과 작업대 반영 사이에 await·코루틴·후속 프레임을 넣는다면 예약/확정 계약이 먼저 필요하다 |
| 실패 복구 | 성공 누적이 없을 때 실제 차감량만 원래 요청자에게 복구한다. TryAdd=false이면 성공/복구 완료를 응답하지 않고 복구 대기 상태와 재시도 책임을 정한다. 재시도 중복도 차단한다 |
| 인출 | 서버가 비공개 역할과 공용 잔량을 검사한다. 개인 TryAdd 성공과 공용 차감을 함께 확정한다. 시민 실패 복구를 정상 인출 경로로 우회하지 않는다 |
| 기록 | v4 §7.2의 투입·인출 서버 기록은 이 개인 API에 없다. 처리기 측 거래 식별·승인량·성공/복구 결과와 공개 범위를 합의한다 |
| 수명 | 현재 PlayerInventory에 서버 수량 초기화·저장/복원 API가 없다. OnStopLocalPlayer의 InventoryReset은 UI 알림이며 서버 _data 초기화가 아니다. 판 종료/새 판의 플레이어 객체 파괴·재생성 경로를 확인한다 |
| 정보 수신 | Counts는 동기화된 읽기용 뷰이고 서버 판정 원본은 _data다. 이벤트 구독은 OnStartLocalPlayer 이후이며 초기 스냅샷은 직접 읽는다. Owner 동기화는 신뢰된 호스트가 서버 수량을 아는 것까지 차단하지 않는다 |

N09 거래 보존, W08 인출 한도·경합, R22 소환 후 개인 화물 처리는 여전히 별도 계약이다. 위 표로 미정 정책을 임의 결정하지 않는다.

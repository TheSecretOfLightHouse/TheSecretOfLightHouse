# 기능 담당자의 서버·클라이언트 협업

이 게임은 4인 리슨 서버다. 각 담당자가 자기 기능의 서버 판정·동기화·클라이언트 표현을 함께 맡는다. 실제 경로·계정은 [담당표](../CODE_OWNERSHIP.md), 어셈블리는 [아키텍처](../04-architecture.md)를 따른다.

## 1. 작업 위치

`Assets/01.Scripts/{번호.도메인}/{기능}/` 아래 필요한 `Rules/`, `Net/`, `Server/`, `View/`를 둔다. 네 층은 담당자를 나누는 단위가 아니며, 공용 접속 담당과 기능 담당의 경계는 [기능 사이의 경계](../CODE_OWNERSHIP.md#2-기능-사이의-경계)를 따른다.

도메인별 담당자와 범위(시스템&UI·AX 지원 포함)는 [담당표 §1](../CODE_OWNERSHIP.md#1-담당표)이 단일 기준이다. 이 문서는 담당자가 서버·클라이언트를 함께 맡는 협업 절차만 다룬다.

## 2. 리슨 호스트 경계

서버 판정 코드는 일반 빌드의 Lighthouse.Runtime에 포함하며 `UNITY_SERVER` 전용으로 제외하지 않는다([아키텍처 §3](../04-architecture.md#3-어셈블리)). 호스트는 서버와 로컬 클라이언트가 동시에 활성인 프로세스다. `isServer`와 로컬 클라이언트 여부를 별도로 판정하고, 서버 변경과 시각 연출이 호스트에서 두 번 실행되지 않는지 확인한다. 클라이언트가 공유 상태를 확정하지 않는다. 역할·투표 등 비밀 정보는 허용 대상에게만 보낸다.

`Server/`에 파일을 놓는 것만으로 서버 측 실행 제한이 생기지 않는다. Mirror 서버 콜백·속성·호출 경로로 판정 책임을 보장한다. 현재 혼합 MonoBehaviour 코드는 위치 이관 후에도 기존 구현 상태로 표시한다.

## 3. 교차 기능 연결

기능 사이의 생성·판정·소비 책임은 [기능 사이의 경계](../CODE_OWNERSHIP.md#2-기능-사이의-경계) 표가 기준이다.

다른 영역 변경 전 [영역 변경 안내](../CODE_OWNERSHIP.md#4-다른-영역을-수정해야-할-때)로 대상·담당·이유·영향·검증을 알리고 필요한 합의를 확인한다. 이미 승인된 범위를 반복 확인하지 않는다.

## 4. 인수 기록 틀

| 항목 | 기록할 내용 |
|---|---|
| 담당 | 생산자·소비자의 실제 담당자와 경로 |
| 요청 | 송신자·대상·입력·중복 처리 계약 |
| 서버 | 권한·상태·거리·쿨타임 검증과 결과 변경 |
| 동기화 | 공개/개인 데이터, 최초 접속·재접속·이탈 처리 |
| 표현 | 입력과 결과 표시, 호스트 이중 실행 방지 |
| 연결 | 실제 씬·프리팹·등록·인터페이스 |
| 검증 | 호스트/원격 각각의 재현·관찰 결과와 미실행 |
| 남은 작업 | 미구현·미연결·미검증을 구분 |

4인 안정화는 김지훈이 리드하며, 각 담당자가 자신의 서버·클라이언트 관찰과 복원 검증 결과를 제공한다. [멀티플레이 테스트](../ai/04_MULTIPLAYER_TEST_PROTOCOL.md)를 따른다.

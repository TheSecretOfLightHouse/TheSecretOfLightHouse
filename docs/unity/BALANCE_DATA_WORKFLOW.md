# 밸런스 데이터 작업

규칙 우선순위는 최신 사용자 결정 → [제공된 v4](../design/references/game-design-v4.md)이며, 문서 기준의 상세는 [AI 작업 문서](../ai/README.md)를 따른다.

## 1. 기준과 현재 구현

게임 내용과 수치의 의도는 [기획서](../design/references/game-design-v4.md)를 유지한다. 문서 정리를 이유로 수치나 데이터 구조를 바꾸지 않는다. 실제 값이 코드·인스펙터·에셋 중 어디에 있는지 먼저 확인하고 변경한다.

현재 `Assets/01.Scripts/02.World/Harvest/Rules/ResourceDefinition.cs`는 ID·이름·아이콘·희귀도·획득 프리팹을 담는 ScriptableObject다. `05.Player/Movement/Rules/MoveConfig.cs`는 이동 배율과 입력 잠금을 담는 struct이며 SO가 아니다. 통합 데이터베이스나 모든 밸런스 SO가 이미 존재한다고 가정하지 않는다. 배치와 구현 규칙은 [아키텍처](../04-architecture.md)와 [코딩 컨벤션](../coding-convention.md)을 따른다.

## 2. 데이터 책임 기록

| 항목 | 기록할 내용 |
|---|---|
| 대상 | 실제 타입·필드·에셋 경로 |
| 소유 | 담당 기능과 확인된 담당자 |
| 값 | 기존 값·변경 값·단위·허용 범위 |
| 이유 | 플레이 관찰·재현 조건·설계 의도 |
| 영향 | 서버 판정·로컬 표현·다른 수치·저장 데이터 |

정의 에셋과 런타임 상태를 구분한다. 게임 진행 중 변하는 수량·진행도 등의 상태를 공유 정의 SO에 덮어쓰지 않는다. Play Mode에서 바꾼 에셋 값이 남았는지 종료 후 확인한다.

## 3. 값과 구조 변경

값 조정은 기존 요청 범위와 담당 책임을 따른다. 다른 시스템에 영향을 주는 값은 소비자를 함께 확인한다. 필드 삭제·이름·타입 변경과 enum 재배열은 직렬화된 데이터에 영향을 줄 수 있다. 이름 변경에는 기존 값을 보존하는 마이그레이션을 검토하고, 변경 전후 모든 관련 에셋을 확인한다. 구조 변경의 합의 절차는 [저장소 지침](../../AGENTS.md)을 따른다.

## 4. 검증과 기록

값만 바꿔도 실제 인스펙터와 런타임에서 소비되는 값을 확인한다. 공유 판정에 영향을 주면 호스트·원격 클라이언트에서 같은 결과인지 확인한다. 실행하지 않은 수치를 검증된 밸런스로 쓰지 않는다. 문서와 데이터가 다르면 현재 구현값과 설계 의도의 차이를 기록하고 의도적인 조정인지 확인한다.

변경 기록에는 대상, 이전/이후 값, 근거, 영향, 실제 검증, 되돌릴 조건을 남긴다. 자세한 실행 근거는 [검증 플레이북](../ai/03_VERIFICATION_PLAYBOOK.md)을 따른다.

수치 조정 제안은 [밸런스 이슈 양식](../../.github/ISSUE_TEMPLATE/03-balance.yml)으로 등록하고, 커밋 타입은 [커밋 컨벤션 §2](../commit-convention.md#2-타입)를 따른다(의도한 밸런스 수치 조정은 `chore`, 수치가 기획서와 달라 바로잡으면 `fix`).

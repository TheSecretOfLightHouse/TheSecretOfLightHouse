# 네트워크 권위 규칙

규칙 우선순위는 최신 사용자 결정 → [승패·투표 결정](../design/win-vote-decisions.md) → [제공된 v4](../design/references/game-design-v4.md)이며, 새 결정과 충돌하는 v4 규칙은 적용하지 않는다. 문서 기준의 상세는 [AI 작업 문서](../ai/README.md)를 따른다.

기존 4인 리슨 서버(호스트 1 + 원격 클라이언트 3)와 Mirror 96.0.1을 유지한다. 게임 규칙은 위 기준 순서, 현재 구조는 [아키텍처](../04-architecture.md), 코드 작성은 [코딩 컨벤션](../coding-convention.md)을 따른다. 아래는 작업 검토 기준이며 각 기능의 구현 완료 목록이 아니다.

## 1. 판단 기준

값이 플레이어마다 다르면 게임 결과가 바뀌는지 확인한다. 결과에 영향을 주는 상태는 서버가 판정하고 클라이언트는 요청·표현을 담당한다. 호스트는 서버와 클라이언트 역할을 함께 수행하므로 로컬 실행 성공만으로 권위 경계를 검증할 수 없다.

| 구분 | 등대 프로젝트에서 검토할 대상 |
|---|---|
| 서버 판정 | 채집·획득 결과, 인벤토리 변화, 등대 수리 진행, 투표·역할·승패 등 공유 게임 규칙 |
| 서버 기준 상태 | 게임 진행·시간, 플레이어와 배의 내구도·난파·승선 등 판정 상태, 공유 자원·상호작용 결과 |
| 소유 클라이언트 권위 | 자기 플레이어·배의 이동 위치와 회전(NetworkTransform ClientToServer). 서버는 보고 위치를 판정 입력으로만 쓴다(§4) |
| 클라이언트 표현 | 입력 수집, 카메라, UI, 조명·날씨 표현, 소리·이펙트 |

플레이어·배 이동의 ClientToServer 동기화는 2026-10-13 결정(N07)이다. 서버 권위 이동으로 바꾸려면 새 사용자 결정이 필요하며 개별 작업에서 동기화 방향을 임의 변경하지 않는다. 비밀 역할이나 개인 정보는 필요한 대상에게만 전달한다.

## 2. 요청과 동기화

| 흐름 | Mirror 수단 | 검토 |
|---|---|---|
| 클라이언트 요청 | `[Command]` | 호출자, 소유권, 거리·범위(클라이언트 보고 위치 기준, §4), 현재 상태, 쿨타임 검증 |
| 지속 상태 | `SyncVar`, 동기화 컬렉션 | 늦은 접속 시 현재 상태 복원 |
| 일회 표현 | `ClientRpc` | 중복 실행·호스트 이중 재생 방지 |
| 개인 응답 | `TargetRpc` | 수신 대상과 비밀 정보 노출 확인 |
| 서버 객체 수명 | `NetworkServer.Spawn/Destroy` | 프리팹 등록·생성/제거 책임 확인 |

`requiresAuthority = false`로 요청 경로를 열면 서버에서 호출자를 검증한다. UI나 클라이언트 콜백에서 권위 상태를 확정하지 않는다. 지속 상태를 일회 Rpc만으로 전달해 늦은 접속자가 놓치게 하지 않는다.

투표·확인·소환 요청은 송신자와 ActorId, 시민/마피아 역할, 요청별 허용 상태, 투표 횟수·의식 잠금 또는 10초 소환 권리를 서버에서 검증한다. 난파 중에도 시민 투표는 가능하지만 마피아의 확인·소환은 불가하다. 마지막 확인권이 소진돼도 이미 받은 유효한 소환 권리를 횟수 0이라는 이유로 거부하지 않는다. 승패 조건의 제공자와 최종 확정 책임은 [기술설계 §6](../03-technical-design.md#6-상태와-실행값)을 따른다. 확정된 게임 결과는 한 번만 종료하며 같은 판정 시점의 경합 우선순위는 [문제 대장](../07-design-issue-register.md)의 미결 사항으로 유지한다.

### 2.1 투표·확인 정보의 수신 범위

아래는 [새 결정 §7](../design/win-vote-decisions.md#7-정보-공개-범위--n04r16)의 공개 계약이다. 서버 판정에 필요한 값이라도 공개 동기화 상태에 넣는 근거가 되지 않는다.

| 정보 | 서버·클라이언트 전달 경계 |
|---|---|
| 개인 투표와 잔여 투표권 | 서버가 관리하고 해당 시민 본인에게만 필요한 상태를 전달 |
| 봉인·심해 게이지 | 서버 판정에서만 사용, 마피아를 포함한 모든 플레이어에 비공개 |
| 확인 성공과 10초 소환 권리·확인 기회 소진 | 마피아의 개인 응답/상태. 시민에게 성공·소진 사실을 알리지 않음 |
| 확인 실패 결과 | 중복되지 않는 무작위 시민의 무고함을 공개. 비밀 투표나 역할 명단 전체는 보내지 않음 |

직군·부식·환영 섬·힌트 등 다른 정보의 수신 계약은 v4와 문제 대장 N01~N06·N15를 별도로 확인한다. 이 표로 해당 미결 항목 전체가 해결됐다고 판단하지 않는다. 호스트는 서버 상태를 보유하므로 이 경계는 호스트 운영자의 메모리 접근 차단을 보장하지 않는다.

### 2.2 JH02 상호작용 요청 경로

2026-10-13 김지훈 결정이다. 어떤 요청을 JH02(김지훈 Interaction) 경로로 보내고 어떤 요청을 기능 자체 Command로 보낼지 정한다. 두 경로 모두 §2의 서버 검증을 적용한다.

| 요청 | 경로 | 예 |
|---|---|---|
| 월드 대상이 있는 `InteractionAction` | JH02. 플레이어 프리팹의 Interaction 컴포넌트가 대상을 탐지·선택하고 Relay로 요청 | 채집, 작업대 투입·인출·레시피, 모듈 장착·수리, 배 수리, 난파 동료 구조, 픽업, 특수 섬, 유령선 조사 |
| 부식 검사 능력 | JH02. 검사와 사용권 소비가 같은 요청 번호로 한 번만 처리되게 함 | 직군 검사 능력 |
| 자기 이동과 승하선 | 기능 자체 Command | `BoatController`의 승하선 |
| 투표·확인·소환 | 기능 자체 Command | `VotingNetworkController` |
| 사격, 대상 없는 직군 능력 | 기능 자체 Command | 대포 발사 요청 |

- Player는 상호작용 키 입력만 알린다. 대상과 Action은 Interaction이 정한다. 메뉴에서 동작을 고르는 경우(작업대 등)에는 UI가 대상·Action·인자를 Relay에 직접 넘긴다.
- 대상 식별(2026-10-14 결정, 2026-10-13 TargetRegistry 발급안을 대체): 네트워크 객체 대상은 Mirror netId로 식별한다. 판 하나가 서버 실행 한 번이라 netId가 판 안에서 재사용되지 않기 때문이다. 대상 프리팹에는 등록하지 않는 InteractionTarget 표식만 붙인다. 네트워크 객체가 아닌 대상(각 PC에서 만드는 채집 지점 등)은 클라이언트가 대상 종류와 기존 ID(예: `SpotId`)를 보내고 서버 변환기가 해당 기능의 조회 계약으로 확인한다. 어느 대상이 네트워크 객체인지는 해당 기능 담당이 정한다. 상세는 [지훈 시스템 설계 §5.1](../design/jihun-system-design.md#51-식별과-전송).
- 채집·구조 같은 지속 상호작용은 Interaction이 세션 시작·취소·완료와 이탈·대상 소멸 시 해제를 맡는다. 소요 시간과 취소 조건은 각 기능이 정한다.
- 새 `InteractionAction`이 필요하면 값·인자 의미·오류를 김지훈과 합의한 뒤 추가한다. 기존 값의 번호는 바꾸지 않는다.
- 위 표에 없는 새 요청은 구현 전에 경로를 김지훈과 확인한다.

## 3. 상태와 표현 분리

서버가 확정한 시간·날씨·판정 위치를 바탕으로 클라이언트가 표현을 만든다. 플레이어·배의 위치는 예외로 소유 클라이언트가 정한다(§4). 렌더링 색이나 파티클을 매 프레임 공유 상태처럼 보내지 않는다. 피해·상호작용 범위에 영향을 주는 위치·시점은 표현으로 보이더라도 판정 계약을 따른다.

의식 시작의 게임 기한 정지와 최후 전투의 기한 제거를 World 시간 전체의 정지/제거로 확대하지 않는다. 숨은 단계 수리도와 전투 수리 진행도, 현재 HP와 최대 HP도 분리해 동기화·표시한다. 최후 전투 자원 투입으로 HP 회복·새 보상이 생기지 않는지 확인한다.

### 3.1 접속 단절

[결정 §8](../design/win-vote-decisions.md#8-접속-단절과-재접속--n11n12)(2026-10-13 변경)에 따라 판 진행 중 한 명이라도 끊기면(호스트 포함) 판을 종료한다. 서버가 이탈을 감지하면 전원에게 종료 사유를 보내고 판을 끝낸다. 로비 이탈은 자리만 비우고, 판 시작 후 새 접속은 거절한다. 판 시작은 4명 전원 준비 시 자동이며, 서버가 4명 모두의 로딩 완료를 확인한 뒤 입력을 연다. 그래서 각 기능은 단절된 참가자의 상태를 보존할 필요가 없고, 판 종료 정리 경로만 따른다. 난파 중 시민 봉인·오투표 누적은 계속한다. 재접속은 10/25 이후 선택 범위다. JH07이 이 흐름을 구현했다(2026-10-13, 같은 PC 4인 M2 검증). 클라이언트는 나가기 전에 서버에 나감 요청을 보내므로 서버는 직접 나감과 연결 끊김을 구분해 종료 사유와 로그에 남긴다. 판 시작 후 접속은 인증 단계(`SessionJoinAuthenticator`)에서 사유와 함께 거절한다. 로비 설정이 없는 시험 씬은 JH01처럼 접속 즉시 플레이어를 만들고 이탈해도 판을 끝내지 않는다.

## 4. 이동과 물리 권위

2026-10-13 사용자(김지훈) 결정으로 [문제 대장 N07](../07-design-issue-register.md)의 이동 위치 권위를 정했다. 아래 4.1은 결정, 4.2는 담당 간 합의 대기 제안이다.

### 4.1 결정된 규칙

| 규칙 | 내용 |
|---|---|
| 이동 권위 | 플레이어 캐릭터와 배는 소유 클라이언트가 움직이고 NetworkTransform(ClientToServer)으로 보고한다 |
| Rigidbody 모드 | 한 물체를 PC마다 다르게 둔다. 움직이는 소유 PC만 Dynamic, 서버와 다른 클라이언트는 Kinematic으로 보고 위치를 따른다. 이동 로직을 모드별로 따로 두지 않고 권위 여부만 검사한다 |
| 실행 위치 | 힘을 주는 코드(부력·바람·해류·입력)는 소유 PC 한 곳, 결과를 확정하는 코드(피해·난파·픽업·자원)는 서버 한 곳에서만 실행한다. 보고 위치를 따르는 PC에서 같은 계산이 돌아 판정이 중복되지 않게 한다 |
| 신뢰 한계 | 서버 거리·범위 검증은 보고 위치와 보간 지연을 전제로 한다. 위치 조작 치팅은 지인 4인 플레이 범위에서 허용 한계로 둔다 |

현재 `BoatController`·`PlayerController`는 위 Rigidbody 모드 전환을 따른다. Kinematic 물체에는 `OnCollision*` 콜백과 정확한 속도 값을 기대하지 않는다. 프로젝트 물리 설정의 Contact Pairs Mode는 기본값이므로 서버에서 원격 배의 충돌 이벤트가 오지 않는다.

### 4.2 합의 대기 제안

아래는 김지훈의 제안이며 관련 담당이 확인하기 전에는 확정 규칙이 아니다. 확인된 항목부터 4.1로 옮긴다.

| 항목 | 제안 | 확인 담당 |
|---|---|---|
| 서버 판정 수단 | 피해·범위 판정은 충돌 이벤트가 아니라 서버의 거리·겹침 검사(`Physics.OverlapSphere`·trigger)와 쿨다운으로 한 번만 적용 | 최명기·박태욱·강민서 |
| 몬스터 공격·대포 명중 | 서버 판정. 대포 발사는 요청, 탄과 명중은 서버 | 박태욱·최명기 |
| 암초 충돌 | 서버 겹침 검사 | 최명기 |
| 파도 충격 | 배 주인 PC가 감지해 보고, 서버가 날씨 단계·쿨다운·피해 상한을 검증. 거짓 미보고는 허용 한계 | 강민서·최명기 |
| 토네이도 흡입 | 서버 거리 판정 | 강민서 |
| 배끼리 충돌 | 피해 없음, 물리적으로 서로 밀지 않음. 플레이어 간 피해(R24) 기획 결정 전까지 | 기획·최명기 |
| 서버 강제 이동 | 자동 구조·하선·경계 복귀는 `NetworkTransformBase.ServerTeleport`만 사용. 호스트 모드 동작은 실행 확인 필요 | 최명기·김지훈 |
| 경계 검사 | 해역·폭풍벽 밖 보고 위치는 서버가 되돌림. 속도 검사는 시간 여유 시 | 강민서·김지훈 |
| 허용 오차 | 상호작용·공격 범위 여유를 설정값으로 두고 시험값에서 시작, 4인 테스트 후 조정 | 각 기능 담당 |

## 5. 완료 근거

호스트와 원격 클라이언트에서 같은 결과인지(특히 원격 플레이어 배의 피해가 호스트와 같게 들어오는지), 권한 없는 요청이 상태를 바꾸지 않는지, 중복 입력과 연결 해제 시 결과가 일관되는지 확인한다. 지원 범위에 포함된 늦은 접속·재접속은 별도로 확인한다. 코드 검토와 실제 다인 실행 결과를 구분해 [검증 플레이북](../ai/03_VERIFICATION_PLAYBOOK.md)에 맞춰 기록한다.

## 6. 기능 소유와 실행 경계

기능별 담당과 공용 접속 담당의 경계는 [담당표](../CODE_OWNERSHIP.md#1-담당표)와 [기능 사이의 경계](../CODE_OWNERSHIP.md#2-기능-사이의-경계)를 따른다. `Server/`도 일반 빌드에 포함한다([아키텍처 §3](../04-architecture.md#3-어셈블리)). 호스트는 서버와 로컬 클라이언트가 동시에 활성임을 고려해 중복 판정·이중 연출을 검증한다.

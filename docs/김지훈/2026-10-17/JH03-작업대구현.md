## 결과
- [등대·작업대 모듈 결정](../../design/lighthouse-module-decisions.md)의 작업대 범위를 구현했다. 공유 작업대 1개, 레시피 1개씩, 자원 투입 전에는 레시피 변경 가능·투입 뒤 잠금, 남은 필요량까지만 차감, 완성 시 작업대에 종류별 보관, 레시피별 존재 개수 상한.
- 에디터 호스트 단독 M0 자동 시험 33/33 PASS. 2인 M2(동시 투입 경합)는 사용자가 집에서 진행하기로 했다(미실행).

## 수행 과정과 결정 이유
- 단일 씬 모드(`IsSessionFlowEnabled=false`)는 판 단계가 `Lobby`에 머물러 라우터가 `NotInProgress`로 거절한다. 그래서 JH07 흐름(오프라인 → 로비 → 게임 씬)으로 시험하며 게임 씬을 `JH03TestScene`으로 둔다.
- 처리기는 동작당 1개만 등록되므로 `ModuleInteractionHandler` 하나가 `SelectRecipe`·`Deposit`을 받아 대상 컴포넌트(`WorkbenchNet`)로 분기한다. 등대·표류 모듈은 JH04·JH05에서 같은 처리기에 분기를 더한다. 모듈 기록(`ModuleLedger`)도 이 처리기가 판마다 새로 만든다(존재 상한이 작업대·등대·표류를 모두 세기 때문).
- 모듈 기록은 첫 투입 때 만든다(선택만 하고 투입 전이면 아직 존재하지 않음). 상한은 선택 때와 첫 투입 직전 두 번 확인한다.
- 처리 순서: 상한·남은 필요량 확인 → `PlayerInventory.TryRemoveTo` → 실제 차감량만 누적. 차감 0이면 아무 상태도 바꾸지 않고 `Rejected`. 완성 때 추가 차감 없음.
- 네임스페이스: 규칙대로면 `Lighthouse.Lighthouse.Workbench`이지만, 이 이름이 생기면 `Lighthouse.*` 안에서 `Lighthouse.Monsters...`처럼 전체 이름을 쓰는 코드가 `Lighthouse.Lighthouse`로 해석되어 컴파일이 깨진다(박태욱 `MonsterCondition.cs` 13·18행에서 실제 확인). 타인 코드를 고치지 않으려고 도메인 단계를 빼고 `Lighthouse.Workbench.*`·`Lighthouse.Modules.*`로 했다. 등대 본체도 `Lighthouse.Lighthouse`를 피해야 한다.
- 시험 플레이어는 최명기 `Myeongki/Offline.unity`와 같은 `Tech 1` 프리팹(인벤토리·`PlayerController`·Relay 포함).

## 2026-10-17 추가: 첫 투입 확인과 제작 버튼(사용자 결정)
- 사용자 요청: ① 투입을 시작하면 레시피를 바꿀 수 없다는 것을 알려야 한다. ② 재료를 다 넣으면 바로 생성하지 말고 제작 버튼을 눌러 생성한다(동기화 포함).

- 화면: 가운데 아래 `제작` 버튼(재료가 다 차야 켜짐), 진행 제목 아래 안내 문구(바꿀 수 있음/고정됨/제작 가능). 레시피에 첫 자원을 넣을 때 "레시피가 고정됩니다" 확인창(넣기/취소, Esc는 확인창만 닫음).

- 자동 시험 갱신: 덜 찼을 때 제작 거절, 다 차도 보관 0 유지, 제작 후 완성, 두 액터 동시 제작(`CRAFT_RACE`).
- 검증(실행함): 컴파일 오류 0. M0 37/37 PASS. M2(에디터 호스트 + 재빌드 클라이언트) 호스트 37/37·클라이언트 7/7, `CRAFT_RACE` 호스트 Rejected·클라이언트 Success로 정확히 1회, 클라이언트 로그 예외 0. 확인창 표시는 호스트 캡처로 확인(취소해서 투입 없음).

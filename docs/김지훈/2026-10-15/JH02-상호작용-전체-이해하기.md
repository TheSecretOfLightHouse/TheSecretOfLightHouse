2026-10-14 기록 4개(설계 검증 → A-1 → A-2 → 문서 동기화)는 "무엇을 왜 바꿨는지"를 시간 순서로 적은 작업 일지라 처음 보는 사람이 전체를 파악하기 어렵다. 이 문서는 **지금 코드가 실제로 어떻게 동작하는지**를 처음부터 끝까지 한곳에 정리한다. 세부 결정 이유와 검증 기록은 맨 아래 [기존 기록](#12-기존-기록과-더-읽을-문서)에서 찾는다.

## 1. 한 줄 요약

> 플레이어가 E키를 누르면, **"이 대상에게 이 동작을 하고 싶다"는 요청서**를 서버에 보내고, 서버가 **누가·언제·어디서·무엇을** 했는지 검사한 뒤 그 동작을 맡은 **기능 코드(처리기)** 에 넘겨 결과를 적용하고, 결과를 **보낸 사람에게만** 돌려주는 공용 통로다.

비유하면 **민원 창구**다.

| 민원 창구 | JH02 |
|---|---|
| 민원인 | 플레이어 PC |
| 민원 신청서 | `InteractionRequest`(요청) |
| 신분 확인(신청서에 적힌 이름이 아니라 신분증으로) | 서버가 **실제로 요청이 들어온 연결**로 누구인지 판단(ActorId) |
| 접수 번호표 | 요청 번호(Sequence) |
| 접수 창구 직원(공통 검사) | `InteractionRouter` |
| 담당 부서(실제 업무) | 기능 처리기(채집·작업대·배 수리… 각 담당자가 만듦) |
| 처리 결과 통지 | `InteractionResult`(본인에게만) |
| 오래 걸리는 업무(대기 번호 들고 기다림) | 세션(길게 누르기: 채집·구조) |

JH02는 **창구와 규칙**만 만든다. "채집하면 뭘 얼마나 주는지" 같은 실제 업무는 각 기능 담당자가 처리기로 만든다.

## 2. 용어 사전 (먼저 읽기)

| 용어 | 뜻 | 예 |
|---|---|---|
| **ActorId** | 서버가 판 안에서 플레이어 한 명에게 붙인 번호(1~4). 로비 접속 순서대로 정해진다 | 호스트 = Actor 1, 원격 = Actor 2·3·4 |
| **netId** | Mirror가 네트워크 객체(배·작업대 등)마다 붙이는 번호(`uint`). 서버를 끄기 전까지 재사용되지 않는다 | 배 `netId = 15` |
| **Action** | 하려는 동작 종류. `InteractionAction` enum | `Harvest`(채집), `PickUp`(줍기), `RepairBoat`(배 수리) … |
| **Arg0, Arg1** | 요청에 붙는 **추가 숫자 두 칸**(`int`). 동작마다 뜻이 다르다. [7장](#7-arg0-arg1은-무엇인가) | 예: 넣을 개수, 고른 레시피 번호 |
| **요청 번호(Sequence)** | 플레이어마다 1, 2, 3… 으로 올라가는 번호. 같은 요청이 두 번 처리되지 않게 한다 | Actor 2의 3번째 요청 = Sequence 3 |
| **대상(Target)** | 상호작용하려는 물체 | 배, 작업대, 채집 지점 |
| **표식 `InteractionTarget`** | "이 물체는 상호작용할 수 있다"를 표시하는 컴포넌트. 허용 Action·범위를 가진다 | 배 프리팹에 붙임 |
| **처리기(Handler)** | 실제 업무를 하는 기능 코드. 한 번에 끝나는 것은 `IInteractionHandler`, 시간이 걸리는 것은 `IInteractionSessionHandler` | 줍기 처리기, 채집 세션 처리기 |
| **세션(Session)** | 몇 초 동안 계속되는 상호작용(길게 누르기). 서버가 매 프레임 "계속해도 되는지" 확인한다 | 채집 1.5초 |
| **원장(Ledger)** | 서버가 플레이어별로 "다음에 받을 요청 번호"와 "마지막 결과"를 적어 두는 장부 | `RequestLedger` |
| **adapter** | 네트워크 객체가 **아닌** 대상(각 PC가 따로 만드는 채집 지점 등)을 서버가 확인하게 해 주는 번역기. 해당 기능 담당자가 만든다 | 채집 지점 adapter(강민서, 미구현) |
| **Command** | Mirror 기능. 클라이언트 → 서버 호출. **자기 플레이어 객체에서만** 보낼 수 있다 | `CmdRequest` |
| **TargetRpc** | Mirror 기능. 서버 → **특정 클라이언트 한 명** 호출 | `TargetReceiveResult` |
| **판 단계(Phase)** | `Loading`(로딩 중) → `InProgress`(진행 중) → `Ended`(종료). JH07이 관리 | 요청은 `InProgress`일 때만 받는다 |

## 3. 전체 그림

```text
 ┌──────────────── 플레이어 PC (클라이언트) ────────────────┐
 │                                                          │
 │  [E키]                                                   │
 │    │  PlayerController.InteractionRequested (본편)       │
 │    │  또는 DevInteractionKeyInput (시험)                 │
 │    ▼                                                     │
 │  PlayerInteractionInput ──▶ InteractionSelector          │
 │                              │ "가장 가까운 대상" 선택    │
 │                              ▼                           │
 │                         InteractionRelay                 │
 │                              │ 요청서 작성 + 번호 붙임    │
 └──────────────────────────────┼───────────────────────────┘
                                │ CmdRequest(요청)   ← Command
 ┌──────────────── 서버(호스트 PC) ─┼────────────────────────┐
 │                              ▼                           │
 │                     InteractionRouter.Process            │
 │   ① 누구? (연결 → ActorId)                               │
 │   ② 판 진행 중?                                          │
 │   ③ 요청 번호 맞나? ── RequestLedger                     │
 │   ④ 대상 있나? Action 허용? ── TargetResolver            │
 │   ⑤ 거리 안인가?                                         │
 │   ⑥ 처리기 호출                                          │
 │        ├─ 단발: IInteractionHandler.Handle → 바로 결과   │
 │        └─ 세션: InteractionSessions.TryStart → 세션 시작 │
 │                    (이후 매 프레임 InteractionRelay가 확인)│
 │   ⑦ 결과를 원장에 기록                                   │
 │                              │                           │
 └──────────────────────────────┼───────────────────────────┘
                                │ TargetReceiveResult(결과) ← 보낸 사람에게만
                                ▼
                  InteractionRelay.ResultReceived 이벤트 → UI
```

핵심 원칙 세 가지:

1. **결과는 서버만 정한다.** 클라이언트는 "하고 싶다"고 요청만 한다.
2. **누가 보냈는지는 서버가 연결로 알아낸다.** 요청서에 ActorId 칸이 없다(위조 불가).
3. **Interaction은 기능을 모른다.** 채집량·인벤토리 같은 규칙은 처리기(각 담당자) 안에만 있다.

## 4. 스크립트 전체 목록

모두 `Assets/01.Scripts/03.Interaction/` 아래다. 폴더 이름의 뜻: `Net` = 네트워크로 오가는 것, `Server` = 서버에서만 실행, `View` = 클라이언트 화면·입력, `Rules` = 순수 규칙·값.

### 4.1 플레이어에 붙는 컴포넌트 (3개)

| 스크립트 | 경로 | 어디서 실행 | 하는 일 |
|---|---|---|---|
| `InteractionRelay` | `Relay/Net/` | 클라이언트(보내기) + 서버(받기·세션 확인) | **요청 송수신 담당.** 요청에 번호를 붙여 `CmdRequest`로 보내고, 결과를 `TargetReceiveResult`로 받는다. 한 번에 하나만 보낸다(응답 오기 전 두 번째 요청은 거절). 서버에서는 매 프레임 자기 플레이어의 세션을 확인하고 시작·종료를 알려 준다. 필수: 같은 오브젝트에 `NetworkActor` |
| `InteractionSelector` | `Relay/View/` | 클라이언트(내 플레이어만) | **대상 고르기.** 매 프레임 주변 표식 중 범위 안에서 가장 가까운 것을 고른다. `TryInteract()`가 호출되면 고른 대상의 기본 Action으로 요청을 보낸다. `CancelSession()`은 진행 중 세션 취소. 필수: `InteractionRelay` |
| `PlayerInteractionInput` | `Relay/View/` | 클라이언트 | **본편 입력 연결.** 최명기의 `PlayerController.InteractionRequested`(E키)를 받아 `InteractionSelector.TryInteract()`를 부른다. Interaction이 Player 코드를 아는 유일한 곳. 필수: `InteractionSelector`, `PlayerController` |

### 4.2 대상에 붙는 컴포넌트 (1개)

| 스크립트 | 경로 | 하는 일 | 설정값(Inspector) |
|---|---|---|---|
| `InteractionTarget` | `Targets/Net/` | "상호작용 가능" 표식. 켜져 있는 동안 전역 목록(`InteractionTarget.Active`)에 들어가 선택기가 찾을 수 있다. 등록·번호 발급 없음(대상은 netId로 식별) | `_defaultAction`: E키로 보낼 기본 동작 / `_supportedActions`: 허용 동작 목록 / `_range`: 선택 가능 거리(기본 3m) / `_serverRangeSlack`: 서버 여유 거리(기본 1.5m). 필수: `NetworkIdentity` |

서버 허용 거리 = `_range + _serverRangeSlack`. 여유가 필요한 이유: 서버가 보는 플레이어 위치는 클라이언트가 보낸 값이라 약간 늦게 도착하기 때문이다.

### 4.3 서버 전용 로직 (컴포넌트 아님, static 또는 일반 클래스)

| 스크립트 | 경로 | 하는 일 |
|---|---|---|
| `InteractionRouter` | `Router/Server/` | **창구.** 모든 요청의 공통 검사 → 처리기 호출. 처리기 등록 API(`RegisterHandler`, `RegisterSessionHandler`)도 여기 있다 |
| `RequestLedger` | `Validator/Server/` | **요청 번호 장부.** 플레이어별로 "다음 번호"와 "마지막 결과" 하나만 기억한다 |
| `TargetResolver` | `Targets/Server/` | **대상 확인.** netId면 `NetworkServer.spawned`에서 찾고, 아니면 등록된 adapter에 묻는다. 세션 중 재확인(`TryRefresh`)도 한다 |
| `InteractionSessions` | `Sessions/Server/` | **세션 관리.** 한 사람당 세션 하나. 시작·매 프레임 검사·완료·취소·정리 |

| `INonNetworkTargetAdapter` | `Targets/Server/` | 네트워크 객체가 아닌 대상 종류를 서버가 확인하게 할 때(채집 지점) |

### 4.5 데이터 구조 (네트워크로 오가거나 처리기에 전달)

| 타입 | 경로 | 내용 |
|---|---|---|
| `InteractionRequest` | `Requests/Net/` | 요청서. [7.1](#71-한-문장-정의)에서 칸별로 설명 |
| `InteractionResult` | `Requests/Net/` | 결과. `Sequence`(몇 번 요청의 결과인지), `Code`(결과 코드), `NextExpectedSequence`(다음에 보낼 번호) |

| `InteractionTargetKind` | `Requests/Rules/` | 대상 종류: `NetworkObject`(netId로 식별) / `HarvestSpot`(채집 지점 키로 식별) |
| `InteractionAction` | `Requests/Net/` | 동작 enum: `Harvest`=1, `Deposit`=2, `Withdraw`=3, `SelectRecipe`=4, `InstallModule`=5, `RepairModule`=6, `PickUp`=7, `UseSpecialIsland`=8, `InspectGhostShip`=9, `RepairBoat`=10, `Rescue`=11 |
| `InteractionContext` | `Router/Server/` | 공통 검사를 통과한 뒤 처리기가 받는 정보: `ActorId`, `Sender`(연결), `Action`, `Target`, `Arg0`, `Arg1` |

| `InteractionSessionEndReason` | `Sessions/Rules/` | 세션 종료 사유. [8.3](#83-세션이-끝나는-8가지-이유) |

## 5. 컴포넌트를 어디에 붙이나

### 5.1 붙이는 위치 정리

| 붙일 곳 | 컴포넌트 | 현재 (시험) | 본편 (예정, 최명기 작업) |
|---|---|---|---|
| **플레이어 프리팹** | `InteractionRelay` + `InteractionSelector` + 입력 연결 1개 | `02.Prefabs/_Net/NetworkTestPlayer.prefab`에 Relay·Selector·`DevInteractionKeyInput`·`InteractionTestAutomation` | `02.Prefabs/Player/`의 `captain`·`farm`·`tanker`·`tech` 4개에 Relay·Selector·`PlayerInteractionInput`. 설정값 없음 |
| **상호작용 대상** (네트워크 객체) | `InteractionTarget` (+ 이미 있는 `NetworkIdentity`) | `JH07Game.unity`의 `InteractionTarget_*` 오브젝트 11개 | 배 프리팹(`Cube.prefab`), 이후 작업대·등대·표류 모듈 등 |
| **처리기** | 각 기능의 `NetworkBehaviour`가 `IInteractionHandler`/`IInteractionSessionHandler` 구현 | `JH07Game.unity`의 `DevInteractionHandler` 오브젝트(`DevInteractionHandler`+`DevSessionHandler`) | 각 기능 담당자가 정한 위치 |
| **비네트워크 대상 adapter** | `INonNetworkTargetAdapter` 구현 후 `TargetResolver.RegisterAdapter` | 없음 | 채집 지점(강민서, 확인 ①~③ 후) |

### 5.2 붙이는 순서와 이유

```text
플레이어 오브젝트
 ├─ NetworkIdentity      (Mirror, 원래 있음)
 ├─ NetworkActor         (01.Network, 원래 있음 — ActorId 보유)
 ├─ PlayerController     (05.Player, 본편 프리팹에 원래 있음)
 ├─ InteractionRelay     ← NetworkActor 필요
 ├─ InteractionSelector  ← InteractionRelay 필요
 └─ PlayerInteractionInput ← InteractionSelector + PlayerController 필요
```

- `[RequireComponent]`가 걸려 있어 순서가 틀리면 Unity가 필요한 컴포넌트를 자동으로 붙이거나 경고한다.
- Relay가 **플레이어 객체에** 있어야 하는 이유: Mirror Command는 그 객체의 주인만 보낼 수 있다. 그래서 서버는 "이 Command가 들어온 연결 = 이 플레이어"라고 믿을 수 있다. 배나 작업대에 Relay를 두면 이 확인이 불가능하다.

## 6. 서버 검사 순서와 결과 코드

`InteractionRouter.Process`는 아래 순서로 검사하고, **처음 걸린 곳에서 바로 결과를 돌려준다.**

| 순서 | 검사 | 실패 시 코드 | 요청 번호 |
|---|---|---|---|
| ① | 이 연결이 판 참가자인가 (`ConnectionDirectory.TryGetActorId`) | `NotParticipant`(3) | 소비 안 함 |
| ② | 판이 `InProgress`인가 | `NotInProgress`(2) | 소비 안 함 |
| ③ | 요청 번호가 "다음 번호"인가 | 더 크면 `SequenceGap`(4), 더 작으면 `StaleSequence`(5). 마지막 번호와 같으면 **저장된 결과 그대로 재응답** | 소비 안 함 |
| ④ | 대상이 존재하고 표식이 켜져 있는가 | `InvalidTarget`(6) | **소비** |
| ④' | 대상이 이 Action을 허용하는가 | `ActionNotSupported`(7) | 소비 |
| ⑤ | 플레이어–대상 거리 ≤ `_range + _serverRangeSlack` | `OutOfRange`(8) | 소비 |
| ⑥-a | 세션 처리기가 등록된 Action → 세션 시작 시도 | 이미 세션 중·독점 대상 사용 중이면 `Busy`(11), `Begin` 실패 코드 | 소비 |
| ⑥-b | 단발 처리기가 등록되어 있나 → `Handle` 호출 | 처리기 없음 `NotHandled`(9), 처리기 예외 `Rejected`(10) | 소비 |
| 통과 | | `Success`(1) | 소비 |

**"소비 안 함"과 "소비"의 차이**

- **소비 안 함(미접수)**: 창구가 아예 받지 않은 것. 같은 번호를 다시 써도 된다. 예: 로딩 중에 누른 E키는 없던 일이 된다.
- **소비(접수)**: 창구가 받아서 처리를 끝낸 것. 성공이든 실패든 결과가 원장에 기록되고 번호가 올라간다.
- 결과에 `NextExpectedSequence`가 들어 있어서 클라이언트는 다음에 보낼 번호를 서버 기준으로 맞춘다.

**같은 번호 재전송**: 마지막 번호로 다시 오면 처리기를 다시 실행하지 않고 저장된 결과만 돌려준다. 내용이 달라도 마찬가지다. 그래서 같은 요청으로 아이템을 두 번 받는 일이 없다.

## 7. Arg0, Arg1은 무엇인가

### 7.1 한 문장 정의

**동작마다 필요한 "추가 정보" 숫자 두 칸이다.** 요청서의 공통 칸(누구·어느 대상·무슨 동작)만으로는 부족한 정보를 담는다.

```text
InteractionRequest
 ├─ Sequence     : 요청 번호              ← 공통
 ├─ TargetKind   : 대상 종류              ← 공통
 ├─ TargetNetId  : 대상 netId             ← 공통 (네트워크 객체일 때)
 ├─ TargetKey    : 대상 키                ← 공통 (비네트워크일 때, 예: 채집 지점 ID)
 ├─ Action       : 동작                   ← 공통
 ├─ Arg0         : 추가 정보 1 (int)      ← 동작마다 뜻이 다름
 └─ Arg1         : 추가 정보 2 (int)      ← 동작마다 뜻이 다름
```

### 7.2 왜 이름이 Arg0·Arg1인가

동작이 11가지이고 각각 필요한 정보가 다르다. 동작마다 필드를 따로 만들면(`ItemCount`, `RecipeId`, `SlotIndex`…) 요청서가 계속 커지고, 새 동작을 넣을 때마다 네트워크 구조체를 바꿔야 한다. 그래서 **범용 칸 두 개만 두고, 뜻은 동작별로 정한다.** 함수의 "첫 번째 인자, 두 번째 인자"와 같은 개념이다.

### 7.3 현재 정해진 뜻

| Action | Arg0 | Arg1 | 상태 |
|---|---|---|---|
| `Harvest` (시험 처리기 `DevSessionHandler`만) | 세션 소요 시간(밀리초). 0이면 기본 1.5초, 100~20000 밖이면 거절 | 안 씀 | **시험 전용.** 실제 채집 처리기(MK03)가 생기면 다시 정함 |
| `PickUp` (시험 처리기 `DevInteractionHandler`) | 안 씀(0) | 안 씀(0) | 시험 전용 |
| 그 외 모든 Action | 미정 | 미정 | 각 기능 담당자가 처리기를 만들 때 김지훈과 함께 정함 |

E키(`InteractionSelector.TryInteract`)는 항상 `Arg0 = 0, Arg1 = 0`으로 보낸다. 0이 아닌 값은 메뉴 UI 등에서 `InteractionRelay.TrySendToNetworkTarget(netId, action, arg0, arg1)`로 직접 보낼 때만 생긴다.

### 7.4 앞으로 쓰일 모습 (이해를 돕는 예시 — **결정 아님**)

| Action | Arg0 예시 | Arg1 예시 |
|---|---|---|
| `Deposit`(작업대에 넣기) | 아이템 종류 번호 | 개수 |
| `Withdraw`(꺼내기) | 아이템 종류 번호 | 개수 |
| `SelectRecipe`(레시피 고르기) | 레시피 번호 | 안 씀 |
| `InstallModule`(모듈 설치) | 인벤토리 슬롯 번호 | 설치 위치 번호 |

### 7.5 꼭 지킬 것

- **Arg0·Arg1은 서버 공통 검사를 거치지 않는다.** `InteractionContext` 주석에도 "still unchecked"라고 적혀 있다. 처리기가 직접 범위를 확인해야 한다. 예: 개수가 음수이거나 99999면 거절.
- 뜻을 정하면 [지훈 시스템 설계 §5.1](../../design/jihun-system-design.md#51-식별과-전송)의 "Arg0/Arg1의 의미를 라우트별로 고정" 원칙대로 문서에 남긴다.

|---|---|---|---|
| 1 | Actor 2 PC, 매 프레임 | 선택기가 `InteractionTarget.Active`를 돌며 범위 안 가장 가까운 상자를 고른다. UI는 `SelectedChanged`로 강조 표시 가능 | `InteractionSelector.Update` / `FindNearest` |

### 8.2 세션 동작: Actor 3이 채집(Harvest) 1.5초

| # | 어디서 | 무슨 일 |
|---|---|---|
| 1~8 | 위와 같음 | 요청이 공통 검사 ①~⑤를 통과 |
| 9 | 서버 | `Harvest`에 **세션 처리기**가 등록돼 있으므로 `InteractionSessions.TryStart` 호출 |
| 10 | 서버 | Actor 3에게 이미 세션이 있으면 `Busy`. 처리기가 독점(`IsExclusive`)이고 다른 사람이 같은 대상을 쓰는 중이면 `Busy` |
| 11 | 서버 | 처리기 `Begin(context, out 1.5초)` → `Success`. 세션 번호 발급, 활성 목록에 등록 |
| 12 | 서버 → Actor 3 | 요청 결과 `Success`(= "세션이 시작됨"이지 "채집 완료"가 아님) |
| 13 | 서버, 다음 프레임 | Actor 3의 `InteractionRelay.Update` → `ServerTickSession`이 시작 알림 `TargetSessionChanged{진행 중, 1.5초}`를 한 번 보냄 → 클라이언트 `SessionChanged` 이벤트(진행 바 표시 가능) |
| 14 | 서버, 매 프레임 | [8.3](#83-세션이-끝나는-8가지-이유)의 순서로 검사 |
| 15 | 서버, 1.5초 뒤 | 처리기 `Complete(session)` → **여기서만 결과 적용**(아이템 지급 등) |
| 16 | 서버 → Actor 3 | 종료 알림 `TargetSessionChanged{종료, Completed}` 한 번 |

키를 떼면(시험 입력 기준): 클라이언트 `CancelSession()` → `CmdCancelSession(세션 번호)` → 서버가 **자기 세션이고 번호가 맞을 때만** 처리기 `Cancel` 호출 → 종료 사유 `CancelledByPlayer`. 취소는 자원을 바꾸지 않으므로 요청 번호를 쓰지 않고, 두 번 보내도 결과가 같다.

### 8.3 세션이 끝나는 8가지 이유

서버는 매 프레임 아래 순서로 확인한다(`InteractionSessions.Tick`).

| 순서 | 확인 | 실패 시 종료 사유 | 처리기 호출 |
|---|---|---|---|
| 1 | 판이 아직 `InProgress`인가 | `MatchEnded` | `Cancel` |
| 2 | 대상이 아직 있나 (`TargetResolver.TryRefresh`) | `TargetLost` | `Cancel` |
| 3 | 아직 거리 안인가 | `OutOfRange` | `Cancel` |
| 4 | 처리기 `CanContinue`가 true인가 (예: 인벤토리 가득) | `ConditionFailed` (예외면 `HandlerError`) | `Cancel` |
| 5 | 소요 시간이 지났나 | `Completed` | **`Complete`** |
| — | 플레이어가 키를 뗌 | `CancelledByPlayer` | `Cancel` |
| — | 플레이어가 나감·판 종료로 플레이어 객체 제거 | `ActorLeft` | `Cancel` |

처리기 입장의 규칙: **결과는 `Complete`에서만 적용, `Cancel`은 원래 상태로 되돌리기만.** `Complete` 전에 활성 목록에서 먼저 빼므로, 처리기 안에서 대상을 지워도 같은 세션이 두 번 끝나지 않는다.

### 8.4 요청 번호 시간표 예시 (Actor 2)

| 시각 | 상황 | 보낸 번호 | 서버 다음 번호 | 결과 | 비고 |
|---|---|---|---|---|---|
| 로딩 중 | E키 | 1 | 1 | `NotInProgress` | 미접수, 번호 그대로 |
| 판 시작 | E키 | 1 | 1 → 2 | `Success` | 접수 |
| | 너무 먼 대상 | 2 | 2 → 3 | `OutOfRange` | 실패지만 접수, 번호 소비 |
| | (시험) 번호 2 재전송 | 2 | 3 | 저장된 `OutOfRange` 재응답 | 처리기 재실행 없음 |
| | (시험) 번호 9 전송 | 9 | 3 | `SequenceGap` | 미접수 |
| 판 종료 후 | E키 | 3 | 3 | `NotInProgress` | 미접수 |

플레이어 객체는 판마다 새로 생기므로(`InteractionRelay.OnStartServer` → `InteractionRouter.BeginActor`) 다음 판은 다시 1번부터다.

## 9. 기능 담당자가 할 일 (처리기 만들기)

### 9.1 단발 처리기 뼈대

```csharp
public sealed class BoatRepairHandler : NetworkBehaviour, IInteractionHandler
{
    private bool _isRegistered;

    public override void OnStartServer()
    {
        _isRegistered = InteractionRouter.RegisterHandler(InteractionAction.RepairBoat, this);
    }

    public override void OnStopServer()
    {
        if (_isRegistered)
        {
            InteractionRouter.UnregisterHandler(InteractionAction.RepairBoat, this);
            _isRegistered = false;
        }
    }

    // 서버에서, 한 프레임 안에 끝낸다. 실패하면 아무 상태도 바꾸지 않는다.
    public InteractionResultCode Handle(in InteractionContext context)
    {
        // context.ActorId: 서버가 확인한 실제 요청자
        // context.Target:  존재·Action 허용·거리 확인이 끝난 대상
        // context.Arg0/1:  미검사 → 여기서 직접 검사
        return InteractionResultCode.Success;
    }
}
```

### 9.2 세션 처리기에서 구현할 것

| 멤버 | 언제 불리나 | 할 일 |
|---|---|---|
| `IsExclusive` | 시작 시 | 같은 대상을 한 명만 쓸 수 있으면 true |
| `Begin(context, out duration)` | 공통 검사 통과 후 | 시작 가능하면 `Success`와 양수 소요 시간(초) 반환. 0 이하면 시작 안 됨 |
| `CanContinue(session)` | 매 서버 프레임 | 계속할 조건(인벤토리 공간 등) |
| `Complete(session)` | 시간 다 됨 | **결과 적용** |
| `Cancel(session, reason)` | 그 외 모든 종료 | 원상태로 |

등록은 `InteractionRouter.RegisterSessionHandler(action, this)`. 한 Action에는 단발·세션 중 하나만 등록할 수 있다.

### 9.3 클라이언트 UI가 쓸 수 있는 것 (본인 PC에서만 발생)

| 이벤트·속성 | 위치 | 용도 |
|---|---|---|
| `SelectedChanged`, `Selected` | `InteractionSelector` | 지금 고른 대상 강조, "E: 채집" 같은 안내 |
| `ResultReceived` | `InteractionRelay` | 결과 코드별 메시지 |
| `SessionChanged`, `Session`, `HasActiveSession` | `InteractionRelay` | 진행 바 시작·종료 |
| `IsAwaitingResult` | `InteractionRelay` | 응답 대기 중 표시 |
| `TrySendToNetworkTarget(netId, action, arg0, arg1)` | `InteractionRelay` | 메뉴에서 고른 동작 보내기(작업대 레시피 선택 등) |

## 11. 아직 안 된 것과 주의

| 항목 | 상태 | 담당 |
|---|---|---|
| 본편 플레이어 프리팹 4개에 Relay·Selector·`PlayerInteractionInput` 부착 | 미착수(develop 반영 후) | 최명기 |
| 배 프리팹에 `InteractionTarget`(기본 Action·범위 결정) | 미착수 | 최명기 |
| 실제 처리기: 배 수리(MK02)·채집(MK03)·구조(MK04) | 미착수 | 최명기 |
| 채집 지점 adapter | 강민서 확인 ①~③ 대기 | 강민서 |
| 본편 키 뗌 이벤트 없음 → 본편에선 손을 떼서 세션 취소 불가 | 결정 필요 | 최명기 |
| Interact 입력의 `Hold`(0.4초) → 단발 동작도 0.4초 눌러야 함 | 의도 확인 필요 | 최명기 |
| 미검증: `ActorLeft`·`ConditionFailed` 직접 재현, 비네트워크 대상, 본편 입력, 다른 PC(M3) | | 김지훈 |
| develop PR | 사용자 지시로 보류 | 김지훈 |

주의:

- 로비 없는 단일 씬에서는 판이 `InProgress`가 되지 않아 **모든 요청이 `NotInProgress`** 로 거절된다. 시험은 로비를 거치는 JH07 방식으로 한다.
- 처리기는 `await`·코루틴 없이 한 프레임 안에 끝내야 한다. 오래 걸리면 세션 처리기로 만든다.
- 숨겨야 하는 정보(직업·부식 등)를 드러내는 결과 코드를 만들지 않는다. 그런 실패는 `Rejected`로 돌려준다.

# 이동 권위(N07) 결정과 문서 갱신

작성자: 김지훈
작성일: 2026-10-13
갱신일: 2026-10-13
상태: 완료(문서·결정 반영), 팀원 확인 대기
브랜치·기준 커밋: `feature/jihun`, `ac2bd12`

## 요청과 목표

- 김지훈 담당의 다음 작업을 확인한다.
- 최명기 `ce48fae`(개인 배 생성·소유권 동기화·자동 승하선)가 김지훈 작업에 주는 영향을 검토한다.
- 플레이어·배 이동을 클라이언트 권위로 정하고 관련 문서를 갱신한다.
- 팀원별 작업 영향 문서와 최명기 합의 안건을 만든다.

## 진행 과정과 결정 이유

- 2026-10-13 다음 작업 검토: JH01만 구현·검증(같은 PC 4인)됐다. JH02는 `InteractionRequest`·`InteractionAction` 데이터 정의만 있고, `04.Lighthouse/`에는 코드가 없다. 그래서 다음 작업을 JH02 A단계로 판단했다. `PlayerController.InteractionRequested`는 대상 정보 없이 발생하고 구독자가 없다. 대상 탐지·선택 담당(N10)이 미정이라 JH02를 실제 플레이에 연결하려면 최명기와 합의가 필요하다.
- 2026-10-13 `ce48fae` 검토:
  - 배는 `NetworkServer.Spawn(boat, connection)`으로 연결에 소유된다. 그래서 Mirror 기본 단절 처리에서 플레이어와 배가 함께 삭제된다. JH07 보존 대상에 배를 추가해야 한다.
  - 배·플레이어 NetworkTransform이 `syncDirection: 1`(ClientToServer)로, N07을 사실상 클라이언트 권위로 구현한 상태다.
  - `LighthouseNetworkManager.cs`에 들어온 변경은 직군 프리팹 무작위 배정 코드인데 전부 주석이다. 실행 코드는 바뀌지 않았고 배 생성에는 영향이 없다. 직군 프리팹 배정만 동작하지 않는다.
- 2026-10-13 사용자 결정: 플레이어+배 모두 소유 클라이언트 권위(A안).
  - 근거: 현재 코드와 같고, 원격 조작 지연이 없다. 기능 동결(10/25)이 가까워 서버 권위로 다시 짤 비용을 감당하기 어렵다. 지인 4인 리슨 서버라 호스트 신뢰 한계(N01)가 이미 있다.
- 2026-10-13 확인한 기술 근거:
  - Mirror 96.0.1에는 `ServerTeleport`/`RpcTeleport`가 있고, 소스 주석에 클라이언트 권위에서도 서버 강제 이동이 허용된다고 적혀 있다.
  - 프로젝트 물리 설정은 `m_ContactPairsMode: 0`이다. 그래서 서버에서 Kinematic인 원격 배의 충돌 이벤트가 오지 않는다. 피해 판정은 서버 겹침 검사로 하자고 제안했다.
  - `BuoyancyBody._isSimulating`의 기본값이 `true`이고 권위와 연결돼 있지 않다. 배에 붙이면 파도 충격이 중복 감지될 수 있다. 배 주인 PC에서만 켜자고 제안했다.
- 2026-10-13 합의 안건 검증과 결정(사용자): 안건 1 B(Interaction 컴포넌트가 대상 탐지·선택), 4·5·6 동의, 안건 3은 다음 대화로 미룸. 반영 전에 설계·코드를 대조한 결과는 다음과 같다. (1) 대상 장부는 서버에 있는데 탐지는 클라이언트라 TargetId 전달 경로가 비어 있었다. (2) 스포너 등록에는 해제 경로가 없었다. (3) 안건 6의 배 대상 행동 목록이 v4와 달랐다. (4) 투표 코드도 접속 이벤트 계약에 의존한다. 이에 따라 서버 장부(TargetId+Generation) 유지, 비네트워크 대상은 클라이언트가 종류+기존 ID를 보내 서버가 변환(b안), 네트워크 대상은 자기 `OnStartServer`/`OnStopServer`에서 등록·해제로 결정했다. Action 결정 경로·홀드 세션 분담·JH02 경유 기준도 제안대로 결정했다. 안건 6 행동 목록(배 수리·구조 Action 누락)과 안건 2는 설명 후 결정 대기다.
- 2026-10-13 추가 결정(사용자): `InteractionAction`에 `RepairBoat = 10`(배 내구도 수리), `Rescue = 11`(난파 동료 구조)을 추가했다. v4 4장·9장에서 배를 대상으로 하는 행동인데 enum에 없었기 때문이다. 수리 비용과 구조 시간 규칙은 최명기(MK02·MK04)가 정한다. 안건 2는 A(매니저에 프리팹 선택 훅만 두고 선택 로직은 최명기 코드)로 정했고, 직군 배정 시점은 D06 결정에 맡긴다.
- 2026-10-13 접속 정책 결정(사용자): 10/25 전에는 재접속을 넣지 않고 접속은 KCP IP 직접 접속을 유지한다. 재접속을 넣게 되면 판 한정 복귀 토큰으로 Steam과 독립 설계한다. Steam은 인터넷 플레이가 필요할 때 따로 검토한다. Steam이 대신하는 것은 사람 식별과 접속 대상뿐이고, 재접속의 본체(객체 보존·재결합·기능별 상태 복원)와는 무관하다는 비교 결과에 따른 것이다. 안건 3은 남김·사라짐을 비교했다. 사라짐은 투표 규칙이 같고 마피아 이탈 미정 문제도 공통이며, 실제 차이는 자원 소멸·다른 기능의 참조 문제·작업량이었다. 비교 후 사용자가 "판 진행 중 한 명이라도 나가면 판 종료(방 폭파)"를 골랐다. 4인 마피아에서 한 명이 빠지면 판이 성립하지 않고, 남김·사라짐의 예외 처리가 모두 필요 없어지기 때문이다. 승패·투표 결정 §8(2026-10-11 허수아비 결정)을 바꿨다. 로비 이탈은 자리만 비우고 판 시작 후 새 참가는 거절한다. 지속 상호작용 세션 정리는 JH02에 포함한다.
- 2026-10-13 전체 결정 반영: 안건 1~7과 위 결정을 공용 기준 문서, 지훈 설계, 작업표, 대장, 인수인계 문서에 반영했다. 안건 7은 김지훈 쪽 동의로 기록하고, §4.2는 최명기 확인 뒤 §4.1로 옮기도록 남겼다.
- 2026-10-13 로비 시작 결정(사용자): 4명 전원 준비 시 자동 시작, 준비 취소 가능, 게임 씬 전원 로딩 완료 후 시작·시간 초과(시험값 60초) 시 판 종료, 시작 인원은 설정값(기본 4). `NetworkRoomManager`는 `ActorJoined` 계약 시점을 바꾸므로 쓰지 않고 지금 매니저에 준비 상태를 추가한다.
- 피해 원인별 판정 위치, 판정 수단, 경계 검사, 허용 오차는 다른 담당(최명기·박태욱·강민서)의 기능이다. 그래서 확정하지 않고 "합의 대기 제안"으로 기록했다.

## 검증

- 실행한 확인과 결과: 변경 문자열이 파일마다 한 번만 일치하는지 스크립트로 확인하며 교체했다. 다른 문서가 `NETWORK_AUTHORITY.md`의 기존 §4·§5 앵커를 참조하지 않는지 확인했다. 새 문서의 상대 링크는 경로 계산으로 작성했고 렌더링 확인은 하지 않았다.
- 실행하지 못한 확인과 이유: Unity 실행·4인 시험은 이번 범위(문서)가 아니어서 하지 않았다. `ServerTeleport`의 호스트 모드 동작, 원격 배 충돌 이벤트 미수신은 소스·설정에 근거한 추론이며 실행 확인이 필요하다.

## 남은 일과 차단 조건

- 팀원 확인 대기: 최명기(합의 안건 전체, 안건 7 §4.2 항목), 박태욱(접속 이벤트 계약·판 종료, §4.2 몬스터·대포), 강민서(채집 지점 생성 방식·근처 조회, §4.2 파도·부력).
- 남은 결정: 직군 배정 시점(D06, 최명기), 인터넷 플레이 필요 여부(N13), 판 종료 후 돌아갈 화면(로비/타이틀, 최명기 UI 흐름), 채집·구조 소요 시간과 취소 조건(MK03·MK04).
- 재접속 참고안(지훈 설계 §8.2 아래·§8.3)은 현재 범위가 아니라고 표시만 했고 본문은 남겼다.
- 작업 시작 시점에 없던 `Assets/00_Scenes.meta` 삭제가 작업 트리에 생겼다. 이번 작업에서 만든 변경이 아니며 손대지 않았다. 폴더는 이미 `00.Scenes`로 바뀌어 있다.
- 디스크 폴더는 `Docs/`, Git 추적 경로는 `docs/`다. 새 파일을 추가할 때는 `git add docs/...`처럼 소문자 경로를 쓴다(`Docs/`로 추가하면 대소문자가 다른 경로로 기록됨, dry-run 확인).

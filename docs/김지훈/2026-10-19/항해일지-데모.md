# 판 종료 후 항해 일지 데모 (CrewMultiplayer 확장)

- 작성일: 2026-10-19
- 위치: SVN `_Demo/Jihun/CrewMultiplayer/` (git 밖). 조작·화면은 데모 README의 "항해 일지" 절
- 성격: 기획 제안 데모. v4에 없는 기능이며 확정 기획 아님

## 왜
2026-10-16 바이브코딩 후보 추천에서 사용자가 "판 종료 후 항해 일지"를 골랐다. v4 9장은 추리의 근거를 "누가 언제 어디에 있었나"로 두지만, 판이 끝난 뒤 그 답을 확인하는 장면이 없다. 마피아 게임에서 판 뒤 공개가 재미와 다음 판 학습의 핵심이라는 가설을 직접 보고 판단하려고 만들었다.

## 결정과 이유
- 새 데모 폴더 대신 2026-10-17 마피아 미니판(CrewMultiplayer)에 얹었다. 판 시작·종료·마피아 행동이 이미 있어서, 일지만 따로 만들면 기록할 판이 없기 때문이다
- 미니판 종료 화면에 이미 텍스트 "진행 기록"이 있다. 겹치지 않도록 일지는 위치 중심(지도 항적 재생 + 사건 순간 근처 선원)으로 잡았다
- 판 중에는 아무것도 보내지 않고 종료 순간 한 번에 보낸다. 위치·비밀 행동이 판 중에 새지 않게 하려는 것이다(v4 4.8 비밀 정보 원칙과 같은 방향)
- 지도 배경은 판 끝에 위에서 맵을 한 번 찍어 만든다(URP 렌더 요청 → 지원하지 않으면 `Camera.Render`). 맵마다 따로 그린 지도가 필요 없게 하려는 것이다
- 화면은 기존 데모와 같은 IMGUI다. 본편 UI(UGUI Canvas)로 옮길지는 채택 뒤 결정한다

## 실제 검증
- Unity 6000.0.83f1(UnityMCP 연결) 컴파일 요청 후 에러·경고 0. 새 타입이 Assembly-CSharp에 있는지 리플렉션으로 확인
- 메뉴 `Add Mafia Round To Built Scene` 실행, 완료 로그와 프리팹·씬 컴포넌트 존재 확인
- 플레이 모드 호스트 1명 스모크 시험(2회, 두 번째는 수정 후): 혼자서는 마피아 판이 열리지 않아 기록 시작을 직접 호출하고, 선원 위치를 옮기며 행동을 기록한 뒤 판 단계를 리플렉션으로 `Ended`로 바꾸고 전송했다. 확인한 것: 호스트 클라이언트가 항적(샘플 9~20개)·사건(3~5개)·비밀 표시·마피아 표시를 받음, 지도 배경이 실제 섬을 위에서 찍은 모습으로 나오고 항적 방향이 맞음, 재생 화면·낮밤 띠·선택 사건의 20m 원과 "근처 선원" 표시(화면 캡처)
- 시험 중 고친 것: 아래 HUD가 오른쪽 패널 뒤로 비침(배경 불투명), 시간 표시 줄바꿈, 종료 직전 이동이 1초 샘플에 안 잡힘(전송 직전 한 번 더 기록)
- 미실행: 실제 마피아 판(2명 이상)의 자연 종료 흐름, 원격 클라이언트 수신(MPPM·다른 PC), 다른 맵 배경 촬영, 5일 판 전송량·성능. 마피아 미니판 자체의 플레이도 아직 미확인

## 추가: 3인 빌드 시험과 "남의 이동 끊김" 진단 (2026-10-19)
### 경과
- 데모 씬만 담은 빌드를 만들었다(`Builds/CrewDemo/CrewDemo.exe`, git 제외 폴더). `BuildPipeline`에 씬을 직접 지정해 공용 Build Settings는 바꾸지 않았다. 같은 PC에서 1280×720 창 3개로 실행했다
- 사용자 보고: 자기 이동은 문제없는데 남의 이동이 심하게 끊겨 보인다. 데모가 본편 네트워크인지, 본편에도 같은 문제가 생기는지 질문
- 확인한 점: 데모는 본편 접속·상호작용·플레이어 코드를 쓰지 않는다. 다만 이동 동기화 부품은 본편 `Assets/02.Prefabs/Player/tech.prefab`과 같다(`NetworkTransformReliable`, 소유 클라이언트 → 서버, 바뀔 때만 보내기·보간 켬). 본편 M2 기록에도 남의 이동이 부드러운지 확인한 기록은 없었다
- 진단 표시 `Scripts/CrewNetDiagnostics.cs`(F3 화면, 3초마다 플레이어 로그) 추가: 창 FPS·최악 프레임·포커스, RTT, 남의 캐릭터 위치 수신 횟수·간격, 보간 버퍼, 화면 멈칫

### 원인
- 1차 로그(`Builds/CrewDemoLogs_before/`): 조작 중인 창은 280~350FPS인데, 나머지 창은 **3~4FPS(프레임당 250~340ms)**로 떨어졌다. 서버는 60Hz로 보내고 있었고 버퍼도 비지 않았다. 받는 창이 초당 3~4번만 그려서 끊겨 보인 것이다. 방장 창도 3FPS가 되면서 RTT가 100~280ms까지 올랐다
- 근본 원인: 프로젝트에 프레임 상한이 없다(`ProjectSettings/QualitySettings.asset`의 PC 품질 `vSyncCount: 0`, 코드의 `targetFrameRate` 없음). 한 PC에 창 여러 개를 띄우면 조작 중인 창이 GPU를 독차지한다
- 데모만 고침: `CrewNetworkManager.Awake`에서 `Application.targetFrameRate = 60`(`_targetFrameRate`)

### 수정 후 재시험 (사용자 조작, 3창)
- 세 창 모두 포커스와 상관없이 **FPS 60, 최악 프레임 17ms**. RTT 17~32ms
- 움직이는 동안 남의 캐릭터 위치 수신 **60회/초, 최대 간격 17ms, 버퍼 5 유지**, 화면 멈칫 대부분 0
- 남은 작은 현상: 멈춰 있다가 움직이기 시작할 때 한 번씩 100~133ms 멈칫(수신 간격 183~567ms와 같은 구간). "바뀔 때만 보내기"가 정지 후 다시 보내기 시작할 때의 동작으로 추정한다. 본편도 같은 설정이라 같은 현상이 날 수 있다. 체감 여부는 미확인

### 본편 영향 (팀 결정 필요, 수정하지 않음)
- 실제 PC 4대 판에서는 창끼리 GPU를 다투지 않아 이 끊김은 생기지 않을 것으로 본다(추론, M3 미검증)
- 본편을 한 PC 여러 창으로 시험할 때(M2)는 같은 끊김이 생긴다. 상한이 없으면 실제 판에서도 GPU가 계속 최대로 돈다
- 결정 필요: 프레임 상한 방식(수직 동기화 / 고정 60 / 설정 메뉴)과 위치(품질 설정 공용 에셋 vs 시작 코드). 공용 설정이라 팀 합의 후 반영

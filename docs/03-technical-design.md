## 1. 목적과 적용 범위

2026-10-29 최신 사용자 선택: 아래 뱃머리 반원 감싸기와 물방울 확대는 철회하고 녹화003119 당시 표현으로 복원했다. 접점 단일 발생·물방울0.035~0.08·반각28도·물줄기5개이며 수면 높이/배 방향·색/알파·배율은 유지한다. 반원 관련 이전 단락은 변경 이력이다. 프리팹 저장 완료, 실제 Play는 사용자 담당이다.

2026-10-29 배 충돌 뱃머리 감싸기 후속: 물방울 크기0.09~0.2·거품 별도 크기, 선체 폭/효과 배율로 산출한 반경의 반원형 발생점을 사용한다. 접점에서 좌우 선체를 감싸고 배 방향으로 퍼지도록 분사 반각65도·물줄기7개로 변경했다. 색·접촉 검증·피해/반동 유지, 프리팹 저장 완료·사용자 Play 테스트 대기다. [작업 기록](최명기/2026-10-28/배-충돌-이펙트-시안.md).

2026-10-28 경비병 쉴드 탑승 조건: GuardShieldAbility.IsAboardOwnedBoat를 Q 실행·선택창·GuardShieldRequest의 클라이언트/서버에서 사용해 시전자와 대상이 각자의 정상 소유 배에 실제 탑승한 경우만 부여한다. 하선/빈 배 요청은 사용권 차감 전에 거절한다. 기존 일일 제한·방어 판정·이미 부여된 효과는 유지한다. 컴파일·격리 요청 검사 확인, 실제 Play/M2는 미검증이다. [기록](최명기/2026-10-28/경비병-쉴드-4색연출.md).

2026-10-28 경비병 쉴드 연출: BoatShield의 SyncVar hook/OnStartClient가 유지 상태를, 성공 부여·피해 소모 ClientRpc가 일회 펄스와 즉시 표시/숨김을 전달한다. BoatShieldView는 대상 배의 직군별 파랑/주황/보라/초록 게임용 껍질을 배에 부착하고 펄스는 로컬 생성·정리한다. 외부 에셋의 충돌체·데모 스크립트를 게임용 복사본에서 제거했으며 피해 판정은 기존 BoatShield가 계속 담당한다. 컴파일·4종 격리 검사·렌더 확인, 실제 Play/M2는 미검증이다. [구현·검증 기록](최명기/2026-10-28/경비병-쉴드-4색연출.md).

2026-10-28 난파 Player 분리: 서버 `PlayerWreckRecovery.TryBeginRecovery`가 Downed 설정 후 `BoatController.TryDetachForWreck`로 실제 탑승을 해제한다. 기존 난파 배 부력 정지를 유지하고 구조 완료는 비탑승을 검사한다. `ApplyRecoveryPosition`은 이미 분리된 Player에도 복귀 위치를 적용하며 완료 실패는 같은 정산 계획으로 재시도한다. `PlayerController`의 선택적 Wreck Buoyancy 슬롯은 소유자가 난파·비탑승·동적 물리이고 세션 진행 중일 때만 켜진다. 실제 Player 부력 계산과 슬롯 연결은 아직 없으며 일반 낙수에는 적용하지 않는다. MCP 컴파일·4직군 격리84조건 통과, 실제 Play/M2·파도는 미검증이다. 아래 10/27의 탑승 유지 설명은 과거 상태다. [기록·연결 방법](최명기/2026-10-28/난파-Player분리와-부력전환준비.md).

2026-10-27 플레이어 지형 접지 보정: `PlayerMotor`는 중심 단일 Raycast 대신 캐릭터 하단 캡슐 반경의 SphereCast로 같은 물리 씬의 지면을 검사한다. 자기 충돌체·트리거·충돌 제외 쌍/레이어는 접지에서 제외한다. 접지 이동은 지면 접선 속도와 지면 방향 하강 속도를 나누며, 접촉 여유보다 큰 틈에서만 최대 1.5m/s의 제한된 밀착 속도를 적용한다. 보행3/달리기4.5·점프·애니메이션·이동 위치 권위는 유지한다. 컴파일과 격리 물리 비교는 확인했으며 실제 섬 체감·승하선·원격 M2는 미검증이다. [조사·수정 기록](최명기/2026-10-27/플레이어-충돌-초기조사.md).

2026-10-27 사용자 원복 요청: 이번 보행 보정을 철회하여 목표 걷기3/달리기4.5(배율1.5), 클립기준2/3, 블렌드경계3/4.5·Idle→Walk0.5, 재생범위0.65~1.5로 복구했다. 앞선 접지 보정은 유지한다. [철회 기록](최명기/2026-10-27/보행-발미끄러짐-보정.md).

2026-10-26 개인 인벤토리 UI: `InventoryChestScreen`은 소지품·선체수리·배모듈 3탭을 런타임 uGUI로 구성한다. 소지품은 기존 Owner 동기화 수량과 직군별 스택용량을 사용하고, 선체수리는 자기 배의 현재/최대 내구도 및 `BoatRepair`의 보유·기투입·필요량을 구분한다. 재료 투입은 기존 `RepairBoat`, 모듈 장착은 기존 `InstallModule` Relay 요청으로 서버가 판정한다. 2026-10-29 승인 상자형 UI 반영: 자원8칸+운반모듈1칸, 간소화 수리 레시피, 배모듈4종 아이콘 클릭으로 기존 장착 요청(드래그 없음). 운반 종류 일치·탑승·요청대기를 검사하며 배 내부 모듈 표시는 `OwnedBoat`의 실제 `BoatModuleEquipment.HasModule`을 읽는다. 배 이미지는 Resources/Inventory에서 로드하며 씬 수정 없이 런타임 UI를 구성한다. 좌하단 운반 모듈 HUD는 같은 Canvas에서 창과 별도로 생성하고 본인의 기존 운반 모듈 ID/레시피를 읽어 아이콘·이름을 표시한다. 빈 상태·미연결·인벤/오버레이 표시 중에는 숨기고 입력을 가로채지 않는다. 이 변경은 운반1개·탑승수리·30%이상·부분투입 등 기존 계약을 변경하지 않는다. 컴파일·격리상태/시각 검증과 실제 접속/M2를 구분하며 후자는 검증 대기다. [작업 기록](최명기/2026-10-26/인벤토리-3탭-개편.md).

[제공된 v4](design/references/game-design-v4.md)의 4인 호스트-클라이언트 구조와 비밀 정보 보호를 유지한다. v4 4.8은 직군·마피아, 소환 여부, 부식 여부, 미래 날씨, 환영 섬 대상을 당사자에게만 보내는 비밀 정보로 정한다. 투표·봉인·심해·확인 결과의 구체적인 수신 범위는 [새 결정 §7](design/win-vote-decisions.md#7-정보-공개-범위--n04r16)을 따른다. 백엔드·전용 서버·영구 저장 체계는 현재 확인된 기획 범위에 없다. 도입이 필요하면 요구사항과 기술 방향을 별도로 결정한다.

## 3. 실행 구성

리슨 호스트 한 명과 원격 클라이언트 세 명이 한 판을 구성한다. 각 담당자는 자기 기능의 서버 판정·동기화·클라이언트 표현을 함께 구현하며 [담당 경계](CODE_OWNERSHIP.md)를 따른다. 공용 접속 기반과 4인 안정화 테스트는 김지훈이 담당한다. 게임 규칙 판정은 호스트의 서버 측에서, 입력과 표현은 각 클라이언트에서 처리하는 방향이다. 플레이어·배 이동은 소유 클라이언트가 계산해 NetworkTransform(ClientToServer)으로 서버에 보고하고, 피해·상호작용 등 게임 결과는 서버가 판정한다(2026-10-13 결정, N07). `PlayerController`·`BoatController`는 `NetworkBehaviour`이며 본편 프리팹의 4인 실행 검증은 아직 없다.

### 3.3 점프·체공·착지 표현

2026-10-26 체공 분리 시험은 사용자의 점프 이상 보고·원복 요청으로 철회했다. 원래 Jump.fbx1배와 HFSM Jump 상태 기반 IsJumping 표현 및 기존 점프 전환을 사용한다. 별도 AirLoop/Land 상태·클립·IsRising은 제거했다. [철회 이력](최명기/2026-10-26/점프-체공-착지-분리.md).

후속 사용자 요청으로 추가된 Falling.fbx를 낙하 전용 반복 상태에 연결했다. 일반 점프 동작은 유지하고 Jump 후반(정규화0.95) 이후에도 비접지 하강 중이면 Falling으로 전환한다. 절벽 낙하는 직접 Falling으로 들어가며 기존 이동 코드와 같은 접지 기준으로 이동 상태에 복귀한다. 소유자의 비접지/하강 지속 판정이 IsFalling bool을 쓰고 원격은 NetworkAnimator를 소비한다. 착지 재현 후 낙하 전용 지면거리는 제거했고 Falling 진입 중에도 접지 복귀가 전환을 취소할 수 있게 했다. 물리 점프/이동 및 채택 보행2/달리기3은 유지했다. 사용자 착지 이상6회 재현 후 수정, 전환 프리뷰11항목·접지 재현3항목 통과. 수정 후 실제 Play·원격은 검증 대기다. [Falling 연결·착지 수정 원문](최명기/2026-10-26/낙하-Falling-연결.md).

## 4. 권위와 통신

| 구분 | 책임 |
|---|---|
| 호스트 서버 | 게임 진행·승패·몬스터 AI·비밀 투표 등 공유 규칙 판정 |
| 클라이언트 | 입력·카메라·UI·연출, 허용된 요청 전달 |
| 네트워크 계약 | 요청과 동기화 데이터. 클라이언트의 결과 주장 자체를 신뢰하지 않음 |

Command 인자의 권한·범위·쿨타임은 서버에서 검증한다. 비밀 투표 결과는 본인과 시스템만 알며 역할 등 비밀 정보는 전체 SyncVar/ClientRpc로 보내지 않는다. 필요한 정보만 해당 대상에게 전달한다. 몬스터의 소환/자연 스폰 여부는 클라이언트에 보내지 않는다. 상세 운영 규칙은 [네트워크 권위](unity/NETWORK_AUTHORITY.md)를 따른다.

호스트 자신은 서버 상태를 가진다. 원격 클라이언트 정보 제한이 호스트 운영자의 메모리 접근까지 막는다는 보장을 뜻하지 않는다.

이동 위치는 소유 클라이언트가 보고한 값이다. 서버의 거리·범위 검증은 이 보고 위치와 보간 지연을 전제로 하며, 조작된 클라이언트의 순간이동·속도 조작을 완전히 막지 못한다. 4인 지인 플레이 범위에서 이 한계를 허용한다. 물리 모드·판정 수단·강제 이동 규칙은 [네트워크 권위 §4](unity/NETWORK_AUTHORITY.md#4-이동과-물리-권위)를 따른다.

## 5. 현재 요청·데이터 계약

2026-10-22 채집 결정: [원본별 공유 잔량](design/resource-gathering-decisions.md)을 따른다. 돌 한 원본은 전원 합계 3회이며 소진 후 원본은 유지한다. 현재 `HarvestInteractionHandler`는 요청자 `PlayerHarvestProgress`의 개인 잔량을 차감하므로 기획과 불일치한다. 전환 시 서버 World 잔량을 단일 원장으로 연결하고 드롭 생성 실패 복구·동일 지점 ID·변환기 중복 등록을 함께 확인한다. [구체적 수정 안내](최명기/2026-10-22/공유자원-잔량전환.md)는 제안이며 이번에는 코드를 수정하지 않았다.

- `Assets/01.Scripts/03.Interaction/Requests/Net/InteractionRequest.cs`: 2026-10-14 JH02 A-1에서 요청 번호·대상 종류·대상 netId·비네트워크 대상 키·Action·Arg0·Arg1(2026-10-18 작업대 투입용 Arg2 추가, 기본 0)을 가진 전송 구조체로 바꿨다. ActorId와 ServerTime은 넣지 않고 서버가 연결에서 ActorId를 얻는다. 처리 경로는 `Relay/Net/InteractionRelay` → `Router/Server/InteractionRouter`(판 진행 중·송신자·요청 번호·대상·거리 검사 후 기능 처리기 호출)다.
- `Assets/01.Scripts/03.Interaction/Requests/Net/InteractionAction.cs`: 상호작용 종류를 정의한다.
- `Assets/01.Scripts/02.World/Harvest/Rules/ResourceDefinition.cs`: 자원 ID·표시명·아이콘·희귀도·픽업 프리팹의 ScriptableObject 정의다.

요청·응답·지속 세션 계약은 [지훈 시스템 설계 §5·§6](design/jihun-system-design.md#5-요청검증응답-계약)이 기준이며 JH02 A-1·A-2로 구현됐다(2026-10-14, 같은 PC M2). 실제 기능 처리기(채집·작업대·수리 등)는 아직 연결되지 않았으므로 이 경로의 존재를 해당 기능의 완료로 보지 않는다.

송신자와 ActorId의 관계는 JH01에서 다음과 같이 구현했다. 상세 설계는 [지훈 시스템 설계 §5.1·§8](design/jihun-system-design.md)을 따른다.

- ActorId는 서버가 플레이어 생성(`OnServerAddPlayer`) 때 1부터 발급한다. 0은 무효다. 연결 번호(connectionId)·객체 번호(netId)와 분리된 주체 번호다.
- 서버 코드는 Command 인자로 클라이언트가 보낸 ActorId를 신뢰하지 않는다. JH02 요청에는 ActorId 필드가 없다. `LighthouseNetworkManager.Instance.Connections.TryGetActorId(connectionToClient, out actorId)`로 송신자를 조회하거나 `IsSender`로 대조한다.
- 플레이어 객체의 `NetworkActor.ActorId`는 모든 클라이언트에 공개된다. 역할 등 비밀 정보와 연결되지 않는다.
- 타임스탬프(`ServerTime`)는 클라이언트 값을 신뢰하지 않고 서버가 기록한다. 요청 번호는 2026-10-14 재접속 없음 전제로 `(ActorId, 요청 번호)` 키와 판 진행 중(`InProgress`) 접수만 두고, 연결 세대는 재접속 채택 시 추가한다([지훈 시스템 설계 §5](design/jihun-system-design.md#5-요청검증응답-계약)). JH01의 현재 `OnServerDisconnect`는 `ActorLeft` 알림 후 연결 명단에서 제거하고 Mirror 기본 해제를 실행한다. 2026-10-13 결정으로 판 진행 중 이탈은 판 종료다. JH07이 이를 구현했다. 로비 씬·게임 씬 전환 방식에서 이탈을 감지해 직접 나감/연결 끊김을 구분한 종료 사유를 전원에게 보내고, 첫 화면으로 돌려보낸다(같은 PC 4인 M2 검증, 다른 PC 미검증). 로비 프리팹이나 게임 씬이 없는 매니저는 기존 JH01 단일 씬 방식으로 동작하지만, 2026-10-14 결정으로 이 방식의 시험 씬은 폐기 예정이고 JH02 이후 기능은 지원하지 않는다. 재접속은 10/25 이후 선택 범위다.

| 최후 전투 전환 | 소환 시 기존 의식 타이머·게임 기한 제거. 소환 전 수리도와 별개인 새 수리 진행도 0%. 고정 최대 HP와 환산 현재 HP로 시작 | 박태욱 소환 → 최명기 단계 관리·김지훈 등대 |
| 최후 전투 수리·보상 | 자원 투입은 새 수리 진행도만 올림. 현재 HP 회복·최대 HP 증가 없음. 기존 수리 보상 유지·전투 진행도로 새 보상 또는 중복 보상 지급 없음 | 김지훈 등대 → 최명기 Player 보상 적용·시스템·UI |
| 최후 전투 종료 | 새 수리 진행도 100% 또는 HP 0에 먼저 도달하면 시민 또는 마피아 승리를 한 번만 확정. 별도 점화·기한 패배·괴물 처치 승리 없음 | 김지훈 등대 상태 → 최명기 최종 승패, 박태욱 몬스터 종료 소비 |
| 공격력 정산 | 시민별 유지 시간 기록, 아침 기본 충전·봉인/오투표 합산. 난파·확인 성공 후에도 누적(단절은 판 종료). 소환 시 미정산분과 완료된 하루의 기본 충전만 반영, 최소 공격력 보장·소환 이후 고정 | 강민서 아침/시간 제공 → 박태욱 정산·몬스터 공격력, 최명기 Player 상태 연결 |

등대는 숨은 단계 수리도, 최후 전투용 수리 진행도, 현재 HP, 최대 HP와 이미 획득한 보상을 구분한다. 소환 시 현재 HP는 `기본 HP + (최대 HP − 기본 HP) × 소환 전 수리도 비율`이며 비율 범위는 0~1이다. 전환 전 값을 읽어 환산한 결과와 새 진행도 0%를 구분해 소비한다. 최명기 시스템이 최종 승패를 한 번만 확정하며 각 기능은 필요한 조건과 상태를 제공한다. 동일 판정 시점의 의식 완료/소환 또는 수리 100%/HP 0 우선순위는 아직 정하지 않았다.

게임 기한과 월드의 일차·아침 이벤트·일일 효과는 별개 계약이다. 의식 시작은 게임 기한만 정지하며 월드 시간까지 멈춘다는 결정을 뜻하지 않는다. 최후 전투의 기한 제거가 모든 일일 효과의 제거를 뜻하지 않는다. 의식 중 월드 시간 진행, 최후 전투 일일 효과 및 의식 중 억제한 낙하의 후속 처리도 [설계 문제 대장](07-design-issue-register.md)의 남은 결정을 확인한다.

기획과 현재 코드를 구분한다. `07.Mafia/Voting/Rules/VoteService.cs`는 참가자·횟수·같은 대상 재클릭을 처리하지만 마피아/자기 투표 제한과 의식 잠금은 아직 검사하지 않는다. 위 단계 전이·승패·HP·보상·공격력·정보 전달의 통합 구현이나 4인 실행 검증이 완료된 것으로 보지 않는다.

현재 `NetworkActor.ActorId`는 `uint`이고 `VoteService`의 참가자 ID는 `int`다. 실제 호출자 연결 전에 ID 타입·허용 범위와 매핑 여부를 김지훈·박태욱·최명기가 합의해야 한다. 문서 갱신으로 코드 타입을 바꾸거나 두 값이 이미 연결됐다고 표시하지 않는다.

판 길이 값(숨은 단계 기한 기본 5일, 낮 5분·밤 2분, 귀항 알림, 해금 비율 1/3·2/3)은 기준 문서대로 설정값 한 곳에서 바꿀 수 있게 둔다. 확인 횟수·성공 기준, 최소 공격력·기본 심해 충전량·유지 시간당 증가량은 설정값이며 최종 수치는 플레이테스트 후 조절한다. 직군 세부·레시피·회복량 등 남은 미정 항목은 작업 브리프에 입력 대기로 적는다.

## 7. 장애·접속과 남은 결정

[결정 §8](design/win-vote-decisions.md#8-접속-단절과-재접속--n11n12)(2026-10-13 변경)에 따라 판 진행 중 참가자가 한 명이라도 끊기면(호스트 포함) 판을 종료한다. 김지훈이 이탈을 감지해 전원에게 종료 사유를 알리고 판을 끝내며, 종료 사유 화면도 맡는다. 클라이언트는 나가기 전에 서버에 나감 요청을 보내므로 서버는 직접 나감과 연결 끊김을 구분한다. 최명기는 게임 상태 중단을 맡는다. 로비 이탈은 자리만 비우고 판 시작 후 새 참가는 거절한다. 판 시작은 4명 전원 준비 시 자동이며, 게임 씬은 4명 모두 로딩·월드 생성을 마친 뒤 입력과 시계를 연다(시간 초과 시 판 종료). 월드 생성 완료 같은 기능별 준비는 서버에서 판 시작 게이트(`IMatchStartGate`)로 매니저에 등록하며, 매니저는 전원 로딩과 모든 게이트 준비 뒤 `MatchStarted`를 한 번 낸다(2026-10-16 매니저 측 구현, World 등록은 미연결). 단절된 참가자의 상태 보존·재결합은 필요하지 않다.

재접속은 10/25 이후 선택 범위이며, 채택하면 판 한정 복귀 토큰으로 설계한다. 호스트 이전과 저장·복구는 범위에 넣지 않는다. 접속은 KCP IP 직접 접속을 유지하고 인터넷 플레이 필요 여부는 미정이다(대장 N13). 배 물리 권한(v4 13장, N07)은 2026-10-13 배 주인 클라이언트로 결정됐다. 피해 원인별 최종 판정 위치와 허용 오차는 남아 있으며, 해당 기능 착수 전에 담당 간 합의로 확정한다.
